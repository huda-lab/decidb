# Lessons Learned

Corrections and patterns discovered during development. Updated after mistakes to prevent recurrence.

## Rules

- **Grammar files are templates**: Never edit `src_backend_parser_gram.cpp` directly. Edit `.y`/`.yh` files in `third_party/libpg_query/grammar/`, then run `python3 scripts/generate_grammar.py`.
- **Build before testing**: Always `make` (or `make debug`) after grammar or source changes before running tests.
- **`done.md` ⟷ `todo.md` are disjoint by construction**: A `todo.md` holds *only* remaining work; the moment a task ships, its content moves to the matching `done.md` (rewritten as present-tense "how it works" documentation, not a "✅ completed" checklist). Never leave a finished item sitting in a todo, and never let a done doc read like a list of completed action items. When implementing a todo task, the same change set updates both files: remove from todo, describe in done. Applies to every `context/descriptions/**/{done,todo}.md` pair.

## Gotchas

- **Don't rewrite aggregates to SUM at parse time if the return type matters**: Renaming `AVG(x)` → `SUM(x)` before binding changes the return type from DOUBLE to BIGINT (for integer inputs). DuckDB's comparison binding then casts fractional RHS values (e.g., `0.5`) to BIGINT → `0`, silently breaking constraints. Instead, let the original aggregate flow through binding natively (preserving its return type) and detect it at execution time via `BoundAggregateExpression::function.name`. This applies to any future aggregate rewrite where the original function's return type differs from SUM's. *(Resolved — current AVG implementation rewrites post-binding in `DecideOptimizer::RewriteAvgToSum` with `AVG_REWRITE_TAG` for execution-time scaling. Lesson retained as a general principle for future aggregate rewrites.)*
- **Big-M disjunction sign convention**: For `x ≠ K` via Big-M, BOTH constraints must have z coefficient = `-M` (not `+M`/`-M`). Correct: `x - M*z ≤ K-1` (z=0 → x ≤ K-1) and `x - M*z ≥ K+1-M` (z=1 → x ≥ K+1). Wrong sign (+M on first constraint) makes z=0 trivially satisfy both constraints, leaving x unrestricted.
- **FindDecideVariable is "find any"**: `FindDecideVariable(expr)` recursively returns the first DECIDE variable found in the expression tree. For complex LHS expressions (e.g., `z_0 + z_1`), it finds only the first variable and silently ignores the rest. Use `ExtractLinearTerms` for multi-variable LHS, or check `GetExpressionClass() == BOUND_COLUMN_REF` first.
- **FunctionExpression::is_operator defaults false**: Programmatically-created `FunctionExpression("+", ...)` has `is_operator=false`, unlike parser-created ones where it's `true`. Don't gate logic on `is_operator` for expressions from rewrites.
- **McCormick bilinear rewrite must preserve outer coefficients**: When `FindAndReplaceBilinear` (in `src/optimizer/decide/decide_optimizer.cpp`) replaces a bilinear product like `coeff * b * x` (left-associative parse `(coeff*b)*x`) with the McCormick auxiliary `w`, the `coeff` factor must be folded into the replacement (`coeff * w`) — not silently dropped. The binder inserts implicit CASTs around mixed-type multiplications, so coefficient extraction must unwrap `BoundCastExpression` before pattern-matching the `*` node. Symptom: MINIMIZE objectives produce suboptimal results (solver minimizes `SUM(w)` instead of `SUM(coeff*w)`); MAXIMIZE often masks the bug because the corner solution coincides. See `ExtractMultiplicativeCoefficient` and its call sites in the Bool×Non-Bool branch.
- **Entity-scoped DECIDE variables must register their key columns with the scan**: Columns referenced ONLY by `DECIDE Table.var` (not by SELECT/WHERE/constraints/objective) were silently pruned from the table scan at bind time. The `entity_key_bindings` on `EntityScopeInfo` then resolved to a subset of columns, and the `VarIndexer` grouped rows by whatever column happened to survive (often a WHERE-filter column like `n_regionkey`), collapsing distinct entities. Fix: at bind time in `bind_select_node.cpp`, call `TableBinding::GetColumnBinding(col_idx)` for every entity-key column to force it into `bound_column_ids`; store `BoundColumnRefExpression`s on `LogicalDecide::entity_key_expressions` so the column pruner's `VisitExpression` rebinds them alongside other columns; refresh `entity_scopes[...].entity_key_bindings` from these expressions in `plan_decide.cpp` before resolving physical indices. Symptom: single-table-no-join entity-scoped queries produced suboptimal results (entities collapsed); JOIN queries masked the bug when the join condition happened to force identity columns into the scan.
- **Snapshot aggregate sub-state before rebinding `expr` in optimizer rewrites**: Inside a `VisitExpression`-style rewrite, it is tempting to take a reference like `auto &agg = expr->Cast<BoundAggregateExpression>()` and then reassign `expr = BindAggregateFunction(...)` to swap in the rewritten aggregate. But the reassignment destroys the old `BoundAggregateExpression` that `agg` points into, so any later read of `agg.filter`, `agg.children`, `agg.alias`, etc. is a use-after-free. Always deep-copy or move the needed sub-state into a local `unique_ptr<Expression>` (or equivalent) **before** the `expr = BindAggregateFunction(...)` call, then install it on the new aggregate after. Symptom: the rewritten aggregate silently drops its WHEN filter because the optimizer was copying a freed `agg.filter` pointer, and the freed memory often still holds a plausible-looking expression so there is no crash — just a formulation that ignores the filter.
- **Read child bindings BEFORE `CreatePlan` on the child, not after**: In `plan_decide.cpp` the code captured `op.children[0]->GetColumnBindings()` *after* calling `CreatePlan(*op.children[0])`. Many logical operators (notably `LogicalProjection`) `std::move` their `expressions` vector into the physical op during CreatePlan, which leaves `GetColumnBindings()` returning an empty vector afterward. `LogicalGet` is immune because its bindings come from `column_ids`, so direct-base-table queries worked while subquery/CTE-wrapped ones silently collapsed to a single entity (`entity_key_physical_indices` stayed empty → zero key columns → every row hashed to the same entity → `keep=0` everywhere). Always snapshot anything you need from a child logical op **before** handing it to `CreatePlan`. Fix: capture `child_bindings` on entry.
- **DECIDE EXPLAIN rendering is duplicated across `LogicalDecide` and `PhysicalDecide`**: `ParamsToString()` and the tagged-expression walker (`CollectTaggedExpressionStrings` / `…Physical`) exist as near-identical copies in `src/planner/operator/logical_decide.cpp` and `src/execution/operator/decide/physical_decide.cpp`. The **default** `EXPLAIN` (`explain_output='physical_only'`) renders via the *physical* copy, so a fix applied only to the logical one looks correct in code review but does nothing to the visible output. When changing EXPLAIN rendering, edit BOTH and verify with both `physical_only` and `optimized_only` PRAGMAs. Related gotcha: `BaseExpression::GetName()` returns the `alias` verbatim when one is set (only falling back to `ToString()` when empty). A WHEN/PER-tagged objective/constraint wrapper has its alias set to the internal tag (`__when_constraint__`), so calling `GetName()` directly on the wrapper leaks the raw tag instead of rendering the expression — always route tagged wrappers through the walker.
- **Implied-bound propagation is only sound under all of: nonneg coefficients, nonneg lower bounds, every-row coverage, and `K>=0`**: `DecidePropagateImpliedBounds` derives a shared variable upper bound `maxᵣ K_r/a_r` from `<=`/`=` constraints. The shared bound applies to EVERY row instance of a decision variable, so it is valid only if every row actually constrains the variable. Three traps, each of which silently cuts the optimum (or makes the model infeasible) if missed: (1) **negative coefficients** — the `IN`/`ABS` rewrites produce constraints like `x − z₁ − 3·z₂ = 0`; dropping a negative term to get `x ≤ K/a` is invalid, so skip the constraint if ANY coefficient is `< 0`. (2) **WHEN-conditional / partial constraints** — a `WHEN`-false row (or a row where the variable's coefficient is 0, e.g. `x*w` with `w=0`) leaves that instance unconstrained; deriving the bound from the active subset wrongly caps the excluded rows. Require the variable to have a non-zero coefficient in EVERY row (`every_row_constrained`), and note WHEN-exclusion can appear as a zero coefficient, NOT only as a `row_group_ids` marker. (3) **negative RHS** — skip rows with `K_r < 0`. The differential suite catches violations as wrong optima; lean on it after any change here.
- **Big-M for objective auxiliaries needs the GLOBAL SPREAD, not the per-row magnitude**: the hard `MIN`/`MAX` objective linearizations link an aux `z`/`z_g`/`w` to the expression via `(aux − expr) ± M·y (≷) ±M`. The deactivated branch must stay slack across `maxᵣ exprmaxᵣ − minᵣ exprminᵣ` (signed bounds), which can exceed any single row's range when coefficient signs differ across rows. A magnitude-only `M` (or removing the conservative floor without computing the true spread) is a silent under-estimate that distorts mixed-sign objectives — and ordinary positive-only test data won't expose it. The per-row constraint sites are fine (`|rhs| + range + 1` bounds expr vs. a fixed RHS); only the aux-vs-variable objective sites need the spread. See `compute_big_m` in `physical_decide.cpp`.
- **Verify `build/release/decidb` is newer than the source before characterizing behavior — even when you changed nothing.** The "Build before testing" rule covers *your* edits, but the checked-out tree can already be ahead of the last build (prior-session commits you never rebuilt). Exploring diagnostics against a stale binary produced output that looked like four separate bugs (per-group labeling lost, group identity missing, exploding duplicate rows); a `make release` made all of it correct — the shipped binary predated `finalizing infeasible diagnostics`. Before drawing any conclusion from CLI output, check `stat -f "%Sm" build/release/decidb` vs. the relevant `src/**` mtimes (or just rebuild). Rebuilding is not a source change, so it's always safe even under a "no source edits" constraint.
- **A tolerance cushion in a frozen row is monetized by any secondary objective over continuous variables**: the stage-2b tie-break freezes the user objective at its stage-2a optimum and then minimizes a rank-weighted repair sum. Writing the freeze as `obj ≥ Z* − eps` (the "safe" cushion) let the LP trade the whole eps for rank improvement — shaving eps of repair onto a lower-ranked slack, splitting the reported edit (`x <= 9.999989` plus a phantom second clause). Binary variables can't exploit a sub-1 cushion, which is why the original removals-only tie-break never showed it. When freezing a solved objective before a secondary continuous pass, use the EXACT rhs (the incumbent attains it to machine precision; a rounding pathology just makes the pass non-optimal and the caller falls back) — never leave eps of room.
- **At most one per-row-binary "covering" system per DECIDE query, and `MAXIMIZE MAX`/`MINIMIZE MIN` don't scale**: the MILP-inducing constructs each add ≥1 binary per row — L0 (`norm(e,0)` count indicators), ABS hard-direction Big-M (`SUM(ABS)>=K`, `MAXIMIZE SUM(ABS)`), `<>`, hard `MIN`/`MAX`. Empirically (benchmark suite design): (1) **combining two of them in one query explodes** — L0 + an aggregate ABS-`>=` floor at 2K rows pegged all cores past 90s because the pair forms a covering problem (spread magnitude to hit the floor while minimizing nonzero count); each alone solved in <0.5s. Keep them in separate queries. (2) **hard `MAX` objective (`MAXIMIZE MAX`) couples globally** (one shared `z` + `Σy≥1` + Big-M links) and scales terribly: ~11s at 10K rows, ~32s at 20K, times out past 50K. Row-limit it hard (≤10K). (3) **ABS Big-M and L0 are per-row-independent** and scale far better (ABS-maximize at 50K rows = 2.5s). When a benchmark/diagnostic query must exercise these features, budget one binary-covering system per query and row-limit the globally-coupled ones.
- **A serialized class with hand-written flattening logic (parallel vectors for a `vector<Struct>` member) should be marked `"custom_implementation": true` in its `storage/serialization/*.json` entry, not have its fields enumerated there.** `scripts/generate_serialization.py` skips a class entirely (`generate_class_code` returns `None`) when this flag is set — DuckDB's own pattern for `LogicalGet`, `LogicalCopyToFile`, `BoundFunctionExpression`, etc., whose `Serialize`/`Deserialize` live in the class's own `.cpp` (not the generated `serialize_*.cpp`) for the same reason. `LogicalDecide` hit this: its JSON entry listed fields only up to id 215 while the generated `.cpp` hand-wrote 216-233 (flattening `entity_scopes`/`variable_scopes`, which are `vector<Struct>` the generator's direct member-mapping can't express) — so every `python3 scripts/generate_serialization.py` run would have silently dropped those fields on the next unrelated regeneration, compiling clean but round-tripping plans with no entity/variable scope data. Setting `custom_implementation: true` and moving the hand-written methods to `logical_decide.cpp` makes regeneration a proven no-op (verified: `generate_serialization.py` then leaves `serialize_logical_operator.cpp` byte-identical, with `LogicalDecide` appearing only in the base-class dispatch switch). Prefer this over listing the flattened parallel-vector fields directly in the JSON (which also works, since `has_default_by_default` auto-detects `WritePropertyWithDefault` for any container type) — the `custom_implementation` route is idiomatic-DuckDB and keeps the single source of truth in one file instead of splitting a class's serialization across a generated file and its own.
- **Never key a test on user-facing prose — use a machine-readable marker.** `test_quadratic_constraints.py`'s `_expect_gurobi` absorbed Gurobi's nondeterministic SUBOPTIMAL termination by grepping the error text for `solver status 13|[Ss]uboptimal`. The caveat was later reworded to "DECIDE is returning a feasible solution — the solver could not prove it is the best possible", which contains neither token, so the retry silently stopped firing and the file became an intermittent red (measured 3 failures in 5 consecutive runs; the termination itself occurs in ~23/40 runs of that query). This is structural, not bad luck: CLAUDE.md's user-facing-output principle *guarantees* those strings keep moving, so any test matching them is on a timer. When a test needs to recognize a solver terminal or internal state, emit a marker the principle does not own — DeciDB uses an env-gated `DECIDB_STATUS: <TERMINAL>` stderr line (`DECIDB_STATUS_MARKERS`, same pattern as `DECIDB_BENCH`), stripped by `decidb_cli.py` and surfaced as `DecidBCliError.status`. Gate it on the env var so user-facing output is byte-identical, and only set the var from the call path that strips it (`execute`), never from `execute_raw`/`execute_script`, whose callers classify raw stderr themselves and would read the marker as an error.
- **A "flaky test" whose harness turns an advisory into an exception is usually a misclassification, not nondeterminism.** The SUBOPTIMAL case above reached the test as a `DecidBCliError` only because `DecidBCli.execute` raises on *any* stderr line not prefixed `Warning:` — but DeciDB returns the rows and prints the caveat as an advisory, i.e. the solve succeeded. Before adding retries or widening a regex, check whether the harness is classifying a successful run as a failure; the stale docstring ("DeciDB soundly declines to return it") was describing behavior that had already changed.
- **Any new `Expression`-holding field on `LogicalDecide` must be registered with `ColumnBindingResolver`.** The resolver's `LOGICAL_DECIDE` case (`src/execution/column_binding_resolver.cpp`) enumerates DECIDE's expressions *by hand* — `decide_variables`, `decide_constraints`, `decide_objective` — rather than through `VisitOperatorExpressions`, because DECIDE variables must be shielded from resolution via `ignored_bindings`. So a rewrite that **moves** sub-expressions out of those trees into a side vector silently opts them out of resolution. That is what the composed MIN/MAX rewrite did: `RewriteComposedMinMaxObjectiveTop` lifts each aggregate's inner expression into `composed_minmax_objective_terms` and leaves a constant placeholder behind, so the lifted expressions kept raw `BoundColumnRefExpression`s. `TransformToChunkExpression` then read `binding.column_index` — a *logical* index — as a position in the materialized chunk, so `D.c` silently evaluated as `R.rid`. **A single-table source hides this completely**, because the logical index and the chunk position coincide; it only appears once a join reorders them. Every pre-existing composed MIN/MAX test used `VALUES`/single-table sources, so the whole suite passed against a wrong answer. Two rules follow: (1) when adding a field on `LogicalDecide` that holds expressions the physical layer will evaluate, add it to the resolver's case in the same change; (2) any test for a feature that evaluates coefficient expressions must use a **multi-table join**, or it cannot distinguish logical bindings from chunk positions.
- **`xfail(strict=True)` is the right pin for a confirmed defect, and XPASS is the signal to delete it.** Both composed MIN/MAX defects were pinned as strict xfails with the reproduction in the docstring. When the fix landed, pytest reported `XPASS(strict)` as a *failure* — an unmissable prompt to remove the marker and rewrite the docstring as a regression note. A non-strict xfail would have gone green silently and left a misleading "known defect" comment in the tree.
- **In `decide_symbolic.cpp`, a CAS-visible `MARKER * inner` encoding is only safe for constructs that actually distribute over addition.** `SUM`/`AVG` round-trip through the CAS as `Symbolic("__SUM__") * inner` and it's fine, because `SUM(a+b) == SUM(a)+SUM(b)` — the marker reassembles correctly no matter how `.expand()` redistributes it. `MIN`/`MAX` used the same encoding and were wrong: `MIN(a+b) != MIN(a)+MIN(b)`, so `.expand()` distributing `__MIN__` across a multi-term inner scrambled it into a different (and wrong) expression tree before reassembly — see `06_issues/bugs/done.md` → "`SUM(MIN(expr)) PER col` rejected a multi-term inner MIN/MAX argument at bind time". The fix, and the correct default for any non-distributive construct (a future CASE-like or windowed thing, say) passing through this layer: wrap the *whole* node as one opaque placeholder symbol in a dedicated map (mirrors `abs_map`/`data_map`/`subquery_map`/`column_map`) and restore it verbatim in `FromSymbolic`, never let the CAS see inside it. Before adding a new `MARKER * inner` site here, check whether the construct distributes over `+`; if not, use the opaque-placeholder idiom instead.
- **A DECIDE binder's catch-all `expr.ToString()` fallback (e.g. `decide_constraints_binder.cpp`'s "SUCH THAT clause does not support '%s'(ExpressionClass::%s)") will render whatever internal tag or C++ enum happens to be attached to the rejected node — it has no idea which shape it's being asked to describe.** Fixing the wording in place is unsafe: the same throw site is shared across every unrecognized shape, so a rewrite tuned for one input reads wrong (or misleadingly) for the others. Before touching the fallback text, trace the *actual* parsed shape reaching it (add a temporary `fprintf` at entry logging the node's `ToString()`/`is_top_expression`/`depth` — do not trust a static read of the binder's dispatch chain, since `is_top_expression`/`depth` state threads through many mutually-recursive `BindX` calls and is easy to get backwards by inspection alone). Once the exact reachable shape is confirmed, add an earlier, narrower check that recognizes just that shape and throws a specific SQL-facing message, leaving the shared catch-all's wording untouched for every other input that still falls into it.
- **A per-variable domain signal already threaded end-to-end is the DomainSpec — don't invent a parallel one.** Fixing "BOOL domains round-trip through the constraint tree instead of being variable bounds" (`context/descriptions/06_issues/code_quality/todo.md`) turned out to need no new data structure: `is_boolean_var` (`BoundSelectNode` → `LogicalDecide`, serialized → `PhysicalDecide`) was already the exact carrier the issue asked for, and `ilp_model_builder.cpp`'s `SolverModel::Build` already applied `LogicalType::BOOLEAN` directly to `col_lower`/`col_upper`/`is_binary` for optimizer-created indicators (MIN/MAX, NE) — the DomainSpec-via-type pattern already existed for *some* producers of `is_boolean_var`. The only gap was that user-declared `x(BOOL)` and INTEGER-typed auxiliaries (IN-domain, L0 — which must stay INTEGER so they can appear in arithmetic like `M * z`) fed `is_boolean_var=true` but the binder still synthesized `x >= 0 AND x <= 1` constraint rows for *them specifically*, and `TraverseBoundsConstraints` pattern-matched those rows back into bounds. The fix was one override at the point `SolverInput::variable_types` is built (`physical_decide.cpp` `Finalize`): report `LogicalType::BOOLEAN` whenever `is_boolean_var[var]` is true, regardless of the DuckDB-facing type, unifying every producer onto the one existing type-driven bounds path and deleting both constraint-injection loops in `bind_select_node.cpp`. Before reaching for a new struct, check whether an existing per-variable flag threaded through the whole pipeline already carries the exact partition needed — and whether the "elegant" application mechanism already exists for a subset of producers, waiting to be generalized rather than reinvented.
- **A grammar production keyed on `func_application` doesn't automatically cover other `c_expr` alternatives that "look like" a function call.** Aggregate-local WHEN (`func_application WHEN_DECIDE decide_when_condition`) only fires for the specific `func_application` nonterminal; the relation-qualified reducer (`func_name '(' func_arg_list ':' func_arg_list ')'`) is a sibling `c_expr` alternative, not a `func_application`, so `sum(D: expr) WHEN cond` fell through to the loose, whole-constraint `a_expr WHEN_DECIDE b_expr` production instead, which swallowed a trailing comparison (`<= bound`) into the WHEN condition — silently producing a bare, comparison-less LHS. The binder-side plumbing (`ContainsDecideAggregate`, `GetExpressionType`) already unwrapped the composition correctly, proven by the objective side (no trailing comparison to lose there) — the fix was purely a second grammar alternative mirroring the first, not a binder change. When adding a WHEN/postfix production for one `c_expr` alternative, check whether every other alternative that could sit in the same position needs its own copy; don't assume `func_application` is the only shape reaching that point. See `03_expressivity/decide/done.md` → "Relation-qualified reducers".
- **A worktree-isolated agent must never `cd` into the shared checkout, even for a "harmless" read-only command like running tests.** Bash's cwd persists only *within* one call (`cmd1 && cmd2`), not *across* calls in this harness — each new Bash invocation starts back at the agent's pinned worktree directory. But a command that explicitly does `cd /path/to/main/checkout && test/decide/run_tests.sh ...` runs entirely against the main checkout's files for that call: its own binary, its own copy of every test file. Four consecutive test runs (999 tests + a `--collect-only`) all silently validated the *pre-fix* code and never saw two newly-added test methods, because `cd` had pointed pytest at `/Users/hatim/Code/decidb` instead of the worktree — the harness's own git-tool guard (which blocks `git -C <other-checkout>`) doesn't cover plain `cd` + non-git commands, so nothing errors; the results just quietly describe the wrong tree. Never prefix a command with `cd <other-checkout>`; if some absolute-path anchor is needed, use the worktree's own path (or none, since cwd already defaults there).
- **"This rewrite is unsound, replace it" is usually too strong — find the one respect in which it is unsound, and the layer it belongs in.** The canonicalization plan concluded that folding a factor into a reducer (`K * SUM(x)` → `SUM(K*x)`) was inherently unsound and had to be replaced by peeling the factor *outward*, and budgeted three downstream consumers to learn a new `{sign, scale, term}` shape. Both halves were wrong. The fold is unsound in exactly **one** respect — it was sign-blind, and `MAX(-2x)` is `-2*MIN(x)`, so a negative factor must SWAP MIN and MAX — and it was in the **wrong layer**: it ran on the parsed tree, where the aggregate kind is not yet settled (AVG→SUM and the MIN/MAX linearizations have not run). Adding the swap and moving it to the optimizer made it exact, and no consumer needed changing. **That still turned out to be the wrong destination, for a reason exactness does not capture: folding must CHOOSE MIN or MAX, so it depends on the factor's sign, so it has no answer when the sign is unknown** — an uncorrelated scalar subquery factor died on an internal assertion. The final design keeps the factor outside the reducer permanently, which removes the dependence instead of satisfying it: the sign then only selects which linearization is cheaper. Two lessons, then. Before replacing a rewrite, separate "the transform is wrong" from "the transform is right but blind to one property" from "the transform is right but running where it cannot see what it needs". And when a transform needs a fact to proceed, ask whether the design can be changed so it never needs that fact — that is strictly better than computing it, because the fact may not exist yet.
- **A grep that "proves nothing depends on this" is evidence about the grep, not the code — vary the spelling before reporting it.** Recommending a behavior change, I searched for a data column outside an aggregate with `[a-z_]+ *\* *(SUM|MAX|MIN|AVG)\(` and reported "no test writes this shape". Three did; the pattern missed `col * (SUM(x) WHEN w)` because of the parenthesis, and the whole recommendation was handed to the user resting on that. The suite found them ten minutes later. For a claim of *absence* over a syntax-flexible language, either search on a semantic anchor (here: run the suite, or grep for the aggregate name alone and read the hits) or state the pattern's limits alongside the claim.
- **After subquery flattening, an uncorrelated scalar subquery is indistinguishable from a per-row column — capture the distinction before `PlanSubqueries`, and capture it as data, not as a tag on a node.** `(SELECT k FROM p)` becomes a `BoundColumnRefExpression` whose column is literally named `SUBQUERY`, exactly like `weight`. Two approaches were tried. Tagging the flattened node (save the owning `unique_ptr` slot pre-flatten, stamp the alias post-flatten) relies on that slot surviving a rewrite that may rebuild parent nodes — it demonstrably did not work and was silently wrong rather than loud. What does work: snapshot `root->GetColumnBindings()` *before* `PlanSubqueries` and pass the table-index set down; any column ref outside it is query-wide by construction, because flattening can only add bindings. Prefer a set of stable identifiers captured at the right moment over a mark attached to a node you do not own.
- **Reusing a bound function with substituted children requires re-checking the children against `function.arguments`.** `ExtractCoefficientWithoutVariable` strips a decision variable out of a product and rebuilds the multiply with the original resolved `ScalarFunction` and return type. Stripping the variable also strips the casts above it, so a child can come back *narrower* than the signature was bound for (`CAST(x * price AS DECIMAL(38,2))` leaves a bare `DECIMAL(15,2)` price). DuckDB does not validate this — the function reads the child's physical representation as if it were the declared width and returns a plausible wrong number, no error. Symptom was an objective off by a non-obvious ratio (25707.60 vs 48163.50) while the *hand-written* equivalent expression was correct, which is the tell: same shape, different types. Always `AddDefaultCastToType(child, func.function.arguments[i])` when rebuilding.
- **To prove a code path is dead, make it `throw` — an `fprintf` probe is silently swallowed by the pytest suite.** the canonicalization refactor recommends a temporary `fprintf` in a branch to distinguish "fires and is inert" from "never fires", and that works when driving `build/release/decidb` directly. It does **not** work through `make decide-test`: `run_tests.sh` runs `pytest -v` without `-s`, and pytest captures stderr at the file-descriptor level, so a clean run tells you nothing about whether the printf executed. Two options, and the second is better. Pass `-s` (`test/decide/run_tests.sh -s -q`) to let stderr through — fine for observing *which* shapes reach a branch. But when the claim is "this branch is unreachable and can be deleted", replace its body with `throw InternalException(...)` instead: a throw cannot be captured away, because it surfaces as a test failure. That converts silence from absence-of-evidence into proof, which is exactly what a deletion needs. Used at C.3 to show the physical per-row re-partition never executed across 71 corpus models and 1041 tests; it also disproved a written prediction that those sites were covering B.2's cast-descent shapes (they were covering nothing).
- **When deleting a duplicated implementation, leave a guard, not a hole.** C.3 deleted the physical operator's re-partition of a decision-bearing RHS because `DecideCanonicalizer` (K1) already guarantees it never happens. Deleting outright would have been a *silent* wrong answer if K1 were ever broken — the RHS is evaluated as data, so a stray decision column ref reads as a data column rather than erroring. A three-line check that throws on the invariant violation costs nothing and converts "a future rewrite broke this" from a wrong answer into a loud failure. Where an invariant makes code deletable, the invariant is worth asserting at the place that used to handle the violation.
- **A validation gate that never fires and a validation gate that is correct look identical from the outside — so measure a layer before trusting the checks *behind* it.** C.4 disabled the parsed-level constraint simplifier and expected either zero failures (delete it) or failures naming things it simplified. What actually failed was neither: `SUM(x * POWER(qty, 2))` stopped binding, because `ValidateQuadraticPower` demanded that *every* POWER base reference a decision variable — including one that is pure data and therefore just a per-row coefficient. That gate had never fired on a real query in its life, because the simplifier lowered `POWER(qty, 2)` to `qty * qty` through SymbolicC++ before binding, so no POWER node ever reached it. The lesson generalizes past this instance: when you remove or disable a *transforming* layer, the failures you get are not only "things it was computing" — some are **checks downstream that were being fed a shape they never had to handle**. Read each failure for which of the two it is before concluding the layer was load-bearing. (Same file, earlier instance: `SimplifyComparisonExpr`'s `if (!ContainsSumFunction(lhs)) return` made every rewrite below it dead for a MIN/MAX-only LHS, so one helper was simultaneously dead code and a live wrong answer depending on whether a SUM shared the LHS.)
- **A byte-identical golden dump across a large deletion is only ambiguous when the deleted code might never have run.** C.3 had to rule that out with a `throw` probe, because its branch was plausibly dead. C.4 did not: the parsed-level simplifier demonstrably ran on most corpus entries, so 74/74 models unchanged after deleting ~400 lines of it means the *other* implementation was already producing the same models from the un-simplified tree. Same observation, opposite epistemic value, decided entirely by whether the deleted code was known to execute. Establish that first, then read the dump.
- **When the same bug keeps coming back in a new place, count the places — then remove the decision rather than guarding each one.** Casts broke DECIDE repeatedly. Each fix guarded the site that failed; a census found **45** cast-unwrapping sites, 42 of them independent (including three byte-identical `UnwrapCasts` helpers in different files), only 12 guarded. Guarding does not converge, because the next bug is in one of the other 33 and nothing tells you which. What converged was making the question un-askable downstream: pick the domain the system already commits to (here `DOUBLE` — the solver interface is `vector<double>`, so every value lands there whatever the tree said), reject at ONE boundary anything that would violate it, and the unguarded peels become correct by construction. That also deleted the machinery built to survive the old ambiguity: a 430-line exact cast inverter, eight struct fields, and a per-row lattice search costing 120x on `SUM(x) <= <decimal>`. Check what the layer below you actually accepts before building precision above it. Two supporting notes: (1) DuckDB solves the identical problem this way — one predicate (`BoundCastExpression::CastIsInvertible`), one rewrite rule, run early so nothing downstream sees a cast, and it declines rather than approximating when it cannot be exact; (2) an invariant that removes a decision must state its own scope, and the scope is where the bugs move to. The first cut of the shared unwrap helper peeled unconditionally "because the canonicalizer guarantees it" — true only on the *decision* path. `x <= CAST(1.6 AS INTEGER)` is data, where the rounding is the user's request, and it silently became `x <= 1`. Fixed by putting the predicate in the helper itself so one function is right on both paths, and splitting off a separately named `StripCastsForDisplay` for rendering, which is the one job where an unconditional peel is correct because the output is a label and not a value.
- **When the same expression is accepted in one clause and rejected in another, that asymmetry is a bug — and the clause that accepts it is often the one being propped up.** `SUM((x + y) * z)` bound fine in `MAXIMIZE` and was rejected in `SUCH THAT` as a "triple or higher-order product (total degree > 2)". Neither half was arbitrary: the binder gated products with `CountDecideVariableOccurrencesInternal`, which counts *occurrences* (3 here), not polynomial *degree* (2 — it expands to `x*z + y*z`), and objectives were masked because SymbolicC++ pre-expanded the product before the gate ran while constraints were never expanded. So the working clause was working by accident, and deleting the CAS was what made the defect visible in both. Two rules. (1) **Occurrence count is not degree**: an additive node contributes the MAX of its children's degrees, a multiplicative node the SUM. If a check says "degree" and computes a count, it is wrong for every factored form the user is most likely to write — `(x+y)*z` is the natural spelling of "z gates the pair". (2) Treat a clause-to-clause behavior difference as a defect report before treating it as a design decision; here it named the bug precisely, since the two clauses share `ValidateSumArgumentInternal` and differ only in what ran upstream. Corollary for deletions: a test that fails when you remove a transform is not automatically evidence the transform was load-bearing — check whether it is a pre-existing bug the transform was hiding. See the canonicalization refactor.

- **A failure path that leaves its out-parameter untouched hands every consumer an unstated precondition — and a struct without default member initializers makes that precondition undetectable.** `SolveModel` catches `DecideInfeasibleModelException` from `SolverModel::Build` and returns `INFEASIBLE` *without writing* `*retained_model`, so with diagnosis armed the operator walked a default-constructed `SolverModel`. `idx_t num_vars;` had no initializer, so it held stack garbage (measured: 4408228160) and every `if (col >= retained_model.num_vars) continue;` guard — there are several, and they read like careful code — passed straight through into an empty `col_upper`, aborting the connection fatally. Three things follow. (1) **Give every struct that can be default-constructed as "not yet produced" real default initializers**, so "never populated" is representable and the existing guards actually guard; a field left uninitialized converts a correct check into a coin flip. (2) **Prefer removing the early exit over defending against it**: the fix was to stop throwing at all — `PushNormalizedConstraint` keeps the violated coefficient-free row, flags `model.build_proven_infeasible`, and `SolveModel` short-circuits to `INFEASIBLE` with the model retained, which is exactly the shape the inverted-column-box path in the same function had used for the same reason. The clause then flows through the ordinary infeasible-diagnosis engine, which already had the guard it needed (`editable_weight`'s comment literally reads "guarding a degenerate all-zero row") and had simply never been sent one. (3) **A release stack trace that names one huge inlined function is not a location, and the written "where to look next" guess can be confidently wrong** — this bug's note sent the reader to the elastic engine, which was innocent. Three `fprintf`s and one incremental rebuild printed the empty model directly; that is cheaper than a debug build and far cheaper than reasoning down the wrong path.
- **A value-domain guard must match the contract it defends, and every sibling path that carries the same value**: `ExtractDoubleColumn` refused every non-finite RHS, but the model validator it feeds has always accepted `±inf` and rejected only NaN — and two other RHS paths (a constant bound, a bound absorbed into the column box) never checked at all. So `x <= 1e1000` solved while `x + v <= 1e1000` was refused: canonicalization rebuilds the second as `x <= 1e1000 - v`, which is the same bound routed onto the one strict path. When a rewrite re-routes a value, diff the new path's guards against the old path's, and against what the layer below actually requires; a guard stricter than its contract turns a spelling difference into a behavior difference. Corollary for the other direction: relaxing an input guard pushes the value into consumers that were never reachable before. Here the freed infinity flowed into the Big-M sites, where it became an `inf` coefficient and an `InternalException` — so those sites now refuse it in SQL terms, and the `<>` tautology drop was reordered ahead of its Big-M computation so a vacuous row is dropped rather than refused.
- **A sentinel standing in for "no bound" hides an out-of-range value in exactly one direction**: `absorbed_lower_bounds` starts at `-1e30` and tightens with `max`; `absorbed_upper_bounds` starts at `1e30` and tightens with `min`. So `x <= +inf` was absorbed to the sentinel and vanished, while `x >= +inf` was absorbed as `+inf` and reached the bounds validator as a non-finite column — an `InternalException` that also invalidates the connection, for a query whose mirror image answered fine. Check a value against the box's own range *before* the `min`/`max`, not after; the clamp is precisely what makes one direction look healthy. Better still, leave such a value to the general path (here, an ordinary constraint row) instead of encoding it in a fast path with no room for it — absorption is an optimization, and skipping it costs one row.
- **Classify a bound before asking a rewrite to encode it**: `MIN(x) <= +inf` was refused because no finite Big-M dominates infinity — but that constraint rules out nothing, so it never needed an `M` at all. The working order is: read what the bound means (vacuous / unsatisfiable / finite), drop or report the first two, and compute `M` only over what is left. `<>` already did this with its tautology drop; MIN/MAX did not. Wherever a rewrite refuses a value, ask first whether that value makes the rewrite unnecessary.
- **A pass over terms must key on the variable, not on the term**: implied-bound propagation derived `x <= K/a` once per term, so `2*ship + 3*ship <= 10` produced two candidate bounds (5 and 10/3) and kept the tighter — never the correct one (10/5 = 2), because the two terms name the *same* solver column and only their sum describes it. The optimum stayed right and the emitted row stayed right, so nothing failed; only the model dump showed it. A term list is a spelling, not a set of distinct variables: any pass that reads a coefficient per term and applies it per variable has to fold the repeats first. Anywhere `variable_indices` is iterated, ask whether an index can appear twice.
- **Before relocating a pass in a pipeline, find which earlier passes emit input it consumes — and check that branch is actually covered.** Bound absorption looked like a self-contained walk that could move anywhere in `DecideOptimizer`. It cannot: `RewriteInDomain` emits a floor-lowering `x >= min_value` for a negative all-constant `IN` domain, which is itself absorbable, so absorption has to run *after* it. Run it earlier and the floor stays at 0, the negative domain value becomes unreachable, and the solver returns a different optimum — a wrong answer, not an error. The trap was that nothing tested it: the golden corpus had one `IN` query, all-positive, and every `test_cons_in.py` case used a non-negative domain, so the byte-identical golden diff would have come back clean either way. When a refactor's safety net is a characterization dump, first confirm the dump actually exercises the branch the refactor can break; add the coverage as its own commit so the recapture stays separable from the move.
- **A tag on the tree beats a placeholder when the tree is also a user-facing rendering.** Moving a decision upstream tempts you to erase what it consumed — `RewriteComposedMinMax` swaps a handled comparison for a `TRUE` placeholder, which is a real precedent. But `EXPLAIN` renders DECIDE constraints from that same tree, and `test_explain.py` asserts an absorbed `x <= 10` still shows. Marking the node (`ABSORBED_BOUND_TAG`) moves the decision without moving the rendering, and the tag travels across layer boundaries where a raw `Expression*` handshake cannot. Ask what else reads the structure before deleting from it.
