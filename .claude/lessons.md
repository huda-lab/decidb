# Lessons Learned

Corrections and patterns discovered during development. Updated after mistakes to prevent recurrence.

## Rules

- **Grammar files are templates**: Never edit `src_backend_parser_gram.cpp` directly. Edit `.y`/`.yh` files in `third_party/libpg_query/grammar/`, then run `python3 scripts/generate_grammar.py`.
- **Build before testing**: Always `make` (or `make debug`) after grammar or source changes before running tests.
- **`done.md` ⟷ `todo.md` are disjoint by construction**: A `todo.md` holds *only* remaining work; the moment a task ships, its content moves to the matching `done.md` (rewritten as present-tense "how it works" documentation, not a "✅ completed" checklist). Never leave a finished item sitting in a todo, and never let a done doc read like a list of completed action items. When implementing a todo task, the same change set updates both files: remove from todo, describe in done. Applies to every `context/descriptions/**/{done,todo}.md` pair.

## Gotchas

- **Don't rewrite aggregates to SUM at parse time if the return type matters**: Renaming `AVG(x)` → `SUM(x)` before binding changes the return type from DOUBLE to BIGINT (for integer inputs). DuckDB's comparison binding then casts fractional RHS values (e.g., `0.5`) to BIGINT → `0`, silently breaking constraints. Instead, let the original aggregate flow through binding natively (preserving its return type) and detect it at execution time via `BoundAggregateExpression::function.name`. This applies to any future aggregate rewrite where the original function's return type differs from SUM's. *(Resolved — current AVG implementation rewrites post-binding in `DecideOptimizer::RewriteAvgToSum` with `AVG_REWRITE_TAG` for execution-time scaling. Lesson retained as a general principle for future aggregate rewrites.)*
- **Big-M disjunction sign convention**: For `x ≠ K` via Big-M, BOTH constraints must have z coefficient = `-M` (not `+M`/`-M`). Correct: `x - M*z ≤ K-1` (z=0 → x ≤ K-1) and `x - M*z ≥ K+1-M` (z=1 → x ≥ K+1). Wrong sign (+M on first constraint) makes z=0 trivially satisfy both constraints, leaving x unrestricted.
- **FindDecideVariable is "find any"**: `FindDecideVariable(expr)` recursively returns the first DECIDE variable found in the expression tree. For complex LHS expressions (e.g., `z_0 + z_1`), it finds only the first variable and silently ignores the rest. Use `ExtractLinearTerms` for multi-variable LHS, or check `GetExpressionClass() == BOUND_COLUMN_REF` first.
- **FunctionExpression::is_operator defaults false**: Programmatically-created `FunctionExpression("+", ...)` has `is_operator=false`, unlike parser-created ones where it's `true`. Don't gate logic on `is_operator` for expressions from rewrites.
- **McCormick bilinear rewrite must preserve outer coefficients**: When `FindAndReplaceBilinear` (in `src/optimizer/decide/decide_optimizer.cpp`) replaces a bilinear product like `coeff * b * x` (left-associative parse `(coeff*b)*x`) with the McCormick auxiliary `w`, the `coeff` factor must be folded into the replacement (`coeff * w`) — not silently dropped. The binder inserts implicit CASTs around mixed-type multiplications, so coefficient extraction must unwrap `BoundCastExpression` before pattern-matching the `*` node. Symptom: MINIMIZE objectives produce suboptimal results (solver minimizes `SUM(w)` instead of `SUM(coeff*w)`); MAXIMIZE often masks the bug because the corner solution coincides. See `ExtractMultiplicativeCoefficient` and its call sites in the Bool×Non-Bool branch.
- **Entity-scoped DECIDE variables must register their key columns with the scan**: Columns referenced ONLY by `DECIDE Table.var` (not by SELECT/WHERE/constraints/objective) were silently pruned from the table scan at bind time. The `entity_key_bindings` on `EntityScopeInfo` then resolved to a subset of columns, and the `VarIndexer` grouped rows by whatever column happened to survive (often a WHERE-filter column like `n_regionkey`), collapsing distinct entities. Fix: at bind time in `bind_select_node.cpp`, call `TableBinding::GetColumnBinding(col_idx)` for every entity-key column to force it into `bound_column_ids`; store `BoundColumnRefExpression`s on `LogicalDecide::entity_key_expressions` so the column pruner's `VisitExpression` rebinds them alongside other columns; refresh `entity_scopes[...].entity_key_bindings` from these expressions in `plan_decide.cpp` before resolving physical indices. Symptom: single-table-no-join entity-scoped queries produced suboptimal results (entities collapsed); JOIN queries masked the bug when the join condition happened to force identity columns into the scan.
- **Snapshot aggregate sub-state before rebinding `expr` in optimizer rewrites**: Inside a `VisitExpression`-style rewrite, it is tempting to take a reference like `auto &agg = expr->Cast<BoundAggregateExpression>()` and then reassign `expr = BindAggregateFunction(...)` to swap in the rewritten aggregate. But the reassignment destroys the old `BoundAggregateExpression` that `agg` points into, so any later read of `agg.filter`, `agg.children`, `agg.alias`, etc. is a use-after-free. Always deep-copy or move the needed sub-state into a local `unique_ptr<Expression>` (or equivalent) **before** the `expr = BindAggregateFunction(...)` call, then install it on the new aggregate after. Symptom: the rewritten aggregate silently drops its WHEN filter because the optimizer was copying a freed `agg.filter` pointer, and the freed memory often still holds a plausible-looking expression so there is no crash — just a formulation that ignores the filter.
- **Read child bindings BEFORE `CreatePlan` on the child, not after**: In `plan_decide.cpp` the code captured `op.children[0]->GetColumnBindings()` *after* calling `CreatePlan(*op.children[0])`. Many logical operators (notably `LogicalProjection`) `std::move` their `expressions` vector into the physical op during CreatePlan, which leaves `GetColumnBindings()` returning an empty vector afterward. `LogicalGet` is immune because its bindings come from `column_ids`, so direct-base-table queries worked while subquery/CTE-wrapped ones silently collapsed to a single entity (`entity_key_physical_indices` stayed empty → zero key columns → every row hashed to the same entity → `keep=0` everywhere). Always snapshot anything you need from a child logical op **before** handing it to `CreatePlan`. Fix: capture `child_bindings` on entry.
- **DECIDE EXPLAIN rendering is duplicated across `LogicalDecide` and `PhysicalDecide`**: `ParamsToString()` and the tagged-expression walker (`CollectTaggedExpressionStrings` / `…Physical`) exist as near-identical copies in `src/planner/operator/logical_decide.cpp` and `src/execution/operator/decide/physical_decide.cpp`. The **default** `EXPLAIN` (`explain_output='physical_only'`) renders via the *physical* copy, so a fix applied only to the logical one looks correct in code review but does nothing to the visible output. When changing EXPLAIN rendering, edit BOTH and verify with both `physical_only` and `optimized_only` PRAGMAs. Related gotcha: `BaseExpression::GetName()` returns the `alias` verbatim when one is set (only falling back to `ToString()` when empty). A WHEN/PER-tagged objective/constraint wrapper has its alias set to the internal tag (`__when_constraint__`), so calling `GetName()` directly on the wrapper leaks the raw tag instead of rendering the expression — always route tagged wrappers through the walker.
- **Implied-bound propagation is only sound under all of: nonneg coefficients, nonneg lower bounds, every-row coverage, and `K>=0`**: `DecidePropagateImpliedBounds` derives a shared variable upper bound `maxᵣ K_r/a_r` from `<=`/`=` constraints. The shared bound applies to EVERY row instance of a decision variable, so it is valid only if every row actually constrains the variable. Three traps, each of which silently cuts the optimum (or makes the model infeasible) if missed: (1) **negative coefficients** — the `IN`/`ABS` rewrites produce constraints like `x − z₁ − 3·z₂ = 0`; dropping a negative term to get `x ≤ K/a` is invalid, so skip the constraint if ANY coefficient is `< 0`. (2) **WHEN-conditional / partial constraints** — a `WHEN`-false row (or a row where the variable's coefficient is 0, e.g. `x*w` with `w=0`) leaves that instance unconstrained; deriving the bound from the active subset wrongly caps the excluded rows. Require the variable to have a non-zero coefficient in EVERY row (`every_row_constrained`), and note WHEN-exclusion can appear as a zero coefficient, NOT only as a `row_group_ids` marker. (3) **negative RHS** — skip rows with `K_r < 0`. The differential suite catches violations as wrong optima; lean on it after any change here.
- **Big-M for objective auxiliaries needs the GLOBAL SPREAD, not the per-row magnitude**: the hard `MIN`/`MAX` objective linearizations link an aux `z`/`z_g`/`w` to the expression via `(aux − expr) ± M·y (≷) ±M`. The deactivated branch must stay slack across `maxᵣ exprmaxᵣ − minᵣ exprminᵣ` (signed bounds), which can exceed any single row's range when coefficient signs differ across rows. A magnitude-only `M` (or removing the conservative floor without computing the true spread) is a silent under-estimate that distorts mixed-sign objectives — and ordinary positive-only test data won't expose it. The per-row constraint sites are fine (`|rhs| + range + 1` bounds expr vs. a fixed RHS); only the aux-vs-variable objective sites need the spread. See `compute_big_m` in `physical_decide.cpp`.
- **Verify `build/release/decidb` is newer than the source before characterizing behavior — even when you changed nothing.** The "Build before testing" rule covers *your* edits, but the checked-out tree can already be ahead of the last build (prior-session commits you never rebuilt). Exploring diagnostics against a stale binary produced output that looked like four separate bugs (per-group labeling lost, group identity missing, exploding duplicate rows); a `make release` made all of it correct — the shipped binary predated `finalizing infeasible diagnostics`. Before drawing any conclusion from CLI output, check `stat -f "%Sm" build/release/decidb` vs. the relevant `src/**` mtimes (or just rebuild). Rebuilding is not a source change, so it's always safe even under a "no source edits" constraint.
- **A tolerance cushion in a frozen row is monetized by any secondary objective over continuous variables**: the stage-2b tie-break freezes the user objective at its stage-2a optimum and then minimizes a rank-weighted repair sum. Writing the freeze as `obj ≥ Z* − eps` (the "safe" cushion) let the LP trade the whole eps for rank improvement — shaving eps of repair onto a lower-ranked slack, splitting the reported edit (`x <= 9.999989` plus a phantom second clause). Binary variables can't exploit a sub-1 cushion, which is why the original removals-only tie-break never showed it. When freezing a solved objective before a secondary continuous pass, use the EXACT rhs (the incumbent attains it to machine precision; a rounding pathology just makes the pass non-optimal and the caller falls back) — never leave eps of room.
- **At most one per-row-binary "covering" system per DECIDE query, and `MAXIMIZE MAX`/`MINIMIZE MIN` don't scale**: the MILP-inducing constructs each add ≥1 binary per row — L0 (`norm(e,0)` count indicators), ABS hard-direction Big-M (`SUM(ABS)>=K`, `MAXIMIZE SUM(ABS)`), `<>`, hard `MIN`/`MAX`. Empirically (benchmark suite design): (1) **combining two of them in one query explodes** — L0 + an aggregate ABS-`>=` floor at 2K rows pegged all cores past 90s because the pair forms a covering problem (spread magnitude to hit the floor while minimizing nonzero count); each alone solved in <0.5s. Keep them in separate queries. (2) **hard `MAX` objective (`MAXIMIZE MAX`) couples globally** (one shared `z` + `Σy≥1` + Big-M links) and scales terribly: ~11s at 10K rows, ~32s at 20K, times out past 50K. Row-limit it hard (≤10K). (3) **ABS Big-M and L0 are per-row-independent** and scale far better (ABS-maximize at 50K rows = 2.5s). When a benchmark/diagnostic query must exercise these features, budget one binary-covering system per query and row-limit the globally-coupled ones.
- **A serialized class with hand-written flattening logic (parallel vectors for a `vector<Struct>` member) should be marked `"custom_implementation": true` in its `storage/serialization/*.json` entry, not have its fields enumerated there.** `scripts/generate_serialization.py` skips a class entirely (`generate_class_code` returns `None`) when this flag is set — DuckDB's own pattern for `LogicalGet`, `LogicalCopyToFile`, `BoundFunctionExpression`, etc., whose `Serialize`/`Deserialize` live in the class's own `.cpp` (not the generated `serialize_*.cpp`) for the same reason. `LogicalDecide` hit this: its JSON entry listed fields only up to id 215 while the generated `.cpp` hand-wrote 216-233 (flattening `entity_scopes`/`variable_scopes`, which are `vector<Struct>` the generator's direct member-mapping can't express) — so every `python3 scripts/generate_serialization.py` run would have silently dropped those fields on the next unrelated regeneration, compiling clean but round-tripping plans with no entity/variable scope data. Setting `custom_implementation: true` and moving the hand-written methods to `logical_decide.cpp` makes regeneration a proven no-op (verified: `generate_serialization.py` then leaves `serialize_logical_operator.cpp` byte-identical, with `LogicalDecide` appearing only in the base-class dispatch switch). Prefer this over listing the flattened parallel-vector fields directly in the JSON (which also works, since `has_default_by_default` auto-detects `WritePropertyWithDefault` for any container type) — the `custom_implementation` route is idiomatic-DuckDB and keeps the single source of truth in one file instead of splitting a class's serialization across a generated file and its own.
- **Never key a test on user-facing prose — use a machine-readable marker.** `test_quadratic_constraints.py`'s `_expect_gurobi` absorbed Gurobi's nondeterministic SUBOPTIMAL termination by grepping the error text for `solver status 13|[Ss]uboptimal`. The caveat was later reworded to "DECIDE is returning a feasible solution — the solver could not prove it is the best possible", which contains neither token, so the retry silently stopped firing and the file became an intermittent red (measured 3 failures in 5 consecutive runs; the termination itself occurs in ~23/40 runs of that query). This is structural, not bad luck: CLAUDE.md's user-facing-output principle *guarantees* those strings keep moving, so any test matching them is on a timer. When a test needs to recognize a solver terminal or internal state, emit a marker the principle does not own — DeciDB uses an env-gated `DECIDB_STATUS: <TERMINAL>` stderr line (`DECIDB_STATUS_MARKERS`, same pattern as `DECIDB_BENCH`), stripped by `decidb_cli.py` and surfaced as `DecidBCliError.status`. Gate it on the env var so user-facing output is byte-identical, and only set the var from the call path that strips it (`execute`), never from `execute_raw`/`execute_script`, whose callers classify raw stderr themselves and would read the marker as an error.
- **A "flaky test" whose harness turns an advisory into an exception is usually a misclassification, not nondeterminism.** The SUBOPTIMAL case above reached the test as a `DecidBCliError` only because `DecidBCli.execute` raises on *any* stderr line not prefixed `Warning:` — but DeciDB returns the rows and prints the caveat as an advisory, i.e. the solve succeeded. Before adding retries or widening a regex, check whether the harness is classifying a successful run as a failure; the stale docstring ("DeciDB soundly declines to return it") was describing behavior that had already changed.
- **Any new `Expression`-holding field on `LogicalDecide` must be registered with `ColumnBindingResolver`.** The resolver's `LOGICAL_DECIDE` case (`src/execution/column_binding_resolver.cpp`) enumerates DECIDE's expressions *by hand* — `decide_variables`, `decide_constraints`, `decide_objective` — rather than through `VisitOperatorExpressions`, because DECIDE variables must be shielded from resolution via `ignored_bindings`. So a rewrite that **moves** sub-expressions out of those trees into a side vector silently opts them out of resolution. That is what the composed MIN/MAX rewrite did: `RewriteComposedMinMaxObjectiveTop` lifts each aggregate's inner expression into `composed_minmax_objective_terms` and leaves a constant placeholder behind, so the lifted expressions kept raw `BoundColumnRefExpression`s. `TransformToChunkExpression` then read `binding.column_index` — a *logical* index — as a position in the materialized chunk, so `D.c` silently evaluated as `R.rid`. **A single-table source hides this completely**, because the logical index and the chunk position coincide; it only appears once a join reorders them. Every pre-existing composed MIN/MAX test used `VALUES`/single-table sources, so the whole suite passed against a wrong answer. Two rules follow: (1) when adding a field on `LogicalDecide` that holds expressions the physical layer will evaluate, add it to the resolver's case in the same change; (2) any test for a feature that evaluates coefficient expressions must use a **multi-table join**, or it cannot distinguish logical bindings from chunk positions.
- **`xfail(strict=True)` is the right pin for a confirmed defect, and XPASS is the signal to delete it.** Both composed MIN/MAX defects were pinned as strict xfails with the reproduction in the docstring. When the fix landed, pytest reported `XPASS(strict)` as a *failure* — an unmissable prompt to remove the marker and rewrite the docstring as a regression note. A non-strict xfail would have gone green silently and left a misleading "known defect" comment in the tree.
- **In `decide_symbolic.cpp`, a CAS-visible `MARKER * inner` encoding is only safe for constructs that actually distribute over addition.** `SUM`/`AVG` round-trip through the CAS as `Symbolic("__SUM__") * inner` and it's fine, because `SUM(a+b) == SUM(a)+SUM(b)` — the marker reassembles correctly no matter how `.expand()` redistributes it. `MIN`/`MAX` used the same encoding and were wrong: `MIN(a+b) != MIN(a)+MIN(b)`, so `.expand()` distributing `__MIN__` across a multi-term inner scrambled it into a different (and wrong) expression tree before reassembly — see `07_issues/bugs/done.md` → "`SUM(MIN(expr)) PER col` rejected a multi-term inner MIN/MAX argument at bind time". The fix, and the correct default for any non-distributive construct (a future CASE-like or windowed thing, say) passing through this layer: wrap the *whole* node as one opaque placeholder symbol in a dedicated map (mirrors `abs_map`/`data_map`/`subquery_map`/`column_map`) and restore it verbatim in `FromSymbolic`, never let the CAS see inside it. Before adding a new `MARKER * inner` site here, check whether the construct distributes over `+`; if not, use the opaque-placeholder idiom instead.
- **A DECIDE binder's catch-all `expr.ToString()` fallback (e.g. `decide_constraints_binder.cpp`'s "SUCH THAT clause does not support '%s'(ExpressionClass::%s)") will render whatever internal tag or C++ enum happens to be attached to the rejected node — it has no idea which shape it's being asked to describe.** Fixing the wording in place is unsafe: the same throw site is shared across every unrecognized shape, so a rewrite tuned for one input reads wrong (or misleadingly) for the others. Before touching the fallback text, trace the *actual* parsed shape reaching it (add a temporary `fprintf` at entry logging the node's `ToString()`/`is_top_expression`/`depth` — do not trust a static read of the binder's dispatch chain, since `is_top_expression`/`depth` state threads through many mutually-recursive `BindX` calls and is easy to get backwards by inspection alone). Once the exact reachable shape is confirmed, add an earlier, narrower check that recognizes just that shape and throws a specific SQL-facing message, leaving the shared catch-all's wording untouched for every other input that still falls into it.
- **A per-variable domain signal already threaded end-to-end is the DomainSpec — don't invent a parallel one.** Fixing "BOOL domains round-trip through the constraint tree instead of being variable bounds" (`context/descriptions/07_issues/code_quality/todo.md`) turned out to need no new data structure: `is_boolean_var` (`BoundSelectNode` → `LogicalDecide`, serialized → `PhysicalDecide`) was already the exact carrier the issue asked for, and `ilp_model_builder.cpp`'s `SolverModel::Build` already applied `LogicalType::BOOLEAN` directly to `col_lower`/`col_upper`/`is_binary` for optimizer-created indicators (MIN/MAX, NE) — the DomainSpec-via-type pattern already existed for *some* producers of `is_boolean_var`. The only gap was that user-declared `x(BOOL)` and INTEGER-typed auxiliaries (IN-domain, L0 — which must stay INTEGER so they can appear in arithmetic like `M * z`) fed `is_boolean_var=true` but the binder still synthesized `x >= 0 AND x <= 1` constraint rows for *them specifically*, and `TraverseBoundsConstraints` pattern-matched those rows back into bounds. The fix was one override at the point `SolverInput::variable_types` is built (`physical_decide.cpp` `Finalize`): report `LogicalType::BOOLEAN` whenever `is_boolean_var[var]` is true, regardless of the DuckDB-facing type, unifying every producer onto the one existing type-driven bounds path and deleting both constraint-injection loops in `bind_select_node.cpp`. Before reaching for a new struct, check whether an existing per-variable flag threaded through the whole pipeline already carries the exact partition needed — and whether the "elegant" application mechanism already exists for a subset of producers, waiting to be generalized rather than reinvented.
- **A grammar production keyed on `func_application` doesn't automatically cover other `c_expr` alternatives that "look like" a function call.** Aggregate-local WHEN (`func_application WHEN_DECIDE decide_when_condition`) only fires for the specific `func_application` nonterminal; the relation-qualified reducer (`func_name '(' func_arg_list ':' func_arg_list ')'`) is a sibling `c_expr` alternative, not a `func_application`, so `sum(D: expr) WHEN cond` fell through to the loose, whole-constraint `a_expr WHEN_DECIDE b_expr` production instead, which swallowed a trailing comparison (`<= bound`) into the WHEN condition — silently producing a bare, comparison-less LHS. The binder-side plumbing (`ContainsDecideAggregate`, `GetExpressionType`) already unwrapped the composition correctly, proven by the objective side (no trailing comparison to lose there) — the fix was purely a second grammar alternative mirroring the first, not a binder change. When adding a WHEN/postfix production for one `c_expr` alternative, check whether every other alternative that could sit in the same position needs its own copy; don't assume `func_application` is the only shape reaching that point. See `03_expressivity/decide/done.md` → "Relation-qualified reducers".
- **A worktree-isolated agent must never `cd` into the shared checkout, even for a "harmless" read-only command like running tests.** Bash's cwd persists only *within* one call (`cmd1 && cmd2`), not *across* calls in this harness — each new Bash invocation starts back at the agent's pinned worktree directory. But a command that explicitly does `cd /path/to/main/checkout && test/decide/run_tests.sh ...` runs entirely against the main checkout's files for that call: its own binary, its own copy of every test file. Four consecutive test runs (999 tests + a `--collect-only`) all silently validated the *pre-fix* code and never saw two newly-added test methods, because `cd` had pointed pytest at `/Users/hatim/Code/decidb` instead of the worktree — the harness's own git-tool guard (which blocks `git -C <other-checkout>`) doesn't cover plain `cd` + non-git commands, so nothing errors; the results just quietly describe the wrong tree. Never prefix a command with `cd <other-checkout>`; if some absolute-path anchor is needed, use the worktree's own path (or none, since cwd already defaults there).
