One operator, three stages

Stages 06 to 08 run inside one physical operator, PhysicalDecide, after DuckDB has produced the query's rows. They turn rows into numbers, numbers into a model, the model into a solution, and the solution back into columns.

When a query reaches this operator, the algebra is done. The canonicalizer and the optimizer (stages 04 and 05) have written every clause as a sum of terms, each a decision times a coefficient expression, and have chosen how each construct is encoded (the optimizer). What is left is arithmetic on data. The operator does it in five steps:

  1. Materialize. Sink buffers every input row. The operator is a pipeline breaker: a blocking operator that reads all of its input before it emits a row. It has to be one, because the best value of one decision depends on every row.
  2. Evaluate. Finalize maps each row to its class for every keyed decision, makes the scope checks that need those classes, and evaluates every coefficient, bound, filter and group key on the buffered rows. The result is a SolverInput: numbers, with no expression left in it.
  3. Formulate (stage 06). SolverModel::Build and the linearization passes turn the SolverInput into a SolverModel: columns with types and bounds, a linear objective, an optional Q matrix, and rows.
  4. Solve (stage 07). SolveModel hands the model to the backend chosen at plan time, Gurobi or HiGHS, and normalizes its answer into a SolverResult.
  5. Read back (stage 08). GetData scans the buffered rows again and appends each decision's value to its row.

The stage numbers name layers, not moments. Execution (08) calls formulation (06) and the solve (07) from inside Finalize. This page takes the stages in number order and follows one query through all three.

The running example

The query uses the Guide's five items and declares one decision of each scope. x is per row: pack this item or not. open is keyed by category: a category costs 30 to open, and an item can be packed only if its category is open. cap is query-wide: one capacity for the whole bag, bought at 1 per unit, at most 40.

SELECT item, category, x, open, cap FROM Items DECIDE x(BOOL), per category: open(BOOL), per (): cap(INT) SUCH THAT x <= open AND SUM(x * weight) <= cap AND cap <= 40 MAXIMIZE SUM(x * value) - SUM(per category: 30 * open) - cap

EXPLAIN prints each clause as written and then, after ≡, in the canonical form the model's rows are built from (EXPLAIN in the Guide). The model this query builds is in the example as a model, and its result in reading the solution back.

Model formulation

Stage 06 turns the evaluated SolverInput into a SolverModel that any backend can load. It reads numbers only: it never sees a SQL expression and never names a solver.

A SolverModel is a mixed-integer program. It has columns, the solver's variables, each with a type and bounds. It has an objective to minimize: a coefficient per column, plus an optional Q matrix for squares and products. And it has rows: each row is a sparse list of (column, coefficient) pairs, a sense (<=, >= or =) and a right-hand side.

Columns: one per decision instance

A decision has instances: one per row for a per-row decision, one per class of its key for a keyed decision, and one in all for a query-wide decision (scopes in the Guide). Each instance is one column. VarIndexer lays the columns out in four blocks:

BlockHoldsColumn of an instance
Per-roweach per-row decision on each rowrow × (number of per-row decisions) + the decision's offset
Keyedeach keyed decision's classesthe decision's first column + the row's class id
Query-wideone column per query-wide decisionthat column, whatever the row
Auxiliarycolumns the encodings add: switch binaries, MIN, MAX and ABS helpers, products appended after the three blocks above

One function, VarIndexer::Get(decision, row), resolves a data row to a column. The objective, every row of the model and the readback all go through it. That is why rows share a keyed or query-wide column with no special case anywhere: they resolve to the same index, and what they add to it accumulates.

A class id is the rank of the class's key value, sorted the way ORDER BY sorts the key. It does not depend on the order rows arrive in, so the same data in a different order builds the same columns.

Types and bounds

DeclaredColumnDefault bounds
BOOLbinary[0, 1]
INTinteger[0, ∞)
REALcontinuous[0, ∞)

The model writes "no bound" as the number 1e30, and each backend's adapter turns it into that solver's own infinity. Zero is a default floor, not a rule: execution resolves each decision's lower bound, honoring a written negative one, and the builder takes it as given. The upper bound is the smaller of the type's ceiling and any bound the query implies.

Three passes narrow a column's box. The first two take the place of rows; the third tightens the box beside the rows that imply it:

  • Singleton-row folding (stage 05): a literal bound on one decision, such as cap <= 40, becomes the column's upper bound instead of a row (the optimizer).
  • The per-row fold (TryFoldPerRowBound): a bound on one decision that reads data, such as x <= S.demand, narrows that row's column. It only narrows. Under DIAGNOSE these stay rows, because the elastic model DIAGNOSE solves loosens a clause by giving its rows slack.
  • Implied bounds (DecidePropagateImpliedBounds): a row whose terms are all non-negative, such as SUM(x) <= 5 over non-negative x, bounds each term on its own, so each x is at most 5. Only bounds the rows prove are applied, so the optimum does not move.

Bounds matter more than they look. Every Big-M constant (below) is computed from them, and a solver works faster on a box than on the same limit written as rows. The stage's notes record a 9,600-row box-bounded QP that HiGHS did not finish in 60 s as rows and solved in 0.4 s as bounds.

The objective and the rows

The model always minimizes. A MAXIMIZE query arrives as the minimization of its negation: the canonicalizer has flipped every term's sign (the canonicalizer). For each objective term, the builder adds the term's coefficient on every row into the column that row resolves to. A per-row column receives one row's coefficient. A keyed column receives the sum over its class's rows.

A term with no decision in it, such as a data column or a constant, moves no optimum. It goes into the objective's constant, which no backend receives. The solver session adds it back to every objective value it reads, so a reported objective is the one the query wrote.

A decision beside the reducers (the aggregates over decisions, such as SUM) counts once. In SUM(x * weight) <= cap, cap stands on every row of the clause, but execution keeps its coefficient on one row and zeroes the rest (CountOnce). The row holds −1 times cap, not −5 times. One function owns this rule, and a debug build checks that no such term reaches the builder twice.

Each constraint becomes rows according to its shape:

Clause shapeRows it becomesExample
no reducer (per row)one per kept row; one per class under per K: x <= open: 5 rows
a reducer, no by and no whenone SUM(x * weight) <= cap: 1 row
a reducer with by or whenone per group that has rows SUM(x) by (category) <= 2: 2 rows

Terms that hold no decision move to the right-hand side. <=, >= and = map directly (ApplyComparisonSense). A strict comparison steps its bound to the next integer: > K becomes >= floor(K) + 1, and < K becomes <= ceil(K) − 1. That step is exact only when the left side takes whole values, and the binder admits a strict comparison on no other left side (the binder).

After folding and cancellation, a row can be left with no coefficient. One that always holds, such as 0 <= 3, is dropped. One that never holds, as SUM(0 * x) <= -1 writes, is kept with its source clause. SolverModel::ProvesInfeasible then answers INFEASIBLE without calling a solver, and it does the same for a column whose lower bound passes its upper bound and for a row whose infinite bound no value reaches. HiGHS refuses to load some of these models, so answering them first also keeps the two solvers in agreement. The kept row lets DIAGNOSE name the clause (infeasible queries).

Every row carries its provenance: the clause it came from, the group or class it stands for, and whether the clause is strict. Diagnosis reads it to speak about clauses, not matrix rows.

The example as a model

Set DECIDB_DUMP_MODEL=1 and DeciDB prints the model of every solved DECIDE query to stderr; DECIDB_DUMP_MODEL=path appends it to a file. Each col line gives a column's bounds, whether it is integer and binary, and its objective coefficient. Each row line gives the sense (< for at most, > for at least), the right-hand side, and its column:coefficient pairs. This is the running example's model:

SELECT item, category, x, open, cap FROM Items DECIDE x(BOOL), per category: open(BOOL), per (): cap(INT) SUCH THAT x <= open AND SUM(x * weight) <= cap AND cap <= 40 MAXIMIZE SUM(x * value) - SUM(per category: 30 * open) - cap

Three rules from above show in it. The class gear sorts before tech, so it has the lower keyed column. SUM(per category: 30 * open) counts each category once, through the reducer's own per, so each open column holds 30, not 30 times its rows. And cap holds −1 in row 5 and 1 in the objective, because a decision beside the reducers counts once.

Quadratic objectives: the Q matrix

A square or a product of decisions arrives as a product group: a weight w times one linear form (a square) or two (a product). Execution evaluates the weight and the forms' coefficients on each row. The builder adds each group, row by row, into Q: a sparse matrix kept as a coordinate list (COO, one entry per nonzero with its row and column), lower triangle only.

An entry of Q is the plain coefficient of its monomial: 3·x² stores 3, and 4·x·y stores 4. This is not the ½·xᵀQx form some solvers take, and each adapter converts to its solver's form. For a square w·(a·x + c)² on one row:

  • Q[i,i] gains w·aᵢ², and Q[i,j] gains 2·w·aᵢ·aⱼ. The factor 2 is the square's own expansion: the pair xᵢxⱼ appears twice, and only one triangle is stored.
  • The linear part gains 2·w·c·aᵢ, and the objective's constant gains w·c².
  • A product w·(a·x + c)·(b·x + d) adds w·aᵢ·bⱼ to the monomial xᵢxⱼ, and handles its constants the same way.
SELECT name, score, x FROM Signals DECIDE x(REAL) SUCH THAT SUM(x) <= 5 MINIMIZE SUM(POWER(x - score, 2))

Each POWER(x - score, 2) expands to x² − 2·score·x + score². Q holds 1 on its diagonal, the linear part holds −2·score (−6, −8 and 0 for scores 3, 4 and 0), and the constant 25 is kept aside. The upper bound 5 on each column is an implied bound from SUM(x) <= 5.

Convexity is judged group by group (IsNonconvexProductGroup). The model minimizes, so a square with a positive weight is convex. A square with a negative weight, which is what a square under MAXIMIZE becomes, is not, and neither is a square whose weight is a data column, whose sign only the data knows. A product of two different forms is indefinite. A square of a form over two or more decisions is singular: its Q has rank one, and its minimizers form a flat valley rather than a point. These facts decide which solver can take the model (what each backend takes). A square or product in SUCH THAT becomes a quadratic row through the same loop.

Linearization: Big-M from the data

Some constructs are not linear: <>, a MIN or MAX that has to be pinned to one member, ABS under MAXIMIZE, and a product of a BOOL and a number. Stage 05 has chosen an encoding for each and tagged the clause. Stage 06 writes the rows, because the constants they need come from evaluated data.

The standard encoding is Big-M: a row that must hold only when a binary switch z is on gets a term M·z, with M large enough that the row is slack when the switch is off. DeciDB has no preset M. Each M is computed from the range the row's terms can reach, given the boxes of their columns. When a contributing decision has no finite bound, no M exists, and the query is refused with a message that names the decision to bound. A guessed constant would be worse: if the true range exceeds it, the solver cuts off feasible answers and reports a wrong optimum with no sign of error. The refusal is the same on both backends.

ABS is linearized first. Its pass narrows the ABS helper column to the range it can reach, and every later pass sizes its M from column boxes, so a MIN, MAX or <> over an ABS finds a finite column.

ConstructEncoding
e <> KTwo conditional rows on a switch z: z = 0 implies e ≤ K − 1, and z = 1 implies e ≥ K + 1. When the range of e lies on one side of K, one plain row and no switch: SUM(x) <> 0 over non-negative decisions becomes SUM(x) >= 1.
MIN, MAXA helper column z linked to its members. The envelope side holds z at or above each member (for MAX). The closing side pins z to one member: one Big-M row per member and binaries of which one must be on. An objective supplies one of the two sides by its own direction. One function, EmitExtremumLink, writes every such link.
ABS(e) under MAXIMIZEThe helper's two lower rows, plus two Big-M upper rows on a sign binary. Each sign's M comes from its own end of the range of e.
b * x, b a BOOLThe McCormick envelope: the standard rows that pin a product w = b·x, exact when b is binary. With x in [L, U] and L ≥ 0, three rows: w ≤ U·b, w ≥ x − U·(1 − b), w ≤ x. A negative L turns the last into w ≤ x − L·(1 − b) and adds w ≥ L·b. It needs a finite ceiling U.

Some backends state a construct whole. Gurobi has general constraints, which state z = |t| or z = max(t₁, …) directly, and indicator constraints: a row that must hold when a binary takes a given value. The model keeps such constructs in two lists, general_constraints and indicator_constraints, beside its rows. A <> is always written as its two conditional rows. The last pass, LowerDecideConstructs, reads what the chosen backend declared (recorded on the plan) and, when the backend cannot state a condition, rewrites each conditional row as a Big-M row. Here is one <> on both backends:

SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND SUM(x) <> 2 MAXIMIZE SUM(x * value) SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND SUM(x) <> 2 MAXIMIZE SUM(x * value)

Both dumps declare the same six columns, left out above: the five x columns and column 5, the switch. HiGHS declares no construct, so both halves become rows, and each half gets its own M: the distance from its bound to the far end of what its left side reaches, plus one unit. The sum of five binaries reaches up to 5, so the half SUM(x) <= 1 takes M = 5 − 1 + 1 = 5. It reaches down to 0, so the half SUM(x) >= 3 takes M = 3 − 0 + 1 = 4 and reads SUM(x) − 4·z ≥ 3 − 4. The unit costs nothing on a left side that takes whole values, and keeps the relaxed half clear of rounding in the solver.

MIN, MAX and ABS choose their form where they are written; for MIN and MAX that place is EmitExtremumLink. For MIN and MAX the native form is the fallback: Gurobi receives a general constraint only where no finite M exists, because the lowered rows are the smaller model wherever they work. ABS is stated natively whenever the backend declares it. The test switch DECIDB_NATIVE_CONSTRUCTS=off forces every construct down its lowering path and force states every declared one natively; the tests check that both reach the same optimum.

Before the model leaves this stage, every bound, coefficient, objective entry and Q entry must be a finite number and every column index in range. A sum that overflows a double raises an error naming the clause it came from, here, where the clause is still known, rather than at the solver, where only a matrix row is.

The solvers

Stage 07 hands the neutral SolverModel to one backend, runs it, and returns a normalized SolverResult. It never sees SQL. The Guide gives the user's view of the same choice (solvers in the Guide).

Choosing a backend

The backends live in one table, REGISTERED_BACKENDS (the Registry pattern). Each row, a SolverBackendInfo, holds a name, an availability probe, the model classes the backend accepts, the constructs it states natively, and a factory method that opens a session. Row order is preference order: Gurobi first, HiGHS last. Adding a backend is adding a row; no if or switch elsewhere names a backend.

The choice is made once per query, at plan time. ChooseDecideSolver runs in the DECIDE optimizer when no query-rewriting rule applies (query rewriting), and before any formulation rewrite, because how a construct is encoded depends on what the backend can state. It takes the first available backend in table order. It weighs no cost and reads no model. The answer rides the plan as a name, solver_backend_name, with the backend's construct support copied beside it. It is turned back into a backend only where a solve is about to run, so no later stage asks the question again.

Gurobi's availability is a fact about the machine. Its library is loaded at run time, so DeciDB builds and links without Gurobi installed. The probe loads the library and starts a licensed environment, once per process. HiGHS is compiled into DeciDB and always available, so the choice always succeeds.

DECIDB_FORCE_SOLVER=highs (or gurobi) pins the backend. The test suite uses it to run both solvers on one machine. A name no backend answers to is an error that lists the valid names, so a typo cannot pass for a test of a backend that never ran.

Gurobi sets a construct flag only when the library it loaded exports the function behind it, so the answer is read after the library opens, then kept for the process. No backend declares bilinear: a flag is set only once the code that honors it exists.

A model in a class HiGHS lacks is refused, not sent to HiGHS to see what happens. Three of the classes are shapes the HiGHS backend does not take, and no rewrite turns them into one it does: a quadratic row, a non-convex objective, a QP with integer columns. The fourth, singular_quadratic, is about answer quality. HiGHS loads a rank-one Q without complaint, then stops partway along its flat valley of optima, or fails, on about half of such models in the measurements behind the rule, and a stopped point would be returned as optimal. Refusing is the only way to keep that answer out.

The refusal comes at plan time, when the physical plan is built and before any row is read (RequireDecideSolverSupport), so a query that cannot run costs no scan and no model build. The message names what the query does, the solver that can run it, and an edit that avoids the need. The solver list comes from the registry's model-class table, which needs no library, so Gurobi is named even on a machine without it. The message never blames the query: the same SQL runs where Gurobi is installed. With DECIDB_FORCE_SOLVER=highs on a machine that has Gurobi, a maximized sum of squares reads:

SELECT name, x FROM Signals DECIDE x(REAL) SUCH THAT SUM(x) <= 5 MAXIMIZE SUM(POWER(x, 2))

After the build, SolveModel checks the built model's class against the backend again (AssertBackendAcceptsBuiltModel). The plan-time prediction errs toward demanding more, so a mismatch there is an internal error, never the user's.

Translating the model

Each backend has an adapter (the Adapter pattern): a SolverSession that loads the neutral model into the solver's own API and reads the answer back. Callers use Solve and Continue, which wrap the backend's SolveChunk and ContinueChunk (the Non-Virtual Interface pattern) and add the objective's constant to what comes back.

Gurobi is reached through its C API, loaded at run time.

  • One GRBnewmodel call passes every column's type, bounds and objective coefficient. Each row is one GRBaddconstr, Q goes to GRBaddqpterms untouched (it takes the same plain-coefficient convention), quadratic rows go to GRBaddqconstr, and native constructs to Gurobi's general and indicator constraint functions.
  • NonConvex=2 is set when the objective is non-convex.
  • An open bound becomes Gurobi's own infinity. Left at 1e30, it would be a finite bound to Gurobi, and an unbounded integer would come back at its integer limit as if it were the answer.
  • The integrality, feasibility and optimality tolerances are set to 1e-6, and MIPGap to the session's decide_mip_gap.

HiGHS 1.15.1 is vendored with a series of DeciDB patches and reached through its C++ API. Its adapter is the class DeterministicNaive, a full MIP solver despite the name.

  • The rows pack straight into HiGHS's compressed row-wise matrix. Each sense becomes a range row: <= as [−∞, rhs], >= as [rhs, ∞], = as [rhs, rhs].
  • HiGHS has no binary type: a binary is an integer column in [0, 1]. An integer column's bounds are rounded inward to whole numbers, because HiGHS can answer below a fractional bound. A column whose bounds hold no whole number is INFEASIBLE without loading.
  • HiGHS's passHessian takes the Q of ½·xᵀQx and applies the ½ to the triangle it receives, so the adapter doubles the diagonal entries and leaves the others. Doubling every entry would inflate the cross terms against the squares and could make a convex Q indefinite; the solver would answer a different problem without an error.
  • HiGHS deletes a matrix entry at or below 1e-9, refuses one at or above 1e15, and reads a bound at or past 1e20 as infinite. Both ends are reachable from ordinary SQL: a rate of 1e-9 is data, and a Big-M is a decision's own span. So the adapter multiplies each out-of-range row through by a power of two, bounds included. Scaling a row by a positive constant leaves its solutions unchanged, and a power of two is exact in binary floating point. Columns with a bound past 1e20, and the objective, are scaled the same way and unscaled on readback. A row whose own coefficients span more than the window's 24 orders of magnitude cannot fit, and is refused naming its clause.

Normalizing the outcome

Every solve returns a SolverResult, and callers branch on its status: an outcome is a value, not an exception. Each adapter maps its solver's statuses onto one enum:

SolverStatusGurobiHiGHS

UNBOUNDEDGRB_UNBOUNDEDkUnbounded

TIME_LIMITGRB_TIME_LIMIT; GRB_INTERRUPTED, marked as the user'skTimeLimit; kInterrupt, marked as the user's

ITERATION_LIMITGRB_ITERATION_LIMIT kIterationLimit

A solution comes with OPTIMAL, and with TIME_LIMIT or SUBOPTIMAL when the solver holds a feasible point it has not proven best. The bound and the gap are NaN when no proven bound exists, as after an LP times out, and a report leaves them out then.

SolveModel is the facade every solve goes through (the Facade pattern). In order:

  1. Build. SolverModel::Build runs on the SolverInput.
  2. Check. The built model's class and native constructs must match what the backend declared.
  3. Dump. DECIDB_DUMP_MODEL prints the model here, before any follow-up solve can add one of its own.
  4. Warn. When a coefficient is 1e6 or more, a bound or right-hand side is about 4.5e9 or more, or a nonzero objective coefficient is 1e-6 or less, stderr gets one line, once per query: DECIDE: a very large or very small number may make this answer inaccurate. Scale its data toward 1. The thresholds follow from DeciDB's solver tolerances of 1e-6. The model and the answer do not change.
  5. Answer without a solver. When ProvesInfeasible holds, the result is INFEASIBLE, and no backend loads the model.
  6. Solve. A session loads the model and runs the first chunk.
  7. Settle INF_OR_UNBD. When the solver cannot tell infeasible from unbounded, the same model with a zero objective is solved on the diagnostic budget. That probe cannot be unbounded: OPTIMAL means the original is unbounded, INFEASIBLE means it is infeasible.
  8. Reject the integer ceiling. Neither solver can represent an unbounded integer: both cap an integer column near 2e9 and report the capped answer as optimal. An optimum at that cap on a column the query left open is reported as UNBOUNDED. A bound the user wrote, however large, is answered against.

What a failing status leads to is the operator's decision. Without the DIAGNOSE prefix, the query raises one message that names the state and suggests the prefix. With it, the diagnosis engines run (DIAGNOSE).

Time limits and the gap

One function reads the time limit, ResolveDecideTimeLimit: 300 s, or the number of seconds in DECIDB_TIME_LIMIT. Both backends apply it per chunk, Gurobi as TimeLimit and HiGHS as time_limit, which is what lets a stopped solve resume (slow solves). The follow-up solves of a diagnosis get the smaller of 60 s and the primary limit.

The session setting decide_mip_gap (default 0) is the relative gap at which a mixed-integer solve may stop. The default asks for the proven optimum, not the solvers' own default gap of 1e-4 (a long solve in the Guide).

HiGHS reads the clock only at checkpoints, and several loops in its presolve and MIP setup can run for minutes without reaching one. The vendored copy adds a time-limit and interrupt check to each such loop, leaving through an exit the loop already has: the objective clique partition, symmetry detection, clique extraction, conflict analysis, and the dominated-columns, parallel rows and columns, dual fixing and singleton-column passes of presolve. Each patch is marked in the source and listed in third_party/highs/README.md. In one measured case on macOS arm64, a MIP of 840,000 columns and 1,560,001 rows stayed in presolve for 638 s under a 300 s limit; with the patch it stops at 301 s.

Execution

Stage 08 is the operator itself. It buffers the input, checks it, evaluates every coefficient on it, calls stages 06 and 07, and writes the answer into the result. It does no algebra: every clause arrives as terms.

Materialization

Sink appends each input chunk to a thread-local ColumnDataCollection, and Combine merges the threads' collections under a lock, so input arrives in parallel. Finalize then runs once, over every row. The optimization therefore sees one snapshot of the data: rows another transaction changes during the solve cannot reach it. An empty input gives an empty result and no solve.

Finalize is a short sequence of private methods:

MethodWhat it does
BuildKeyedMappingsmaps every row to its class, for each keyed decision
RunScopeChecksthe scope check that needs those maps
EvaluateConstraints, EvaluateObjective, EvaluateComposedClauses, EvaluateReducerValueLinkscoefficients, bounds, filters and groups, for every clause
BuildSolverInputassembles the SolverInput and settles every column's box
FormulateModelthe linearization of stage 06, against that box
FinalizeSolveResultthe solve of stage 07, then what its status leads to

Scope checks at run time

Some rules of the language are about data, not syntax. per K: in front of a clause says that what the clause reads once per class is the same on every row of the class, and a bound has to be a number. These are scope checks. They run on the data before any coefficient is read, and the first failure stops the query.

Most of them never reach the operator. The optimizer installs them as a plan under the DECIDE node: each check is an aggregate over its own read of the source that comes to one row, its message or NULL, and a projection over all of them raises the first message. The source's rows reach the operator only once that one-row verdict holds: verify, then stream, the way DuckDB plans an uncorrelated scalar subquery. The same code installs the checks for query rewriting (rewriting plans), so both paths refuse the same data in the same words. The side tables that compute a bound-side reducer, such as max(cap) by (g), sit in the same plan. EXPLAIN shows all of it as operators under DECIDE.

One check needs a map the operator builds, so RunScopeChecks makes it: a clause scoped per K: that reads a keyed decision must find one instance of that decision in each class of K. Here the clause is scoped by shift date, but keep is decided per nurse, and three nurses work on December 1:

SELECT n.name, s.shift_date, keep FROM nurses n JOIN shifts s ON n.id = s.nurse_id DECIDE per n: keep(BOOL) SUCH THAT per s.shift_date: keep <= 1 MAXIMIZE SUM(per n: keep * n.skill_score)

When several classes fail, the message names the least by key value, so it does not depend on row order.

Keyed decisions: rows to classes

BuildKeyedMappings gives each row its class for every keyed decision. It evaluates the key's expressions on the buffered rows and finds each row's group in DuckDB's aggregate hash table, used with no aggregates (GroupedAggregateHashTable::FindOrCreateGroups), as GROUP BY uses it. Each group remembers its first row, and its key values are read back from that row only when a message names the group (late materialization). The groups are then numbered by value with DuckDB's order-preserving sort key, as ORDER BY compares rows. The result is a KeyedMapping: a class count and a row_to_class vector, the map VarIndexer reads.

A key is computed once per query and cached (PerGroupCache), so every clause, check and objective term that groups by it shares one numbering. A key over a collated column groups under its collation, as GROUP BY does.

A row with NULL in a key column the query wrote is in no class: it has no decision. It maps to one spare class, absent_class (the Null Object pattern), so every row still resolves to a column. The model pins that column to 0, a reducer skips the row, and the result shows NULL there. The keyed decisions example shows one decision per nurse shared by every shift row.

Coefficient evaluation

Each term carries a coefficient expression over the input's columns. Execution constant-folds it once with DuckDB's own ConstantFoldingRule, runs it chunk by chunk with an ExpressionExecutor, and casts the result of the whole expression to DOUBLE in one step. One cast at the end keeps SQL's semantics: a DECIMAL or integer expression computes in its own type, as SELECT would compute it.

Each clause is read in this order:

  1. Kept rows. The clause's when is read first, on every row (KeptRows). Nothing else is computed on a row it drops.
  2. Groups. A by key gives each kept row its group, and per K: over a clause with no reducer keeps one row per class. The result is one vector, row_group_ids, that sends each row to the model row it feeds, or to none.
  3. Term filters. A reducer's own when becomes a mask on its own terms. A reducer's own per, and the colon form SUM(D: e), keep the first row of each class and zero the rest (BuildQualifierKeepMask). A scope check has proved every row of the class carries the same value, so any row gives the same answer.
  4. AVG. The optimizer has rewritten AVG as SUM. Each such term is divided here by the number of rows its reducer reads in the row's group (ScaleAvgRows).
  5. Count once. A term outside every reducer keeps its coefficient on one row of each group (CountOnce).

Values are checked as they are read. A NULL coefficient or bound skips the instance it reaches: the row of a clause with no reducer, the group of one with a reducer (NULLs in the Guide). A NaN or infinite coefficient raises an error that names the expression as written and the when that would skip such rows. An infinite bound is allowed, because it has a meaning: x <= +inf holds for every value, and x >= +inf for none.

The output is the SolverInput. A coefficient column with one value on every row, such as a constant bound, is stored as one number (CoefficientColumn), not one per row.

The work then splits in two. BuildSolverInput assembles: it settles every column's box, implied bounds included, and runs once. FormulateModel formulates: it derives every M and envelope against a box it is handed, reads no data and evaluates no expression. The split is what lets DIAGNOSE run formulation a second time against a widened box and get constants that are valid for the elastic model it solves (infeasible queries).

Reading the solution back

GetData scans the buffered rows a second time, in the order they are stored. Its source runs on one thread, so the running row offset matches the row numbers the model is built on. The input columns are referenced into the output without a copy. Row r of decision d reads solution[VarIndexer::Get(d, r)], through the same function that built the model. A per-row decision gets a value of its own on each row. A keyed decision gets one value per class, repeated on every row of the class. A query-wide decision gets one value, repeated on every row.

SELECT item, category, x, open, cap FROM Items DECIDE x(BOOL), per category: open(BOOL), per (): cap(INT) SUCH THAT x <= open AND SUM(x * weight) <= cap AND cap <= 40 MAXIMIZE SUM(x * value) - SUM(per category: 30 * open) - cap

The solver returns doubles, and the output type decides the conversion. BOOL returns an INTEGER 0 or 1: it is a domain on an integer, so it stays usable in arithmetic. INT returns a BIGINT and REAL a DOUBLE. An integer is rounded and range-checked (DecideSolutionToInteger). A value past the column's range, or past 253, where a double stops counting whole numbers, raises an error that names the decision. An unchecked cast would saturate and print the type's limit as if it were the answer.

The columns the encodings added leave the operator too, as NULL constants. The projection planned above DECIDE drops them, so only declared decisions reach the result.

Slow solves

A solve stops early in two ways: the time limit expires, or the user presses Ctrl-C. Either way the backend returns TIME_LIMIT, marked when the stop is the user's. Finalize handles it before any diagnosis, because a timeout is ordinary execution: it proves neither that the model has a solution nor that it has none. A DIAGNOSE prefix changes nothing about it.

The operator first prints a report to stderr, in one of two shapes:

DECIDE hit the time limit with a usable solution (not proven best). best objective so far: (within % of the best possible) elapsed · peak memory DECIDE hit the time limit without finding a solution yet. elapsed · peak memory

After Ctrl-C the first line opens DECIDE stopped at your request instead. The closeness clause appears only when the solver proved a bound. Elapsed time comes from a timer around the solve. Peak memory is the whole process's peak resident size (getrusage): the number that tells whether continuing risks running out of memory. What happens next depends on who is there to answer:

SituationWhat happens
the clock ran out; stdin is a terminala prompt, Keep searching?: Enter runs one more full time limit on the same solver, s stops and returns the best rows with a caveat
the clock ran out; no terminal (a pipe, a test, the C API)the report, then an error: nobody can answer a prompt
Ctrl-C, with a solutionthe best rows and a caveat; the query succeeds
Ctrl-C, with nothing foundone error: DECIDE stopped at your request before finding a solution.

Continuing resumes the search; it never restarts it. SolveModel hands back the live SolverSession, and Continue runs another chunk on the same solver, whose search state survives in Gurobi and in HiGHS alike.

Ctrl-C reaches the solver in the middle of a search. On Gurobi, a watcher thread polls the query's interrupt flag every 25 ms during the solve and calls GRBterminate. On HiGHS, the poll is the interrupt callback HiGHS calls at its time-limit checks. One case looks like Ctrl-C and is not: when a sibling DECIDE in the same statement fails, DuckDB stops the other pipelines through the same interrupt. The operator first asks the executor whether it already holds an error, and if it does, prints nothing and raises that error.
