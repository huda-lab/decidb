The benchmarks

Each benchmark answers one question. All of them run the release command-line binary (build/release/decidb), live under benchmark/decide/, and write their results to benchmark/decide/results/.

BenchmarkQuestion it answersRun
TPC-H suiteHow long does each DECIDE query of a fixed set take on the solver path, and did a change make it slower?make decide-bench
Pipeline profilerInside the solver path, which stage takes the time and the memory, on Gurobi and on HiGHS?python3 benchmark/decide/profile_pipeline.py
Direct-solve benchmarkHow much faster is query rewriting than the solver on the same query, as the data grows?python3 benchmark/decide/direct_solve/run.py
DIAGNOSE examplesWhat does a user read, with and without DIAGNOSE, for each example query on each backend?python3 benchmark/decide/diagnose_examples/run.py

Scope-language scalingDoes DeciDB's own time, the optimizer and the model construction, grow linearly with the rows on reducers inside reducers, variants and frame selectors? python3 benchmark/decide/anr_scaling.py
Scale testsDoes DECIDE still match an independent solver on a few hundred to a few thousand rows?./test/decide/run_tests.sh -m large_scale

Two terms recur. The solver path is the pipeline that builds a model and hands it to Gurobi or HiGHS (Model, solvers and execution). Query rewriting, also called direct solve, answers some DECIDE queries with ordinary DuckDB operators and no solver (Query rewriting). The benchmarks keep the two apart, so a number always says which path it measures.

The TPC-H suite

run_benchmarks.py runs eleven DECIDE queries, Q1 to Q11, on two generated TPC-H databases. It sets decide_direct_solve = 'off', so every query takes the solver path. Together the queries cover the language with as few queries as possible: each bundles several features (decision types, problem classes, constraint and objective forms, when, per and by) and lists them in a -- TAGS: header.

  • Data. make decide-bench-setup builds medium.db (TPC-H scale 0.085) and large.db (scale 0.17) with DuckDB's dbgen, then pins lineitem to exactly 500,000 and 1,000,000 rows.
  • Scale tiers. Each query runs at the largest size that completes in reasonable time, set by measurement. Q1, Q4, Q8 and Q10 read the full lineitem; queries over orders or partsupp read their full table. Q3 (an L0 covering problem) and Q5 (quadratic constraints) read a row prefix, because their solve grows faster than their rows. Q9 reads a prefix too.
  • A run. Each iteration is a fresh decidb process on the database, opened read-only, under /usr/bin/time. Wall time therefore includes process start, opening the database and printing the result. The runner keeps every run and reports the median wall time, its standard deviation and the median peak memory.
  • Stage timers. make decide-bench sets DECIDB_PROFILE=1, and the engine prints its timing spans and counters (the profiler below reads the same lines). The runner turns them into optimizer_ms, model_construction_ms, solver_ms and the model's size: variables, clauses handed to the builder (total_constraint_specs) and matrix rows (total_constraint_rows). A clause with per becomes one row per class, so the two counts are different units and are never added.
  • Comparing commits. Results are stored per commit; --compare prints each query's change in median time and peak memory against an earlier commit's file.

A full run, three iterations at both sizes, takes about 17 minutes, mostly Q10, Q6 and Q4. --sizes medium --queries Q1,Q5 narrows it while working on one change.

The pipeline profiler

profile_pipeline.py runs Q1 to Q11 and four more shapes, P1 to P4, once per backend, three times each. Every run is a fresh process with one backend forced (DECIDB_FORCE_SOLVER), so no run can fall back to the other solver. The P queries isolate one effect of model size each over lineitem: a bounded LP (P1), a separable convex QP (P2), the same QP with one budget that couples every decision (P3), and a Boolean problem with one row per l_orderkey (P4).

The run sets DECIDB_PROFILE=1, and the engine prints one JSON line per span: a named, nested interval of work such as execution.tree_descent. Markers around the measured statement keep setup out. The query runs as CREATE TEMP TABLE result AS ..., which produces every output row without formatting millions of them for a terminal. The script sums the spans into one column per stage:

ColumnWhat it covers
parse_bind_ms, canonicalize_ms, plan_msthe front end and physical planning
rewrite_msthe DECIDE optimizer: the choice between a rewrite rule and a solver, and the formulation passes
input_mscollecting the input rows
extraction_msrouting the rows through the plan's tree, evaluating the clauses into coefficients, and formulating
model_build_msbuilding the solver-neutral model
backend_load_mshanding the model to Gurobi or HiGHS
solve_msthe solver's own call
readback_msreading the solution back into rows, and cleanup

non_solver_ms is the statement's wall time minus solve_ms: everything DeciDB does that is not the solver. Each run also records the model's size, the solver's iterations and nodes, and the process's peak memory, which is recorded and never acted on: there is no memory cap or early stop.

A correctness signal. Speed means nothing if the answer is wrong. After a sweep, the profiler compares the optimum of every successful run of a query, across both backends and all repeats. Two proven optima of the same model may differ only by the feasibility tolerance, so a spread above 1e-6 × max(1, |objective|) is flagged. A run stopped at its time limit reports a best-so-far answer, not an optimum, and is skipped.

The direct-solve benchmark

direct_solve/run.py times each rewrite rule against Gurobi on the same query, as the data grows. Gurobi is the solver direct solve competes with; HiGHS is not measured here. Most queries read one TPC-H table, partsupp, with one decision per row and no joins or filters, so the time measures the optimization and not other operators. The O1 query pairs supplier with itself, and S2 reads customer.

  • Modes. direct sets decide_direct_solve = 'require', so a query the rule does not take fails instead of falling back to the solver, and a speedup can never be the solver timed against itself. gurobi sets 'off' and forces Gurobi. Both run DuckDB on 32 threads, the most Gurobi uses by default.
  • Agreement. At every size, every finished run's objective must match direct solve's within 1e-6, relative. A mismatch stops the sweep, so no wrong answer is timed further.
  • Sizes. Scale factors double from 0.125 (100,000 partsupp rows) to 512 (409,600,000 rows), smallest first. A solver runs the next size only if its median at the previous size stayed within a budget (7,200 seconds by default). The databases up to scale 512 take about 270 GB of disk.
  • Against a hand-written plan. --compare runs each rule's plan beside a query an expert would write in SQL for the same answer, carrying the same checks, in one process. Its measure is summed operator CPU, the time of every operator added up, which compares the work of two plans independent of how well each one uses threads. A test, test_direct_comparators.py, checks that each hand plan gives its rule's answer.

Machine and scale

Each set of numbers names its machine. The pipeline profiler's numbers all come from one machine with 18 GiB of memory. The per-rule direct-solve numbers come from an 11-core Apple M3 Pro. The one direct-solve sweep in the repository ran on a server with an 80-core Intel Xeon Gold 6230 and 376 GiB of memory, where the rewritten plans used DuckDB's default of 160 threads and Gurobi its own default, up to 32. Load, the 1-minute load average, is reported beside each measurement, because other work often ran beside it.

What the measurements show

On a hard model the solver dominates: loading the model is under 2% of any solve that takes over 5 seconds. On an easy model the solver is quick, and loading the model costs as much as solving it. Query rewriting, where a rule applies, removes both.

Unless a number says otherwise, it comes from the pipeline profiler on large.db, on builds of 30 October 2026, one query at a time with a 3-second solver limit, as the median of three interleaved runs. Instrumentation is not a factor: the same statements with and without profiling differ by -1.3% to +2.6%, with no consistent sign, inside run-to-run noise, and peak memory is unchanged.

Which engine. Every number on this page was measured before DeciDB 1.0. Since then, 1.0 has replaced the step that evaluates clauses: one pass over the buffered rows routes them through the plan's tree, and each node then evaluates its clauses into coefficients. No number here has been measured again on 1.0, and the repository holds no newer pipeline measurements, so read the figures below as the older engine's.

Fixed costs

Each process and each statement pays a few costs before any data is read. Measured in fresh processes at a load of 2.2 to 2.6:

  • An empty process that opens large.db and runs SELECT 1: 18 ms.
  • Parsing, binding and canonicalizing a DECIDE statement: 0.1 to 0.3 ms.
  • The DECIDE optimizer: 5.1 to 5.3 ms on a process's first statement when Gurobi can be chosen, then 0.15 to 0.25 ms. The difference is a one-time check that the Gurobi library and its license are present, 4.8 to 5.1 ms per process.
  • A Gurobi environment, created per query: 0.6 to 0.8 ms. Reusing it would save under 1 ms a query, so nothing is cached.

The stages and the solver

Follow a query through the solver path. The medians below are Gurobi's, on large.db, from builds of 30 October 2026.

  1. Extraction turns clauses into coefficients. This is the step 1.0 rewrote, and the older engine's figures for it are not kept: they were read from spans the 1.0 engine no longer emits. Its cost on 1.0 is not yet measured.
  2. Formulation lowers constructs such as ABS and MIN/MAX into rows. By cost: ABS, then composed MIN/MAX, then products of decisions, then <>, then a MIN/MAX objective. Q10, the heaviest query, spends 308 ms here.
  3. The neutral model build takes 26 to 60 ns per nonzero coefficient. Q10's model, 5 million variables, 6 million rows and 14 million nonzeros, takes 657 ms.
  4. Backend load. Gurobi's model creation costs about 85 ns per column, and adding rows about 110 ns per row: 85 ms for P1's 1 million columns, 660 ms for Q10's 6 million rows.
  5. Solve. On every query whose solve takes over 5 seconds, loading is under 2% of the solve. Q10's solve takes 72 seconds.
  6. Readback and cleanup. Reading the backend's answer takes 0.3 to 3 ms; turning it into rows, 0.4 ms (Q11, 136,000 rows) to 17.8 ms (Q8, 1 million rows); destroying the model, 0.7 to 17 ms. Less than 10 ms of each statement falls outside every span.

So the balance depends on the model. On a hard model such as Q10, formulation takes 308 ms and the neutral build 657 ms, against a 72-second solve. On an easy one the order flips: P1's Gurobi load takes 91 ms against a 34 ms solve, and P4's 121 ms against 216 ms. There, Gurobi's model creation dominates the load, and it is already a single call. No solver tuning is implemented: these numbers measure the solvers as DeciDB configures them, with an optimality gap of 0.

Memory

  • On medium.db (500,000 lineitem rows), the largest peak across 90 runs is 6,525 MiB, on Q10 with HiGHS at 2.5 million variables; the median is 668 MiB. The machine's 18 GiB hold this scale with room to spare.
  • On Q3 and Q10 the peak falls inside Gurobi's solve, after DeciDB hands over the model. The stages before it hold less than the solve adds.
  • Q10's model build adds about 340 bytes per model row beyond 12 bytes per nonzero, so the per-row structure (each row's provenance record, among others) holds the memory, not the coefficients.

Designs measured against an alternative

Several choices in the pipeline are standard database techniques. Each one below is measured against the plain alternative on the same query and machine, on the older engine from 30 October 2026. These ran with a 3-second solver limit, often beside other work, at loads from 2.5 to 18, where single spans can swing up to 3 times, so read them as large effects, not small ones. Each figure gives the alternative first, then the design.

DesignAgainstMeasured: the alternative against the design
A MIN/MAX helper's member coefficients read a chunk at a time, like every other clauseone value at a time, with a cast per valueQ4, 489 ms against 21 ms
Row buffers that grow geometricallyreserving exactly the needed size at each flush, which copies the whole buffer each timea 1,000,000-row join with a per l_orderkey clause, 6.2 s against 0.98 s
Rows packed once into HiGHS's compressed row matrix and moved into the solverpacking through intermediate copies of the matrixQ10 load 1,164 ms against 699 ms; memory added during load 1,816 MiB against 1,026 MiB

Two more designs are kept in 1.0 but no longer carry a figure, because the older engine's step they were measured on is gone: group ids come from DuckDB's aggregate hash table, with a label formatted only for a group a message names; and a group keeps its first row and reads its key values from it when printed (late materialization), rather than storing one value per group per key column.

One idea measured to save nothing: folding constant subexpressions in a rewritten plan. DuckDB evaluates a constant subtree once per chunk of rows, not once per row, so on 1,000,000 lineitem rows (medians of 9) the A1 plan took 0.119 s without the fold and 0.118 s with it, and S1 0.044 s both ways. What does cost per row is the operation a constant decides, such as a multiplication by 1.0, and DuckDB's own expression rewriter removes those.

What query rewriting saves

A rewritten query builds no model, so it pays for none of the stages above: no extraction into a matrix, no formulation, no load, no solve. On P1, a bounded LP over 1,000,000 rows of large.db, the default configuration answers by rewriting in 113 to 119 ms, against 315 to 340 ms with Gurobi forced and 246 to 256 ms with HiGHS forced (one process running the statement three times, load 2.2 to 2.6, builds of 30 October 2026).

The direct-solve benchmark measures each rule against Gurobi. Each rule's own notes record a run on the 11-core Apple M3 Pro, 9 to 12 November 2026, on the older engine. At 800,000 partsupp rows, median of 3 fresh processes, with every objective agreeing:

At 800,000 rows the speedups run from 3.0x to 313x. Two more rules use other data: O1, pairing 1,600 suppliers with 1,600 (2,560,000 pairs), takes 0.057 s against Gurobi's 11.732 s, 206x; S2, over 150,000 customer rows, 0.052 s against 0.425 s, 8.2x.

The one sweep kept in the repository, in benchmark/decide/results/direct_solve/, goes much larger. It ran on 2 November 2026, also on the older engine, on the Xeon server: five queries (A1, S1 and R1, each also with one global bound) at sizes that double from 100,000 to 204,800,000 partsupp rows, with every objective agreeing. At 204,800,000 rows the rewritten plans ran about 7 to 277 times as fast as Gurobi, in 2.6 to 163 times less memory: A1 took 0.95 s against 264 s. Rewriting is not always ahead. At 100,000 rows, R1 ran at 0.9x, a little slower than Gurobi, the one cell of the sweep where it lost.

Against a plan written by hand in SQL for the same answer, the plans of A1, A2, N1, O1, R1, S1, S2 and S3 use from 0.96 to 2.87 times the hand plan's summed operator CPU, on the same machine at scale 1 (O1 at 3,200 suppliers a side, S2 at scales 1 and 2). The extra is the work a general rule owes: checks over every row or group before the first row is returned, which a hand plan for TPC-H's data can skip because that data cannot trip them. Planning a rewrite adds 0.09 to 1.19 ms.

Open questions

  • The 1.0 engine. Every number here predates DeciDB 1.0. The pipeline profiler, the TPC-H suite and the direct-solve benchmark all run on 1.0, but the repository holds no 1.0 measurement from any of them.
  • One machine per benchmark. The pipeline profiler's numbers come from one machine, and the per-rule direct-solve numbers from another. None has been repeated on a second host, so no number should be read as general.
  • Q9's prefix. Q9 solves near-linearly (120,000 rows in 2.8 s of solver time, measured 18 August 2026), so the 15,000-row prefix it runs at on large.db is smaller than it needs to be. Its tier is not yet re-chosen.
  • A helper decision's box. Bounding each MIN/MAX helper by its own group's reach showed no benefit over one shared box on the one pair of queries measured. A model where that bound decides the relaxation (many groups, an objective on the helper) is not measured.
