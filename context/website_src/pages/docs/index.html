How DeciDB attaches to DuckDB

DeciDB is built inside DuckDB's source tree. A query with a DECIDE clause gains one logical operator, one optimizer pass and one physical operator. A query without one takes DuckDB's own path: the new pass finds no DECIDE node and changes nothing.

DuckDB answers a query in four steps. It parses the text, binds names to tables and types, plans and optimizes a tree of operators, and executes that tree. DeciDB adds to each step and replaces none. The plan of the smallest decision query shows the result. It is the operator tree DuckDB runs, read from EXPLAIN: one DECIDE operator sits above the table scan.

SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 MAXIMIZE SUM(x * value);

Everything DeciDB does for this query happens inside that one node. It reads every row the scan produces, builds an optimization model over them, solves it, and returns the same rows with a new column x. The operators above it see x as an ordinary column.

The hook points

DeciDB attaches at six points, one for each thing DuckDB has to learn:

  1. Keywords. DECIDE, SUCH (as in SUCH THAT), MAXIMIZE, MINIMIZE and DIAGNOSE are reserved words. The clause's when, per and by are not, nor are the frame words at, over and within: the lexer turns them into DECIDE-only tokens inside the clause (below).
  2. Grammar. New productions in DuckDB's Bison grammar read the clause. The parser stores it in one new field of DuckDB's SelectNode, a ParsedDecide that holds the decisions, the constraints, the sense, the objective, and the clause's own text for error messages.
  3. Binder. DuckDB's binder for a SELECT has one DECIDE branch: a call to DecideDeclarationsBinder::BindDeclarations, which binds the whole clause with DeciDB's own expression binders.
  4. A logical operator. LogicalDecide, a new operator type (LOGICAL_DECIDE), sits above the scan and any filter. It carries the decisions, the constraints and the objective through planning. DuckDB's serializer, generated from logical_operator.json, writes it as it writes every operator.
  5. An optimizer pass. DecideOptimizer runs as one entry in DuckDB's list of optimizer passes (OptimizerType::DECIDE_OPTIMIZER), after DuckDB's filter pushdown. It decides how the query is answered and how each construct is written for the solver.
  6. A physical operator. PhysicalDecide executes the node. It is a pipeline breaker, an operator that reads all of its input before it emits a row, because the best value of any one decision depends on every row.

DuckDB's passes that walk every operator have one case for the new type. Column pruning (RemoveUnusedColumns) visits every expression the node owns, so the columns the clause reads stay in the plan. Binding resolution (ColumnBindingResolver) leaves the decision columns alone, since they name the node's own output and no input column.

Gated keywords

A scope is written with ordinary English words: when, per and by. SQL already uses all three. CASE ... WHEN is an expression, GROUP BY is a clause, and per is a legal column name. Making them reserved words would break existing queries.

DeciDB settles this in the lexer, the step that cuts SQL text into tokens before the grammar sees it. The lexer keeps a flag. The DECIDE or SUCH token sets it, and the grammar clears it when the clause ends. Only while the flag is set does the lexer turn these words into DECIDE-only tokens:

  • WHEN becomes WHEN_DECIDE. A CASE inside the clause raises a depth counter, so its own WHEN stays SQL's.
  • PER becomes PER_DECIDE_PAREN before (, PER_DECIDE_ROW before ROW, and PER_DECIDE otherwise. One token of lookahead tells per (), per row and per key apart, which the grammar alone cannot.
  • BY becomes BY_DECIDE directly after ), as in SUM(x) by (g). GROUP BY, ORDER BY and PARTITION BY always follow a keyword, so they stay SQL's.
  • AT becomes AT_DECIDE before (, OVER becomes OVER_DECIDE directly after ), and WITHIN inside that OVER (...) becomes WITHIN_DECIDE. They spell a frame selector, such as at(previous: x) over (t.period), which reads a value at another row. These three apply only after SUCH THAT and outside any subquery written there, so a SQL window keeps its OVER and WITHIN GROUP.

Outside a DECIDE clause the flag is clear and nothing changes. The lexer saves the flag before a nested clause and restores it after, so a DECIDE query written as a subquery inside another one hands the outer clause back its own state.

Why standard SQL is unaffected

Four choices keep a query without DECIDE on DuckDB's behavior:

  • The scope words are tokens only inside the clause, as above.
  • Every grammar conflict is local to DECIDE. Bison expects four shift-reduce conflicts, all from the optional declaration slot of the clause, and both readings build the same node. The WHEN conflict is settled by precedence on a token the lexer emits only inside DECIDE.
  • A decision's type is read as a name, not a keyword. DuckDB quotes every keyword when it prints a name, so a keyword BOOL would quote every column named bool.
  • A stored query writes the DECIDE fields only when they are set, so a database file or view that DuckDB wrote loads unchanged.

The check is DuckDB's own SQL test suite (build/release/test/unittest "test/sql/*"), run on the DeciDB build.

Edits to DuckDB itself

Query rewriting replaces a DECIDE node with ordinary DuckDB operators, so its plans run only as fast as DuckDB's own rules make them. Ten edits to DuckDB make those plans run as DuckDB would run the same answer written by hand in SQL. The first eight, to the expression rewriter, statistics propagation, the perfect hash join and unused-column removal, name nothing of DECIDE: each helps any query with the shape it handles, and a standard query returns the same rows. The last two hook query rewriting's own passes into unused-column removal, and a standard query reaches neither. Two more edits fix DuckDB defects: the order of catalog names, and a hang while a thread waits for a batch of tasks. A few small ones let an error point at the place in the query it is about. Each edit, its reason and its test are on Query rewriting.

The eight stages

The DECIDE path is eight stages, from SQL text to rows with decisions. Each stage owns one kind of behavior, and a change belongs to the stage that owns it, not the one that calls it first.

StageOwnsExplained in
01 ParserThe grammar, the gated keywords, and the parsed form of the clause (ParsedDecide)Parser, binder and plan
02 BinderDecisions and their keys, where when, per and by may stand, types, reducers, and the refusals only binding can make Parser, binder and plan
03 Logical planLogicalDecide, subqueries in a clause, the only ways to add or change a clause after planning, serialization Parser, binder and plan
04 CanonicalizerThe one shape of every clause: decisions on the left, the bound on the right, one spelling per product, and the check of each clause's algebra and degree Canonicalizer and optimizer
05 OptimizerHow each construct reaches the solver (Big-M, McCormick, MIN and MAX, AVG, <>), the choice of solver, the entry to query rewriting, and the lowering of each clause into terms in the clause tree Canonicalizer and optimizer
06 ModelFrom evaluated clauses to a model that names no solver: variable layout, coefficients, bounds, the quadratic matrix Model, solvers and execution
07 SolverGurobi and HiGHS behind one interface, their statuses mapped to one set, time limitsModel, solvers and execution
08 ExecutionBuffering the rows, evaluating the clause tree over them, mapping keyed decisions, reading the answer back as columnsModel, solvers and execution

Two exits leave this path: query rewriting inside stage 05, and DIAGNOSE after stage 07. They are the next section. Life of a query follows one query through all eight stages with real output.

When each stage runs

The numbers give the order of ownership, not of time. Stages 01 to 05 run while DuckDB prepares the statement, before a row is read. When DuckDB builds the physical plan, stage 05's last step lowers each clause into the clause tree: a tree whose nodes are the clauses' scopes, reducers, frames and helper functions, each recording what it reads per row. Stage 08 runs when the plan executes, in three phases:

  1. Sink. PhysicalDecide buffers every input row.
  2. Finalize. It reads the buffer once, from the top of the clause tree, into each node. Then it computes each node from its children, builds the model (stage 06) and solves it (stage 07).
  3. Source. It scans the buffer again and appends each decision's value to its row.

So stages 06 and 07 run inside stage 08. They are separate stages because they keep separate contracts: stage 06 produces a model that names no solver, and stage 07 is the only code that speaks to one. Because the solve reads the buffer, it optimizes the snapshot the query saw; a concurrent write cannot change a running solve.

Rules every stage keeps

  • Shape is decided once. Which side of a comparison a term sits on, and how a product is spelled, is decided by stage 04 and by no other stage. The optimizer reads canonical clauses and returns canonical clauses: every clause it adds or changes re-enters through LogicalDecide::AddClause, CanonicalizeClause or SetObjective, which canonicalize it again. This is a canonical form in the compiler sense, as an LLVM canonicalization pass writes one form per meaning.
  • A promise is checked where it is read. When a stage relies on what an earlier one guarantees (the shape check refuses a degree above 2, the canonicalizer writes each marker once), the reader checks it with an InternalException that names the stage that made the promise. This is a precondition in design-by-contract terms: a broken promise in a release build is an error that names its cause, not a wrong answer.
  • A message quotes the query by location. The parser keeps the text of the clause and one span per expression. A message cuts the user's own text out of the query instead of printing the internal tree, as Clang underlines source text instead of reprinting its syntax tree.
  • No stage depends on one solver. A construct Gurobi states natively, such as an indicator constraint, is a faster path with a Big-M fallback, never a requirement. A model only Gurobi can solve, such as one with a quadratic constraint, is refused on HiGHS before a row is read, never sent to it.

Two ways off the solver's path

Most queries go through all eight stages. Two kinds leave early: a query whose problem has a known exact algorithm is rewritten into DuckDB operators, and a query with no answer can ask why.

Query rewriting

Some optimization problems are solved exactly by sorting, ranking and running totals. Picking the most valuable item in each category is one: rank the items of each category by value and take the first. Before stage 05 writes anything for a solver, it offers the DECIDE node to every registered rule. A rule reads the node's clauses and objective through shared reader functions. A reader returns false for anything it cannot read exactly, and the rule then declines. A rule applies only when it can prove that its algorithm returns the optimum, and at most one rule may apply. When one does, its plan of ordinary DuckDB operators replaces the DECIDE node, and no model is built. The engine calls this feature direct solve.

SELECT item, category, x FROM Items DECIDE x(BOOL) SUCH THAT per category: SUM(x) by (category) <= 1 MAXIMIZE SUM(x * value);

Window operators stand where the DECIDE node stood. The projection that names the rule is the result adapter, which gives the replacement the DECIDE node's columns. Add a weight limit to the same query and no rule applies: it stays on the solver's path, as Life of a query shows. The setting decide_direct_solve takes auto (the default), off or require. A DIAGNOSE query and a forced backend always take the solver's path. How rules are written and proved is on Query rewriting; each rule is on The rewrite rules.

DIAGNOSE

A solve can fail. The constraints may contradict each other (infeasible), or the objective may grow without limit (unbounded). Without help the query stops with an error:

SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND SUM(x) >= 4 MAXIMIZE SUM(x * value);

With the DIAGNOSE prefix the failed solve does not end the query. A router reads the solver's status and sends it to one engine. An infeasible model goes to the elastic engine, which adds a slack to each clause and finds the smallest change that makes the model feasible again (the standard elastic model). An unbounded one goes to the ray engine, which reads the direction in which the objective keeps improving (a recession ray) and names the decision to bound. The answer is a relation whose rows name the clause to change and by how much. Every re-solve runs on the backend that failed. The engines are on DIAGNOSE; the user's view is on Novel features.

Terms

The words these pages use, each with the standard idea it names. The Guide teaches the language itself.

decision
A column whose values DeciDB chooses, declared in DECIDE. Each instance of a decision is one solver variable.
keyed decision
A decision with one value per class of a key, per K: x(TYPE), shared by every row of the class. per (): x(TYPE) is one value for the whole query.
reducer
An aggregate (SUM, AVG, MIN, MAX) over decisions. DeciDB's own word for it, so it is never confused with a SQL aggregate over data. COUNT reads data only.
scope
The when, per and by that decide which rows a clause reads and how many copies of it the query generates.
canonical form
The one shape stage 04 writes every clause in, so later stages read one spelling per meaning.
shape
How a canonical comparison becomes model rows: per row (one row per kept row or class), aggregate (one row per by group) or value (a helper decision per group first).
formulation
The way a construct is written as solver rows. Choosing one is stage 05's work.
linearization
Writing a construct a linear solver cannot state (ABS, MIN, <>) as linear rows, usually with auxiliary variables.
Big-M
A linearization that switches a row on or off with a binary variable times a large constant M. M must be at least as large as the row can get, so DeciDB derives it from the variables' bounds.
McCormick envelope
The linear rows that state a product x * y exactly when one factor is binary and the other is bounded.
auxiliary variable
A solver variable a rewrite adds, not one the user declared. EXPLAIN prints it as the expression it stands for.
native construct
A construct the backend states itself, such as Gurobi's indicator constraint, in place of a Big-M lowering.
singleton-row bound
A constraint on one variable, moved into that variable's lower or upper bound before the model is built, a standard presolve step.
LogicalDecide
The plan operator that carries a DECIDE clause through planning and optimization.
PhysicalDecide
The operator that executes it: buffer, evaluate, build, solve, read back.
clause tree
The tree PhysicalDecide evaluates, built with the physical plan. Its nodes are the clauses' scopes, reducers, frames and helper functions. One pass reads the rows into it from the top, then each node is computed from its children.
pipeline breaker
An operator that reads all of its input before it emits a row, as a sort or a hash aggregate does.
SolverInput, SolverModel
The evaluated clauses (numbers per data row), and the model built from them (columns, rows, coefficients) that a backend loads.
backend
A solver behind DeciDB's interface: Gurobi, when its library and license are present, or the built-in HiGHS.
query rewriting
Replacing a DECIDE node by a plan of DuckDB operators that computes the optimum, when a rule proves that it does. The engine's name for it is direct solve.
reader
A shared function a rewrite rule calls to read part of the DECIDE node, such as a clause's left side as a sum of parts. It returns false for anything it cannot read exactly, and the rule then declines. Rules read the operator itself, as DuckDB's optimizer rules read the operator they match.
rule, applicability condition
A rewrite rule in the Volcano and Cascades sense: a condition it checks, then the plan it substitutes. Here the condition includes a proof that the plan is optimal.
elastic model
A copy of an infeasible model with a slack on each constraint, minimized to find the smallest change that restores feasibility. DIAGNOSE's engine for an infeasible query.
recession ray
A direction along which every point stays feasible and the objective keeps improving: the evidence that a model is unbounded.
oracle
An independent program that states the same problem and computes the right answer, against which a test judges DeciDB's.
golden model dump
A committed copy of the exact model DeciDB builds for each query of a test corpus. Every test run compares against it, to catch a change in the model that the answer does not show.
