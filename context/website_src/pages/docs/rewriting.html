Where rewriting runs

Some DECIDE problems have an exact answer that sorting, ranking, aggregating and joining can compute. Query rewriting finds them in the optimizer and replaces the DECIDE node with those operators, so no model is built and no solver starts.

Take SUM(pick) <= 2 MAXIMIZE SUM(rating * pick). It asks for the two rows with the highest rating. The rewritten plan ranks the rows by rating with a window and sets pick = 1 on the first two whose rating helps the objective. Any query DeciDB cannot prove to be such a shape goes to the solver unchanged. The Novel features page shows rewriting from the user's side.

Rewriting is a transformation rule in the Volcano and Cascades sense: a rule that replaces a subtree of the plan with an equivalent one. It runs in the DECIDE optimizer (stage 05), once per DECIDE node, in these steps:

  1. Bound side. RewriteRhsAggregates replaces every reducer over data on the right side of a clause (SUM(x) <= COUNT(*) / 2) with a placeholder column and records the reducer. It computes nothing yet. It runs on both paths, so the solver and a rule read a data bound the same way.
  2. Check. The rule driver offers the bound DECIDE operator to each registered rule in turn. A rule reads the operator and checks its applicability condition: the facts that make the query an instance of its class. The first rule whose condition holds is taken.
  3. Read the source. The driver builds one reader of DECIDE's input for the whole plan. It joins each recorded reducer to the rows as a side table (an aggregate per group, joined back on the group key), and it puts the value checks before any other use of a row (below).
  4. Apply. The rule builds a relational plan over that reader, called the substitute.
  5. Adapt. The result adapter gives the substitute the DECIDE node's output columns and bindings.
  6. Simplify. The driver turns each NULL guard back into the plain CASE it holds (below), and DuckDB's expression rewriter runs over the substitute. DuckDB's remaining optimizer passes and its executor then treat it as any other plan.

When no rule holds, a solver backend is chosen and the solver path continues as Model, solvers and execution describes. There is no retry in the other direction: once a rewritten plan runs, it cannot hand the query back to a solver. So a rule must prove everything its plan relies on before it applies.

The engine's name for it

The engine calls this feature direct solve: the setting is decide_direct_solve, EXPLAIN prints a Direct solve rule line, and the internal docs live in context/docs/direct_solve/. This documentation says query rewriting.

Recognizing a class

A rule never reads the SQL text or the solver's model. It reads the bound DECIDE operator, the node the binder built, as DuckDB's own optimizer rules read the operator they match. From that operator alone, each rule proves that the query is an instance of its class.

What a rule reads

The bound operator is LogicalDecide. It states each fact of the query once, in typed fields. A rule reads some of them directly: each decision's domain (BOOL, INT or REAL) and scope (one per row, one per key with per K:, or one for the whole query), and each clause's when and per. Other facts take work to read, and several rules read them the same way. Each of those is a shared function, a reader, that a rule calls only when it needs it:

DirectReadClauses
each clause's comparison, right side and left side. The left side becomes a list of additive parts, each sign * scale * reducer(terms), with the reducer's by key and its own when. For a per-row clause it also gives the bound the clause puts on one decision.
DirectReadObjective
the objective, as parts read the same way. Every objective is a minimization (a MAXIMIZE flips each part's sign), so a rule reads the direction from each part's sign.
DirectReadKey
a key, such as a by or per key, as a plan groups by it
DirectSourceFacts
what the plan below DECIDE declares: the columns of each side when DECIDE's own child is a cross product, the columns that a directly scanned table declares NOT NULL, and its UNIQUE keys whose columns are all NOT NULL. O1 reads it.

A rule tests the decisions first, which costs nothing, and calls a reader only when those tests pass. The readers read the operator itself, not a copy of it: a copy for the rules would be a second place for the same fact, and the two paths could then read it differently. They read the complete bound clause, not the solver's flattened model, because a flattened model can drop a term and a rule must see everything the user wrote. Where the solver path has a reader for something, the rules call the same one, so the two paths cannot disagree: the term splitter that breaks SUM(2*x - x) into linear terms, and the classifier that reads a per-row comparison as a bound on one decision (DecideReadSingletonRow).

The analysis is conservative: a reader returns false for anything it cannot read exactly, and the rule that called it declines. Examples are an order-0 norm, a membership such as x IN (1, 2), a per K: in front of a per-row clause, a reducer inside another reducer, and an objective whose constant is not finite. A decline is not an error and carries no reason: the rule applies or it does not. So a gap in a reader can never become a wrong rewrite.

A SUM skips a row whose data is NULL, on both paths. The clause reader keeps this with a NULL guard on each coefficient: a CASE that reads the coefficient as 0 on a row the sum skips. The guard is its own expression node, BoundDecideNullGuardExpression, a Decorator over the CASE. An error message prints the value it protects, and a rule that needs a constant reads through it. When the driver installs a rule's plan, it replaces every guard with the plain CASE, so DuckDB simplifies it as any other expression.

One fact a rule does not read: the value checks. These are the checks the solver makes on a row before it reads a value from it, such as "a limit read from the data is not NaN". They are one list on the operator, and the driver puts them under every rule's plan (below).

Everything a rule reads is a fact of the query or the catalog, never an estimate. A declared NOT NULL holds for every row a plan reads. Column statistics describe the data at planning time and prove nothing, and a prepared plan keeps its choice while the rows change.

The rule registry

Each problem class is one rule, a class that implements DirectSolveRule. This is the Strategy pattern: every rule offers the same four methods.

CheckCondition(decide, context)
reads the bound operator decide and returns the applicability condition when the query is an instance of the class, or null. Only this method can build a condition, so Apply never sees an unverified shape.
Apply(reader, optimizer, condition)
builds the substitute from the condition, reading DECIDE's input through reader
Summary()
the fixed line EXPLAIN prints for the rule
Name()
the rule's name, such as S1_UNIFORM_MATROID

One registry lists the rules, one factory function each (Factory Method): MakeS1UniformMatroidRule(), MakeA1SeparableBoxRule() and so on. A new class is a new file, <id>_<slug>_rule.cpp, and one line in the registry. The driver and the result adapter hold no rule-specific code. The driver is a Template Method: it runs the same steps for every rule, and the rule fills in the two that differ.

Proving a class

CheckCondition checks the shape, then certifies every clause, objective part, decision, runtime check and output the plan relies on. Shape and certification are one step. Cascades separates a cheap pattern match from the rule because one pattern is tried on many subtrees; a DECIDE query offers each rule a single node, so a separate pattern step saves nothing.

Rules prove values with shared predicates, so every rule answers "may I use this value" the same way. A value is admissible when it is numeric, reads no decision, is deterministic and reads only the source row (DirectProveValue). The bound reader reads each kind of value once for all rules: a per-row bound, a fixed value of a BOOL, the limit of a clause, an objective term. For example, S1 proves that its decision is one BOOL per row, that every aggregate clause is a count whose constant coefficients add up to exactly 1 or -1, that all count clauses share one by key and one when, that every constant limit is below 1e20 in magnitude, and that the objective is a linear score.

Recognition reads the bound operator and never the data, so declining costs the same at every size: about 0.14 ms of planning, measured on a query that R4 nearly admits.

Rules are disjoint. The driver offers the operator to the rules in the registry's order and takes the first whose condition holds. Two rules holding at once would mean the rules overlap, which is a bug. A debug build checks every later rule and stops on an assertion if one holds. A release build takes the first, so a user never sees an internal error for it. This departs from Cascades, where several rules may match and the cheapest plan wins: here no ordering between two rules would be safe, so the rules are kept apart by the shape they require. S1 requires a count body whose coefficients add up to 1 or -1, and S3 declines exactly that body. A1 forbids every aggregate clause, and R1 requires one.

The plan a rule builds

Apply builds the substitute: a plan of ordinary DuckDB logical operators (projections, windows, aggregates, joins and materialized CTEs) that computes the optimal assignment. DuckDB optimizes and runs it like any plan it built itself.

Side by side with the solver

The shortlist of the examples: at most two films per genre, with the highest total rating. Rewritten, it runs as these operators:

SELECT title, genre, rating, pick FROM Films DECIDE pick(BOOL) SUCH THAT SUM(pick) by (genre) <= 2 MAXIMIZE SUM(rating * pick);

Read it from the bottom:

  1. Scan. The lower SEQ_SCAN reads genre and rating, and the row id.
  2. Scope and score. Two projections give each row its group key and its score. The score is -rating, because the objective is a minimization in canonical form, with a check that raises the solver's error for a NaN or infinite rating.
  3. Rank. The WINDOW computes ROW_NUMBER per genre in order of the score.
  4. Prefix. Three projections set pick = 1 where the rank is within 2 and the score improves the objective.
  5. Late materialization. The HASH_JOIN fetches title from a second scan by row id, after the rows are chosen, so the wide column never enters the rank (below).
  6. Adapter. The projection that names the rule is the result adapter. The top projection is the query's SELECT list.

With rewriting off, the same problem goes to the solver. DuckDB runs one DECIDE operator over the scan, and the operator builds a model with one binary variable per row:

SELECT title, genre, rating, pick FROM Films DECIDE pick(BOOL) SUCH THAT SUM(pick) by (genre) <= 2 MAXIMIZE SUM(rating * pick);

A rule builds its expressions with ExpressionBuilder, a fluent helper over bound expressions (Fowler's Expression Builder), in their general form: a flag that is always true, a CASE on it, a multiplication by 1.0. DuckDB's expression rewriter runs before the DECIDE optimizer, so nothing has simplified them yet. The driver runs the rewriter over the substitute, and DuckDB's statistics propagation later folds the constants the stages carry as columns. This is canonicalization after lowering, as MLIR's canonicalize pass and LLVM's InstCombine do it. Measured at TPC-H scale factor 1, the rewriter alone lowers the cost of a plan's row-side projections by about a tenth.

Three plan shapes

The rules share three plan shapes, each a standard relational idea. Shared code builds each one, and a rule supplies only what differs.

ShapeRulesHow it computes the answerStandard idea
Ranked prefixS1, S2, S3a window ranks each group's rows by one column, and the answer is a prefix of the rankinga Template Method (DirectRankedPrefix): the builder fixes the plan, and the rule gives the order, the prefix size and the group's verdict
Group then joinA2, N1, R1, R4a hash aggregate reduces each class to one row that holds its answer, and a second read of the rows joins it back on the class keyhow DuckDB decorrelates a scalar subquery (DirectJoinClassAnswers)
Verify then streamA1, O1a first read computes a one-row verdict over every row, and a second read, gated on it, computes each row's answer as the row passesPostgreSQL's InitPlan, DuckDB's uncorrelated scalar subquery (DirectAllRowsValid)

A class key is the set of columns a rule groups rows on and joins answers on. It is built so that a row in no class (a when drops it, or its key is NULL) has a NULL in a column the join compares with =. SQL's outer-join semantics then give that row NULL answers with no flag column, and a single integer key compared with = is what DuckDB's perfect hash join takes (see the edits to DuckDB).

Every row is read

The solver reads every row before it answers, so a bad value on the last row raises an error even under LIMIT 1 or COUNT(*). A rewritten plan owes the same; only LIMIT 0 may skip the read. Each shape keeps it in its own way:

  • A hash aggregate holds every row before it gives one, so every check below it has run on all rows first.
  • A rank window holds every row too, but gives them back group by group, so a check above it reaches a later group only when the parent reads that far. A group's checks therefore stand in a held-rows stage (DirectHeldRows): a materialized CTE that runs to its end before any read of it starts. It is a pipeline breaker, an operator that consumes its whole input before it produces output, like SQL Server's Eager Spool or PostgreSQL's Material node.
  • A streaming plan holds nothing, so it verifies first. One read computes the bool_and of every row's check, which is true or raises, as a one-row CTE. Every later read is a filter on that verdict crossed with the rows (DirectSourceReader::Gate), so no row passes before every row is checked.

A1 is the streaming case. In its plan, the CTE's first child is the verdict: an UNGROUPED_AGGREGATE over the per-row stages of a first scan. Its second child is the gated read: a second scan crossed with the verdict (FILTER over CTE_SCAN), then the projections that compute each row's answer.

SELECT sku, qty FROM Orders DECIDE qty(INT) SUCH THAT qty BETWEEN min_qty AND max_qty MAXIMIZE SUM(margin * qty);

The verdict costs a second evaluation of the per-row stages, in place of memory that grows with the input.

The value checks are the checks the solver makes on a row before it reads a value from it: that a limit read from the data is not NaN, and that an = limit has one value in each group. They are one list on the DECIDE operator, value_checks, and both paths run the same list. The solver runs it on each row before it reads a value from that row (DecideTreeColumns::CheckData). A rewritten plan runs it with DirectAddRowChecks: one verdict over every row, which gates every later read of the source, so the checks run before any check of the rule's own.

Reading the source twice

Most plans read the source more than once: a verdict and a stream, a class plan and a join. One DirectSourceReader serves the whole plan and decides once, from the total number of reads, whether to recompute the source per read or to copy it, the choice DuckDB makes for a CTE.

  • A source made of deterministic projections and filters over one table scan is rebuilt per read, so each read is a parallel scan. It is copied once instead when the copy is cheaper: a read of the copy costs 0.4 of a re-scan (COPY_READ_COST), so a source read three times or more is copied, provided the copy takes at most an eighth of the memory limit (COPY_MEMORY_SHARE). Both constants come from interleaved timings on TPC-H partsupp and a 20-column table at 10,000 to 1,000,000 rows.
  • Any other source (a join, a subquery with an aggregate, a table function, a call to random()) is materialized once, so every read sees the same rows.

The result adapter

The substitute must look exactly like the DECIDE node it replaces: every source column in order, then one column per decision, with the same types. A small logical operator, the result adapter, guarantees it.

A decision's column is INTEGER 0 or 1 for BOOL, BIGINT for INT and DOUBLE for REAL, as on the solver path, and duplicate rows stay separate rows. The adapter (LogicalDirectResultAdapter, built by AdaptDirectResult) is three standard ideas in one operator:

Adapter
in the GoF sense: the substitute presents the interface (columns and types) of the node it replaces
Binding boundary
as a DuckDB projection is: the adapter owns a table index, and its outputs are (index, i)
Optimization fence
a filter or a limit above the result does not cross it. Pushed into the rank's input, it would change which rows are ranked. Optimizing inside the substitute is fine.

A rule states where each output lives in its plan (the slot map, DirectSubstitute::slot_map), which decision outputs may be skipped, and which validated columns must stay live: the columns that force the all-rows read. The driver checks the slot map in release builds and raises an internal error on a misfit, because rules are plug-ins and a broken one must fail loudly.

The driver then gives the adapter a new table index and rewrites every reference above the DECIDE node to the adapter's bindings, once, with DuckDB's ColumnBindingReplacer stopped at the adapter (RebindAboveAdapter). The adapter declares one dependency per output. A transparent wrapper does not work: DuckDB's optimizer would prune the child to the columns it sees used, and a parent that reads another column would read wrong data. In a physical plan the adapter lowers to a projection, so there is no new physical operator; logical EXPLAIN names it DIRECT_RESULT_ADAPTER.

Pruning and late materialization

An output no parent reads becomes a typed NULL placeholder only when skipping it is proved safe: a stored column, a constant, or a column passed through unchanged. A computed column that could raise an error stays live, because the solver would have raised it.

Late materialization is the column-store technique of reading the narrow columns first and fetching the wide ones by row id once the rows are chosen. When the source is one stored table under deterministic projections and filters, the plan carries the table's row id like any source column. After DuckDB's unused-column pass, when it is known what the parent reads, each variable-width column the parent reads and the rule only forwards (VARCHAR, BLOB, lists, structs and the like) comes from a second scan joined on the row id. That is the HASH_JOIN in the shortlist plan above.

Only variable-width columns move, because holding them is what costs memory. Peak memory of S1 over 5,000,000 rows with a 512-byte payload column, in a fresh decidb -readonly process (macOS memory footprint):

The payloadPeak, MiB
unused by the parent (the control)725
carried through the rank3,351 to 3,362
late-materialized811 to 829

A fixed-width column stays in the single read: for a BIGINT key, S1's global top-k at 5,000,000 rows takes 0.28 to 0.33 s with the column moved against 0.21 to 0.25 s with it held, at the same memory.

The step (ApplyDirectLateMaterialization) runs inside DuckDB's UNUSED_COLUMNS pass, right after removal, not beside DuckDB's own LATE_MATERIALIZATION pass: the passes in between add projection maps that unused-column removal does not keep up to date.

The policy

One setting controls rewriting. It is on by default, because a rewritten plan returns the solver's answer and raises the solver's errors, and the whole test suite runs on both paths.

decide_direct_solveA rule appliesNo rule applies
auto (default)rewritten plansolver, silently
offsolversolver
requirerewritten planan error; the solver never runs

The mode is read when the plan is built, and a prepared statement keeps its choice until it is bound again. DIAGNOSE always uses the solver (Inside DIAGNOSE), and so does the test-only environment variable DECIDB_FORCE_SOLVER; require with either is an error. The benchmarks pin require, so a query no rule takes fails instead of being timed on the solver, and so do the tests that assert a rule applies. Adding a lower limit on the total to the shortlist leaves no rule that applies: S1 takes count limits of one scope only, and S2 takes upper limits only.

SELECT title, genre, rating, pick FROM Films DECIDE pick(BOOL) SUCH THAT SUM(pick) by (genre) <= 2 AND SUM(pick) >= 5 MAXIMIZE SUM(rating * pick);

auto is the default because the rules measured faster than Gurobi in every benchmark but one: R1 at 100,000 rows, where the rewritten plan took about 10% longer (the rules and Performance give the numbers). A bug in a proof would give a wrong answer, not a slow one, so the guard is the test suite. Each rule has a differential test that runs every case on an independent oracle model, on off and on require, and requires all three to agree (Testing). The whole suite also runs with DECIDB_TEST_DIRECT_SOLVE=off, which sends every query to the solver.

What EXPLAIN shows

A rewritten plan carries one annotation (DirectExplainAnnotation) with three lines: the mode, the rule, and the rule's fixed condition line, which states the class's shape and holds no number from the query. It shows in logical and physical EXPLAIN and in profiling output.

SELECT title, genre, rating, pick FROM Films DECIDE pick(BOOL) SUCH THAT per genre: SUM(pick) by (genre) <= 2 MAXIMIZE SUM(rating * pick);

When no rule applies under auto, nothing is added, so the EXPLAIN of such a query is exactly what the solver path prints. require says whether a rule applies, not why one does not.

Ties, exactness and errors

  • Ties. When several assignments are optimal, a rewritten plan may return a different one than the solver, with the same objective. Tests compare the row count and the objective, never the tied assignment. A1 and A2 break a tie between equally good ends of an interval toward the end nearest 0.
  • Exact bounds. A rewritten plan compares every bound exactly, in DOUBLE, as DuckDB evaluates it. The solver accepts a violation of about 1e-6. So SUM(x) <= 1.9999999 selects 2 rows on the solver and 1 rewritten, and S3 with weights 0.1 and 0.2 under <= 0.3 (whose DOUBLE sum is 0.30000000000000004) selects both rows on the solver and one rewritten. Rounding the bound removes the difference.
  • Errors. A rewritten plan raises wherever the solver raises (a NaN coefficient, an empty box, an infeasible group), with the solver's text, built by the functions the solver calls (decide_value_messages.hpp). A NULL is skipped where it is read, as on the solver. When a query has several errors, the rewritten plan may raise a different one of them than the solver.
  • Warnings. A rewritten plan builds no model, so the solver path's warnings about coefficient sizes do not print. A rule that divides by a number it computes warns instead when the divisor is below the normal range of a DOUBLE, about 2.2e-308.
  • Two answers the solver path refuses. The solver expands SUM(POWER(x - v, 2)) and refuses the query once the constant v^2 passes a DOUBLE; A1 and A2 answer it, since their answer never reads that constant. And N1 answers a quadratic limit on a machine without a Gurobi license, where the solver path refuses it.

When DeciDB declines

Rewriting is a shortcut, not a second solver. A rule takes a shape only when its proof is short and the gain is large; the solver answers everything else correctly, only more slowly. A rule declines:

  • anything a reader cannot read;
  • a constant limit of magnitude 1e20 or more, because the solver's reading of such a constant depends on the rows;
  • a bound that contradicts the decision's built-in domain (x >= 2 on a BOOL). The solver rejects it with its own message before it reads a row, even over an empty source, so the rule leaves the query to the solver;
  • a sign read from the data that would change the kind of problem, such as a weight that makes a limit non-convex, since the plan cannot hand the query back once it runs. A sign that only changes values within the same pass is handled in the plan, for every sign: R4's weights are of this kind;
  • a shape that would need a long proof or a parity check against solver quirks: S1 declines SUM(x + 1) <= 5, a count with a constant term.

Edits to DuckDB

A rewritten plan is only as cheap as DuckDB's own rules and operators make it. Ten edits to DuckDB's code make a rule's plan run as DuckDB runs the same answer written by hand in SQL.

Eight of the edits name nothing of DECIDE. Each of those helps any query with the shape it handles, and a standard query returns the same rows. The first seven are these:

CaseSimplificationRule
evaluates a constant WHEN without throwing. When the evaluation fails (an overflow, a bad cast), the check stays in the CASE and raises at run time, on the rows that reach it. A rule's checks are CASEs that must raise only where they are chosen; a throwing evaluation would raise while planning, even over no rows. The edit changes when an error is raised, not whether.
Statistics propagation of a CASE
propagates the WHEN checks first, then applies the rule's own fold (CaseSimplificationRule::Simplify): a check the statistics prove false or NULL is erased, and one they prove true becomes the ELSE. DuckDB never reruns the expression rewriter after statistics, so a check proved only by statistics, such as x IS NULL over a NOT NULL column, would run on every row. A rule builds such a check for every nullable input.
ArithmeticSimplificationRule
removes x * 1.0, 1.0 * x, x / 1.0 and x - 0.0 for FLOAT and DOUBLE. These hold bit for bit under IEEE 754 for every x, including -0.0, NaN, the infinities and NULL. x + 0.0 does not (-0.0 + 0.0 is +0.0) and stays. DuckDB's rule set matches integer types only, and a rule's plan computes in DOUBLE.
Statistics of a comparison join
turns a join condition written IS NOT DISTINCT FROM into = when the statistics show that neither side can hold a NULL. The two are then equivalent, and the perfect hash join takes only =.
PerfectHashJoinExecutor
takes LEFT and SINGLE joins on one integer = condition, not only inner joins. One slot past the build range holds NULL in every column, and a probe row whose key is NULL, out of range or absent reads it. A build side with duplicate keys still falls back to the hash join, so a SINGLE join's more-than-one-row error still raises. The class join of a group-then-join plan is a SINGLE join on the class key: at scale factor 1 it costs 20.8 ms of CPU on IS NOT DISTINCT FROM, 15.2 ms as a hash join on =, and 2.1 ms as a perfect hash join.
Folding in statistics propagation
after an expression's own handler, an expression whose children are all constants is evaluated and becomes its value; if the evaluation fails, the expression stays and raises at run time. The handlers turn children into constants, and without this fold the expression above them would compute the same value on every row.
Constant columns
a projection column whose expression is a constant is recorded with its value, and a reference to it inside a computation (a function argument, a comparison, a CASE, a cast) becomes the constant. A reference that is itself an output, a join key or a group stays a column. A rule's plan carries constants through its stages as columns (a seed, a flag, a bound written as a number), and the expression rewriter does not look through a projection.

The eighth serves the result adapter. DuckDB's unused-column pass narrows a materialized CTE's definition to the columns its references read, which is projection pushdown across a CTE boundary (Spark's PushdownPredicatesAndPruneColumnsForCTEDef does the same); DuckDB itself keeps a definition whole. The last two edits hook rewriting's own steps into that pass, and a standard query reaches neither. The pass calls a PruneUnusedOutputs hook on an extension operator, which the adapter uses to replace an output no parent reads with a typed NULL where skipping it is safe. And right after the pass, the optimizer calls ApplyDirectLateMaterialization (late materialization).
