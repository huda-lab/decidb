Three stages

The front end turns SQL text into a LogicalDecide operator in DuckDB's logical plan. It runs in three stages, and each refuses only what it alone can see.

StageReadsProducesRefuses
01 Parserthe query texta parsed SelectNode holding one ParsedDecide, and the text of every expression in the clausesyntax: a missing type, a comma between constraints, a removed spelling
02 Binderthe parsed tree and the catalogbound clause records: decisions, keys, types, reducersnames, keys, scopes, casts over decisions, volatile functions
03 Logical planthe bound treeone LogicalDecide above the scans and filtersnothing of its own; it calls the canonicalizer, which refuses shapes

None of the three moves a term across a comparison or picks a formulation. Which side a term belongs on is decided once, by the canonicalizer, on the bound tree. How each construct reaches the solver is decided by the optimizer. Keeping the front end free of both is what lets EXPLAIN, DIAGNOSE and every message quote a clause exactly as the user typed it.

The parser

The parser turns SQL text into a parsed SelectNode carrying the decisions, the constraints, the objective's sense and the objective. It refuses syntax and decides no shape.

DuckDB parses with libpg_query, its fork of the PostgreSQL grammar. Bison compiles that grammar into an LALR(1) parser: a parser that chooses each step from the next token alone. DeciDB adds its productions to the same grammar, so a DECIDE query is one SELECT statement to DuckDB, with one more optional clause. DECIDE, SUCH, MAXIMIZE, MINIMIZE and DIAGNOSE are reserved keywords.

One clause, two orders

A query may declare its decisions after WHERE, in one block, or between SELECT and FROM, the order the DeciDB paper uses (the full shape). The grammar has a slot for each order, decide_clause for the first and decide_declaration with decide_body for the second, and both build the same PGDecideClause through makeDecideClause(). Nothing after the parser knows which order the user chose.

A declaration is a name and a type in parentheses, alone or behind a per. The type is a plain identifier that makeDecideVariableType reads as INT, REAL or BOOL in any case. DECIDE adds no keyword for a type on purpose: DuckDB quotes every keyword when it prints a name, so a keyword BOOL would quote a column named bool in every message and rendered query.

A name with no type parses as a declaration whose type is missing. The transformer refuses it once the whole query has parsed, with the caret on the name. It waits because Bison runs a grammar action before it reads the next token, so an error raised there would hide a syntax error at that token. A comma between constraints is a plain syntax error.

SELECT item, x FROM Items DECIDE x SUCH THAT SUM(x * weight) <= 50 MAXIMIZE SUM(value * x)

The scopes of the language (when and per in front of what they govern, by after a reducer) are four small productions:

decide_scope ::= decide_when | decide_when decide_per | decide_per decide_when ::= WHEN_DECIDE a_expr decide_per ::= PER_DECIDE expr_list | PER_DECIDE_PAREN '(' ')' | PER_DECIDE_ROW ROW decide_by ::= BY_DECIDE '(' ')' | BY_DECIDE '(' expr_list ')'

A constraint or an objective is decide_scope ':' body or a bare body. Three choices keep the grammar small:

  • The colon ends the scope. So the condition of a when is a full SQL expression and needs no parentheses.
  • One precedence level, DECIDE_ITEM, closes a body. It sits above AND and below the comparison operators. A top-level AND therefore separates two constraints, per g: A AND B scopes only A, and each body keeps its SQL shape. The parser never repairs an association after the fact.
  • A scope inside a call opens with its own token. A reducer's own scope, as in sum(per D: e) or sum(when c: e), is func_name '(' decide_scope ':' func_arg_list ')'. Its first token is a DECIDE-only token, so the parser tells it from an ordinary argument list at once. decideCheckKey then checks that each key element is a column or a relation name.

The grammar declares %expect 4: Bison accepts exactly four shift-reduce conflicts. All four come from the optional declaration slot, one per simple_select alternative. They arise only when FROM and WHERE are both empty, and both derivations build the same node, so Bison's default choice changes nothing.

Gated keywords

Six of DECIDE's words already mean something in SQL. WHEN belongs to CASE, and a DECIDE WHEN after a function call collides with WITHIN GROUP and breaks ordinary function-call parsing. BY belongs to GROUP BY and ORDER BY. And per must stay usable as a column name in every other query. A frame selector, such as at(previous: x) over (t.period), reads a value at another row; its AT, OVER and WITHIN belong to SQL too.

So the words become DECIDE tokens only inside a DECIDE clause. DuckDB's lexer passes every token through a filter, base_yylex, which already looks one token ahead for NOT, NULLS and WITH. DeciDB adds its rules to that filter:

WordBecomesWhen
WHENWHEN_DECIDEoutside any CASE of the clause
BYBY_DECIDEdirectly after )
PERPER_DECIDE_PARENbefore (, as in per ()
PERPER_DECIDE_ROWbefore ROW
PERPER_DECIDEotherwise
ATAT_DECIDEbefore (, at the clause's own level
OVEROVER_DECIDEdirectly after ), at the clause's own level
WITHINWITHIN_DECIDEdirectly inside the parentheses of that OVER

The clause's own level is the body after SUCH THAT, outside any SQL subquery written there. So a window or a WITHIN GROUP inside a subquery lexes as SQL, and a decision may still be named at in the declarations: DECIDE at(REAL).

The three PER tokens need the lookahead: per (), per row and per key cannot be told apart by an LALR(1) grammar alone, since ( also opens an expression and row is also a column name. GROUP BY, ORDER BY and PARTITION BY always follow a keyword, never ), so they stay plain inside a subquery written in the clause.

The filter tracks four pieces of state:

  • Armed. DECIDE or SUCH sets in_decide_clause. SUCH sets it again for the split order, whose declaration slot clears it so that FROM, JOIN ... ON and WHERE lex as plain SQL.
  • Level. decide_in_body marks the body after SUCH. decide_paren_depth counts parentheses, and decide_subquery_depth marks where a SQL subquery opens, so the frame tokens appear only at the clause's own level.
  • CASE depth. CASE adds one to decide_case_depth and END takes one away, so a WHEN inside a CASE stays SQL's.
  • A stack of enclosing clauses. A DECIDE query may be a subquery inside another DECIDE clause. PGDecidePushLexState saves the enclosing clause's state when a new clause opens, and the grammar action that closes the clause restores it, so a scope written after the subquery still lexes as DECIDE's. The stack keeps 16 levels.
if (cur_token == CASE) yyextra->decide_case_depth++; else if (cur_token == END_P) { if (yyextra->decide_case_depth > 0) yyextra->decide_case_depth--; } else if (cur_token == WHEN && yyextra->decide_case_depth == 0) return WHEN_DECIDE; else if (cur_token == BY && after_rparen) return BY_DECIDE;

One clause can hold both kinds of WHEN. The scope's when is at depth 0; the CASE WHEN inside the sum is at depth 1 and stays SQL's:

SELECT item, x FROM Items DECIDE x(INT) SUCH THAT x <= 3 AND when category = 'tech': SUM(x * CASE WHEN weight > 15 THEN 2 ELSE 1 END) <= 4 MAXIMIZE SUM(value * x)

The cost of gating: inside a DECIDE clause, subqueries included, these words are keywords in those positions. A column named per is written quoted there ("per"), as DeciDB's own printer does, and so is a function called at at the clause's own level ("at"(...)). Outside the clause nothing changes.

The transformer and source spans

DuckDB's transformer turns the PostgreSQL parse tree into DuckDB's parsed expressions. TransformSelectNode builds the DECIDE clause as one ParsedDecide in the SelectNode's one new field, decide, which is empty for a query with no DECIDE. It holds variables, constraints, objective, sense (MAXIMIZE, MINIMIZE, or FEASIBILITY when no objective is written) and text. A declaration with no SUCH THAT is refused here: DECIDE has no SUCH THAT clause.

Each part of the clause has a parsed type of its own:

WrittenParsed as
x(INT), per K: x(INT)a DecideDeclaration: the name, the type, and its per as a DecideScope
when c: C, per K: Ca DecideClause: the body C and a DecideScope that holds c and K
per row: Ca DecideScope whose per is ROW, so the clause keeps its spelling
SUM(e) by (G), SUM(per K: e)a DecideReducerExpression: the call, its own scope, and its by key
at(previous: x) over (t.period)a DecideFrameExpression

A plain sum(x) stays a FunctionExpression. The reducer and the frame are parsed expression classes of their own, the way DuckDB's WindowExpression is for a window function.

The transformer also keeps where each expression came from. Every SQL expression reduces through a decorator rule (a_expr: a_expr_body, and the same for b_expr), whose action, noteDecideExpr, records the start and end of each expression of the DECIDE clause. The transformer keys each span by the query location of the parsed node it builds, and TransformSelectNode collects the spans and the clause's text into ParsedDecide::text, a DecideSourceText. This is Clang's SourceManager idea: one store of source text, and a location on every node. A later stage that quotes a clause cuts the user's text at a node's location instead of printing its tree. So a message shows x <> 5 where the tree would print x != 5, and keeps the user's spacing and function names.

SelectNode::ToString() prints the clause back through ParsedDecide::ToString(): the declarations as x(INT) and PER key: x(INT), then the rest as the user typed it when the text is kept, else each clause with its scope in front and a reducer's BY (key) after it. The contract is a structural round trip, not a copy of the text: parsing the printed SQL gives an equal parsed statement. DuckDB's statement verifier checks it whenever verification is on.

The DIAGNOSE prefix is one more alternative of VariableShowStmt, as SUMMARIZE is, and the transformer turns it into a table reference with ShowType::DIAGNOSE. Whether the inner query holds a DECIDE is a binding question, since the clause may sit in a subquery (how DIAGNOSE is routed).

Removed spellings

Some spellings are no longer part of the language: a WHEN or PER written after a constraint, a reducer or the objective, a declaration T.x(INT), and the colon form SUM(D: e), now written sum(per D: e). The grammar has no production for them, so each is an ordinary syntax error at the word the parser cannot place:

SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 WHEN category = 'tech' MAXIMIZE SUM(value * x)

scalar is an ordinary name, so DECIDE scalar(INT) declares a decision called scalar. The tests check each old form against the error the current grammar gives it.

The binder

The binder resolves every name in the clause, gives each decision its key and type, recognizes reducers, and refuses what only binding can see. It moves no term and judges no algebra.

DuckDB binds FROM and WHERE as for any query. The DECIDE section of BindSelectNode then calls DecideDeclarationsBinder::BindDeclarations, which works in this order:

  1. Declarations. Every name is checked and collected, then every key is resolved.
  2. The parsed clauses. Function aliases are renamed, and the checks that need what the user typed run before binding erases it: D.x in a scope, where scopes stand, and casts over decisions.
  3. The constraints. DecideConstraintsBinder binds them, one record per constraint; then volatile functions are refused on the bound tree.
  4. The objective. DecideObjectiveBinder binds it, and volatile functions are refused there too.

The two clause binders derive from DecideBinder, which derives from DuckDB's ExpressionBinder. That is DuckDB's own pattern: one expression binder per clause, with a shared base class for the rules every clause follows. Here the shared rules are reducers, a reducer's own scope and by, key scopes, and where when, per and by may stand.

Declarations and keys

The binder reads every declaration's name before it resolves any key, so a key can be told apart from a decision declared before or after it. A name that matches a column of the FROM clause, or a name declared twice, is refused. A decision is then registered under its bare name, and only that name reaches it. In a when, a key or a by, D.x is refused: 'D.x' is a decision, which when, per and by cannot read. Anywhere else D.x is no decision but an ordinary column name, which SQL resolves as usual.

Each decision gets a scope (DecideVarScope) from the way it is declared (one per row, one per key, or one in all):

ROW
x(INT) or per row: x(INT): one decision per result row.
KEYED
per K: x(INT): one decision per class of the key K. The scope also keeps the key as written, so a message can name the decision the way the user declared it.
GLOBAL
per (): x(INT): one decision for the whole query, a query-wide decision.

A key element resolves against the query's own FROM clause, in this order: a declared decision (refused, since a key holds only data), a column as SQL resolves it, a relation (standing for all its stored columns), a column of an outer query (refused), and otherwise an error that names it:

SELECT S.shipmentID, ship FROM Shipment S JOIN Depot D USING (depotID) DECIDE ship(INT), per depot: open(BOOL) SUCH THAT ship <= S.demand * open MINIMIZE SUM(per D: opening_cost * open) + SUM(unit_cost * ship)

Every key the clauses write goes into one key table of DecideKey entries: a declaration's per K, a reducer's own per, a by (G), a constraint's per K: and the key of each nested reducer's path. FindOrCreateDecideKey compares elements as a set and puts them in one order, so per D.depotID, D.region and by (D.region, D.depotID) are one entry, with one grouping at execution. A keyed decision points at a KeyedScopeInfo: its key and the decisions it keys. One scope exists per key, whichever spelling names it.

A decision has no value until the solve, so WHERE, which runs below DECIDE, may not read one. The select list, ORDER BY, HAVING and QUALIFY run above DECIDE and read a decision as an ordinary column.

Types

The binder is the only layer that fixes the type of a decision's result column:

SELECT item, x, typeof(x) AS x_type, b, typeof(b) AS b_type, r, typeof(r) AS r_type FROM Items DECIDE x(INT), b(BOOL), r(REAL) SUCH THAT x <= 2 AND r <= 1.5 AND SUM(weight * x) + SUM(weight * r) <= 60 AND SUM(b) <= 2 MAXIMIZE SUM(value * x) + SUM(value * b) + SUM(value * r)
  • INT is BIGINT. The width must hold any value the solve can reach, and no bound tells the binder what that is: a limit may arrive as a column read at execution (x <= cap) or as a total that bounds no single variable (SUM(x) <= 5000000000). A 32-bit column would move the failure to the readback, which would truncate the excess. Execution still range-checks every value it returns.
  • BOOL is INTEGER with a flag. It must take part in arithmetic (x * weight), which BOOLEAN cannot. The domain travels separately, in is_boolean_var, to the model builder, which gives the column its [0, 1] box. The binder writes no x >= 0 or x <= 1 constraint.
  • REAL is DOUBLE.

Where when, per and by may stand

A clause with no scope written is per row:, and a reducer with no by is by (). ValidateDecideScopeSpellings checks each scope on the parsed tree, one constraint at a time, before the clauses bind. A condition, a key and a by key may read only data. A decision there has no value until the solve, and a window function or a reducer would read rows the scope has not chosen yet.

SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT when x > 0: SUM(x * weight) <= 40 MAXIMIZE SUM(value * x)

Each constraint binds to a record, a BoundDecideClause, and the objective to one more. A reducer binds to a BoundDecideReducerExpression. Bound, a scope becomes fields of these, not a rewrite of the clause:

WrittenBound as
when c: Cthe record of C, with scope.when set to c
per K: Cthe record of C, with scope.per set and scope.class_key naming K's entry in the key table
per row: Cnothing: the default written out
SUM(e) by (G)the reducer's by field, naming G's entry in the key table
SUM(when c: e)the reducer's own filter
SUM(per K: e)the reducer's per field, naming the key scope whose classes it counts once

No layer turns a scoped clause into a different unscoped one. The canonicalizer reads these fields to choose the clause's shape, and execution partitions rows by each key. That is why EXPLAIN can print a scoped clause in the user's own words.

Reducers

A reducer is an aggregate over decisions: SUM, AVG, MIN or MAX. DECIDE uses its own word so it is never confused with a SQL aggregate over data, which stays DuckDB's. IsDecideAggregateName recognizes the four names, and DecideBinder::BindAggregate binds them for both clause binders as a BoundDecideReducerExpression. A reducer takes exactly one argument: max(x, 2) is DuckDB's top-n aggregate and is refused ('max(x, 2)' has 2 arguments).

  • BindReducer binds a reducer written with its own scope or a by. The condition binds as data onto the reducer's filter; a per K sets its per field to K's key scope; the by key binds last.
  • A reducer whose key names a relation, sum(per D: e), counts each row of D once: the relation's stored columns form the key. Nothing about the body is checked here. A body that reads more than D fixes, such as a column of another relation, counts once per variant: once for each distinct value it reads within a row of D.
  • A reducer may sit inside another, to any depth, as in sum(per k: max(e) by (k)).
  • norm(e, p) binds as a reducer node whose norm field holds its order. The canonicalizer and the optimizer lower it.
  • COUNT binds as data only: COUNT over a decision is not supported.

The binder chooses no formulation for any of them: an ABS, a hard MAX or an IN is still the node the user wrote when the plan is built.

One name per function

DuckDB registers one function under several names: pow, power and ^ for **; abs for @; add, subtract and multiply for +, - and *; mean for avg. Before any check reads a name, RespellDecideAliases renames each such call in the DECIDE clauses to the primary name DuckDB records for it. DeciDB keeps no alias list of its own.

So every later check matches one name per function, and multiply(x, weight) answers as x * weight does. The name the user typed survives in a field, written_name, which only rendering and messages read. The renaming runs in the binder, not the canonicalizer, because binder checks read names: renamed later, multiply(avg(v), x) would slip past the refusal of avg(v) * x.

SELECT item, x FROM Items DECIDE x(INT) SUCH THAT SUM(multiply(x, weight)) <= 50 AND pow(x, 1) <= 3 MAXIMIZE SUM(value * x)

The ≡ lines are the canonical form. multiply is respelled like any *, with the data coefficient moved to the left, and keeps its written name; pow(x, 1) is x.

What only binding can refuse

Four layers refuse a DECIDE query, each for what only it can see:

LayerRefuses
Parsersyntax, including a removed spelling
Bindernames, keys, scopes, function resolution; who wrote a cast; a reducer's kind and argument count; a truth value read as a number
Shape checkthe algebra: functions over a decision, exponents, division by a decision, CASE over a decision, degree, and the whole-number step of <, > and <>
Solver gatewhat the chosen solver cannot take, such as quadratic constraints on HiGHS

The binder judges no algebra, on purpose. It sees the tree as typed, and one polynomial has many trees: 2*x*x, x*2*x and (x-t)*(x-t) differ. A judgement there needs a recognizer per spelling, a list of cases that keeps growing, and every gap in it refuses a legal query. After canonicalization each product has one spelling, so the shape check reads each shape one way.

What the binder does refuse needs the parsed tree, the declared types or the bind context:

  • A cast over a decision. A cast the user wrote and a cast the binder inserted are the same bound node, so authorship is visible only on the parsed tree (casts).
  • A volatile function. Later stages read a clause more than once, so one random() would select different rows each time.
  • An OR between constraints, and a comparison read as a number (x <= (x > 1)): both need an indicator no layer builds.
  • A column of an outer query. A DECIDE solves one problem; solving it again for each outer row is not built.

One refusal moved out of the binder: <, > and <> over fractional values. Each is modeled by stepping the bound one whole unit (< K becomes <= K - 1), which is exact only on whole numbers. The shape check judges it on the canonical left side, so it sees the comparison whichever way the user wrote it (5 > SUM(x)). The rule reads declared types, never rows, so a query's validity follows from the query and the schema, not from the data it happens to hold.

SELECT item, x FROM Items DECIDE x(REAL) SUCH THAT SUM(x) < 5 MAXIMIZE SUM(value * x)

A refusal quotes the clause as typed. Each bound node keeps the query location of the parsed node it comes from (DecideBinder::PreserveQueryLocation), and DecideWrittenSql cuts the user's text at that location. A function is named as typed: count(*), not DuckDB's internal count_star.

The logical plan

The plan holds the decision query as one operator, LogicalDecide, above the scans and filters of its rows. The node carries everything the binder and the canonicalizer decided, and the name of a solver, never a solver.

Where the node sits

LogicalDecide sits above the scans, joins and filters of the query, so the solver only ever sees rows that survive WHERE. A projection above it computes the select list and drops the columns of the auxiliary variables the optimizer adds.

SELECT S.shipmentID, ship FROM Shipment S JOIN Depot D USING (depotID) WHERE D.country = 'US' DECIDE ship(INT) SUCH THAT ship <= S.demand AND ship <= 0.20 * SUM(ship) MAXIMIZE SUM(ship)

The WHERE filter has no operator of its own: DuckDB pushes it into the scan of Depot. The node's output is its child's columns plus one column per decision, auxiliaries included (GetColumnBindings), because the constraints refer to them by binding. A filter written above a DECIDE stays above it: join ordering treats the node as one relation, so a parent's filter never moves into the rows the problem is defined over.

Subquery provenance

DuckDB's PlanSubqueries flattens each scalar subquery into a join. After that, a column that varies by row, an uncorrelated subquery and a correlated one all look alike: each is a plain column reference. Yet DECIDE treats them differently. An uncorrelated subquery is one value for the whole query, and may scale a reducer in the objective; a column that varies by row may not. So Binder::PlanDecide (src/planner/binder/query_node/plan_decide.cpp) records the difference while it is still visible:

  1. Collect. Every scalar subquery in the constraints and the objective, split by IsCorrelated(). It holds the slot, not the node, since flattening replaces the node in place.
  2. Flatten. PlanSubqueries.
  3. Read back. What each slot became, recorded as an entry of computed_values: the value a clause reads, and whether it is one value for the whole query. A read of the value equals its entry wherever a rewrite copies it, so the fact survives copies.
  4. Canonicalize. The constraints and the objective, then the shape check (the canonicalizer).

The canonicalizer reads the allow-list: a factor on a reducer in the objective must be one value for the whole query. An uncorrelated subquery passes:

SELECT item, x FROM Items DECIDE x(INT) SUCH THAT x <= 3 AND SUM(weight * x) <= 50 MAXIMIZE (SELECT max(value) FROM Items) * SUM(x)

A column fails, and so does a correlated subquery. The message quotes the subquery as the user wrote it. The entry of a correlated subquery changes no decision; it lets a message about a bound that holds one print the number instead of SUBQUERY, the internal name of the flattened join:

SELECT item, x FROM Items DECIDE x(INT) SUCH THAT x <= 3 AND SUM(weight * x) <= 50 MAXIMIZE (SELECT max(I.value) FROM Items I WHERE I.category = Items.category) * SUM(x)

The canonicalizer copies the constraint tree, and a bound subquery cannot be copied. So the DECIDE block makes PlanSubqueries flatten every subquery at once, even inside another flattening, where DuckDB would otherwise defer it. Without that, a subquery inside a nested DECIDE would fail.

The ways in after planning

The constraints are a list of records, one per row of SUCH THAT, and no expression joins them. After planning, the list and the objective change only through three methods. Appending a record or assigning the objective directly would skip canonicalization and its checks.

  • AddClause canonicalizes and verifies a new record, then appends it.
  • CanonicalizeClause does the same for a record a pass rewrote where it sits. Each reads one record, so a rewrite costs the clause it changes and never the whole list.
  • SetObjective canonicalizes and verifies the replacement. The constant it peels off is added to objective_constant_offset, not assigned, so the constant the user wrote survives every rewrite.

The optimizer adds every constraint it writes through AddClause, sends every constraint it changes through CanonicalizeClause, and every objective through SetObjective. With the call in Binder::PlanDecide, these are the only places the canonicalizer runs (one shape boundary).

What the node carries

Grouped by who writes it:

Binder
The decisions and their is_boolean_var flags, the clause records, the sense, the objective, each decision's scope, the key table (keys), the key scopes, and the text of the clause (source_text, a DecideSourceText). Planning adds computed_values, the values of the flattened subqueries, and, right after canonicalization, the variant signatures (signatures): what each scoped clause or reducer reads that its key does not fix, so execution makes one instance per variant.
Canonicalizer
objective_constant_offset, and each clause's shape.
Optimizer
The solver's name, the constructs it states natively, the number of auxiliary variables, the table of constructs the rewrites kept (helper_definitions), the labels of auxiliary variables, an account of each rewrite, and the value checks.

The solver is named, not held. The optimizer settles which backend runs the query, and the plan carries the answers: solver_backend_name, use_native_constructs and force_native_constructs. A live solver handle would let a logical plan open a solver session, which is the solver stage's job. A name cannot: execution turns it back into a backend with a registry lookup, where the solve runs.

One list of expressions. LogicalDecide::EnumerateExpressions visits every field that holds an expression execution evaluates: the decisions, the computed values, the clauses, the objective, the key table, the frames, the signatures, the bodies in helper_definitions, the value checks and the reducers the bounds read. DuckDB's column pruning and binding resolution walk that list, so a key column only a declaration names (per region: x) stays in the scan, and every field gets chunk positions. A field missing from the list would read a logical index as a chunk position, an error a single-table query hides and a join reveals.

Serialization

LogicalDecide serializes through DuckDB's generator. Its fields are listed in logical_operator.json, the structs they hold (DecideKey, KeyedScopeInfo, ConstraintSourceInfo, DecideSourceText and others) in nodes.json, and scripts/generate_serialization.py writes both directions. There is no hand-written copy that could drift. Property ids are a running checkpoint, not keys: the reader expects the next field in the stream to be the one it reads, so write order and read order come from one list. A retired field stays in the list marked "deleted": true.

The wire carries bound plans only. LogicalDecide::optimized is set before the optimizer's first rewrite, and from that point SupportSerialization() returns false. The optimizer chooses a formulation for this host's solver, so an optimized plan is an answer for one machine. It declines to be copied rather than arrive elsewhere as a formulation that machine cannot run; the optimizer rebuilds it from the canonical tree wherever the plan lands.

PRAGMA verify_serializer round-trips the bound plan and replaces the live plan with the copy, so a field that never reaches the wire becomes a wrong answer, not a silent omission. Run over the whole suite, it guards every field with no per-field test:

DECIDB_VERIFY_SERIALIZER=1 make decide-test
