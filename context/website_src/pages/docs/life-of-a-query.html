The query

A bag holds at most 40 kg, and it may take at most one item of each category. Which items give the most value?

The table is the Guide's five items: three tech items and two gear items, each with a value and a weight.

SELECT item, category, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND per category: SUM(x) by (category) <= 1 MAXIMIZE SUM(value * x);

The answer is the Laptop and the Lens: 32 kg and a value of 175. Each clause pulls against another. Without the category limit the best bag is the Camera and the Drone, worth 180, but both are tech. Without the weight limit it is the Drone and the Lens, worth 195, but they weigh 42 kg.

The query is small enough to follow by hand, with 5 rows, 5 solver variables and 3 constraints, and it reaches every stage. It has a product of data and a decision (x * weight), a scope in front of a clause (per category:), a reducer with its own group (SUM(x) by (category)), and an objective to maximize.

The order of this page

Stages 01 to 05 run while DuckDB prepares the statement. Stage 08 runs when it executes, and stages 06 and 07 run inside it. The sections below follow time, so stage 08 appears twice: once before the model is built, and once after the solver answers.

01 Parser

The parser cuts the text into tokens, matches them against the grammar, and moves the clause onto DuckDB's parsed SELECT. It decides no shape and refuses nothing here.

The lexer reads DECIDE and sets its DECIDE flag. From that point it reads three words of this query as follows:

WordTokenWhy
perPER_DECIDEThe flag is set, and the next token, category, is neither ( nor ROW
byBY_DECIDEIt follows the ) of SUM(x)
BOOLan ordinary nameA decision's type is a name the grammar reads as INT, REAL or BOOL, not a keyword

The grammar then matches the clause. x(BOOL) is a typed declaration: one decision per result row. The two constraints are separated by the top-level AND, and per category: scopes only the second, because the colon ends the scope and a constraint body binds more tightly than AND. The scope becomes part of its constraint's item, and SUM(x) by (category) becomes a reducer node that holds its by key.

The transformer builds one ParsedDecide on DuckDB's SelectNode, in its one new field, decide. It holds variables (the one declaration), constraints (a list of two DecideClause records, the second with the scope per category), sense (MAXIMIZE), objective, and text, the clause as typed with one span per expression. That text is what every later message and the EXPLAIN output quote. SUM(x) by (category) becomes a DecideReducerExpression, a parsed expression that holds the call and its by key.

02 Binder

The binder resolves every name to a column, a decision or a key, and records what each decision is.

DuckDB binds FROM Items as it binds any table. Its SELECT binder then makes its one DECIDE call, DecideDeclarationsBinder::BindDeclarations, which binds the clause in three steps:

  1. The declaration. x is not a column of Items and is declared once, so it is registered as decision 0. It has no per, so its scope is one value per row. Its type is INTEGER, and a flag marks it as boolean. No x >= 0 or x <= 1 constraint is ever written for that: the 0 to 1 range travels as the flag, and the model builder sets it as the variable's bounds.
  2. The constraints. In x * weight, x binds to the decision and weight to the column. Each constraint becomes a record, a BoundDecideClause. The per category: scope becomes fields of the second record: its per, and the entry of category in the query's key table. SUM(x) by (category) becomes a reducer node whose by field names an entry of the same table. Both keys list the same column, so they share one entry: one key, written twice.
  3. The objective. It has no scope written, so it is produced once for the whole query, the default per ().

Each bound node keeps the location of the text it came from, so a message about it can quote the user's words. Nothing is refused: no decision appears in WHERE, a key or a by. The algebra of each clause, such as its degree, is not judged here. That waits for stage 04, after the clause has one spelling.

03 Logical plan

The planner builds LogicalDecide above the scan, so only rows that survive FROM and WHERE become decisions.

Binder::CreatePlan plans a SELECT bottom up: the scan, then any WHERE filter, then the DECIDE node, then grouping, HAVING, windows and the final projection. That order is the language's meaning in operator form. WHERE runs first and cannot read a decision; everything after the DECIDE node reads the decisions as columns.

CreatePlan builds the DECIDE node by calling Binder::PlanDecide, right after the WHERE. This query has no subquery in its clauses, so its first job, flattening each subquery into a join and recording whether it is correlated, finds nothing. Before it builds the node, it hands both clauses to stage 04. The node it builds holds the canonical clauses. The plan DuckDB runs has the same shape:

SELECT item, category, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND per category: SUM(x) by (category) <= 1 MAXIMIZE SUM(value * x);

The projection on top keeps the three columns the query selects. Had a rewrite added auxiliary variables, the same projection would drop their columns. With a WHERE clause, DuckDB pushes the filter into the scan, still below the DECIDE node.

After planning, a clause can enter or change in LogicalDecide only through AddClause, CanonicalizeClause or SetObjective. All three canonicalize what they receive, so no later stage can leave a clause in a shape stage 04 did not write.

04 Canonicalizer

The canonicalizer writes each clause in one shape: decisions on the left, the bound on the right, each product with its coefficient first. Then it names how each clause becomes model rows.

EXPLAIN prints the result. Each clause appears as written; a line marked ≡ follows when the canonical spelling differs.

SELECT item, category, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND per category: SUM(x) by (category) <= 1 MAXIMIZE SUM(value * x);

Clause by clause:

  • SUM(x * weight) <= 40 becomes sum(weight * x) <= 40. Every product is written as its coefficient times its decisions, so the later stages read one spelling. The decision side already sits on the left and the bound on the right, so nothing moves.
  • per category: SUM(x) by (category) <= 1 is already canonical, so it has no ≡ line.
  • The objective is written coefficient first, so it has no ≡ line either. Inside, it changes: every stage after this one reads a minimization, so as its last step the canonicalizer negates each term's sign, making MAXIMIZE sum(value * x) into MINIMIZE -sum(value * x). The node keeps the sense the user wrote for messages and for EXPLAIN, which prints the objective in that sense.

Then the canonicalizer names each comparison's shape, the rule for how many model rows it makes. Both constraints have the aggregate shape: the decision side is a reducer, so the clause makes one row per by group of the rows it keeps. The weight limit has no by, which means by (): one group, one row. The category limit groups by category: two groups, two rows. Its per category: adds no row of its own. One row per by group already stands for every class, so the scope only names the classes each row stands for, which DIAGNOSE reads to report one class at a time.

Two more steps run here:

  • Variant signatures. Under per category:, the canonicalizer records what the clause reads that the key does not fix. A value that can differ within one class, such as a column of each row, makes one constraint per variant: per distinct value in the class. The bound 1 is a literal, and the by key is the key's own column, so the clause records nothing: one constraint per class.
  • The shape check. It judges the algebra of each clause on the canonical spelling: every function over a decision must be one the model can state, and every term must have degree 2 or less. Here every term has degree 1.

05 Optimizer

The optimizer decides how the query is answered: by a rewrite into DuckDB operators, or by a solver. For a solver, it then decides how each construct is written.

DuckDB runs its own passes first, among them the expression rewriter and filter pushdown. Then DecideOptimizer visits each LogicalDecide:

  1. Data bounds. A reducer over data on a bound's side, as in SUM(x) <= SUM(cap), becomes a column the plan computes once. Both bounds here are literals.
  2. The answer. The node is offered to every rewrite rule, and each reads its clauses through shared reader functions. None applies: the weight limit makes this a knapsack with group limits, a problem no built rule proves. So the query stays on the solver's path.
  3. The solver. The backend is chosen once, here: Gurobi when its library and license are present, otherwise HiGHS. The choice and what that backend can state natively are recorded on the node, and every later stage reads them instead of asking again.
  4. The formulation passes. They always run in the same order: a range frame over decisions, norm, IN, bilinear products, the cheap direction of MIN and MAX, the value rewrite (which also takes every other MIN and MAX), <>, AVG, ABS, the folding of a literal bound on one variable into that variable's bounds, and last the form of each helper decision. Each finds nothing to do here, so the node leaves the optimizer as it entered.

Asking for a rewrite shows the second step's answer. The setting decide_direct_solve='require' makes a query fail when no rule applies:

SET decide_direct_solve = 'require'; SELECT item, category, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND per category: SUM(x) by (category) <= 1 MAXIMIZE SUM(value * x);

Remove the weight limit and rule S1 applies: the best item per category is a ranking, and the overview shows that plan.

Into a physical plan

When DuckDB turns the logical plan into a physical one, src/execution/physical_plan/plan_decide.cpp does three things before it builds PhysicalDecide:

  1. Verify. It refuses a plan the DECIDE optimizer never saw, since a plan without a chosen backend cannot be answered. A debug build also checks that every clause is still canonical after all rewriting.
  2. Lower. One walk, DecideTreeConstruction, builds the clause tree: the tree of nodes execution evaluates, one for each scope, reducer, frame and helper function. From the same clauses it runs stage 05's last step, the linear form, which writes each clause into its node as terms: a decision, a coefficient expression, and a sign. The weight limit is one term, x with coefficient weight. The category limit is one term, x with coefficient 1, grouped by category. The objective is one term, x with coefficient value and sign -1. It runs here, not earlier, because DuckDB's later passes move columns, and this is the first point where the input columns are final.
  3. Gate. It checks the model class this query needs against the chosen backend. This is a linear model with integer variables, which every backend takes. A quadratic constraint on HiGHS would be refused here, before any row is read.

08 Execution: buffer and evaluate

PhysicalDecide reads every row before it can answer, then evaluates the clause tree once, over all rows.

Sink. The scan sends its rows in chunks. Sink appends each chunk to a ColumnDataCollection, DuckDB's in-memory buffer of rows. After the last chunk it holds five rows:

Rowitemcategoryweightvalue
0Laptoptech20100
1Cameratech1060
2Dronetech30120
3Tripodgear1540
4Lensgear1275

Finalize runs once, after the last row, in phases:

  1. Descent. One pass reads the buffer from the top of the clause tree, a chunk at a time. Each node keeps what it reads on the rows that reach it: the category limit's node keeps each row's category, so it can group the rows by it.
  2. Node columns. Each node is then computed from its children, bottom up. Its coefficient expressions run over its entries as columns, with DuckDB's expression executor. The weight limit reads weight: 20, 10, 30, 15, 12. The category limit assigns each row its by group: two groups. The objective reads value with the sign applied: -100, -60, -120, -40, -75. Every value is finite, so no row is refused.
  3. Model emitter. It writes the classes of each keyed decision, the clauses and the objective into a SolverInput, the form stage 06 reads. x is one per row, so there are no classes.
  4. Assembly. A VarIndexer lays out the solver's columns. It has four blocks: decisions per row, keyed decisions, query-wide decisions, and auxiliaries. Here only the first is used: one decision over five rows is five columns, numbered as the rows are.
  5. Lowering. Constructs stage 05 marked for Big-M or similar rows get their constants here, from the data. There are none.

The evaluation does not read the buffer again. What follows works on numbers until the answer is read back.

06 Model

The model builder turns the evaluated clauses into the matrix a solver loads: columns with bounds, rows with coefficients, and an objective. It names no solver.

SolverModel::Build walks each clause. A clause of the aggregate shape emits one model row per group: the weight limit emits one row over all five columns, the category limit one row per category. Each term here names a decision that is one per row, so no two data rows share a solver column, and each coefficient is copied into its row as it is. A keyed decision would put many data rows on one column, and their coefficients would be summed first.

Each column's bounds come from the decision's type. BOOL gives 0 to 1 and marks the column binary. The environment variable DECIDB_DUMP_MODEL prints the model exactly as it is handed to the backend:

SELECT item, category, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND per category: SUM(x) by (category) <= 1 MAXIMIZE SUM(value * x)

Read it against the buffer. Columns 0 to 4 are the rows Laptop to Lens. The objective is a minimization of the negated values. Row 0 is the weight limit. Row 1 is the gear group (Tripod and Lens) and row 2 the tech group. There are no quadratic rows (num_qrows), no general constraints such as a native MAX (num_genconstrs), and no indicator constraints. Gurobi and HiGHS receive the same model for this query, since it uses nothing either one states natively.

Each row also carries its provenance: the clause it came from and the group it stands for. DIAGNOSE reads it to name the clause a repair changes.

07 Solver

The solve facade hands the model to the backend stage 05 chose and returns one status, whichever backend ran.

SolveModel builds the model, checks that it fits what the planned backend declares it can take, and loads it. Gurobi is loaded from its shared library at run time; HiGHS is compiled into DeciDB. Each backend's status is mapped to one SolverStatus, so no code above this stage branches on which solver ran.

Here the status is OPTIMAL, with the solution 1, 0, 0, 0, 1 and the objective -175: the value of the minimization, which is 175 in the sense the user wrote. Check it by hand. The Laptop and the Lens weigh 20 + 12 = 32 kg, within 40, and take one item from each category. No other bag within both limits is worth as much.

Had the status been infeasible or unbounded, a plain query would stop here with an error naming the state. Under DIAGNOSE, the router would send it to an engine instead (DIAGNOSE).

08 Execution: the answer as rows

The operator scans its buffer again and appends each decision's value to its row.

GetData reads the buffered rows chunk by chunk. For each row and each decision, the VarIndexer names the solver column that holds its value: here column i for row i. For a keyed decision, every row of a class reads the same column, so they show one value.

A BOOL decision's result type is INTEGER, so each value is rounded to a whole number and checked against the type's range before it is written. A solver returns 0.9999999 as readily as 1; the rounding makes the column exact. The projection above the node then keeps item, category and x, and the rows at the top of this page are the result.
