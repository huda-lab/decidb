Query rewriting

Some optimization problems have an exact answer that sorting, ranking and running totals can compute. When DeciDB recognizes one, it rewrites the query into those operations and never starts a solver. You write the same SQL; it returns sooner.

Faster, exact, and no license needed

A fair allocation over 800,000 decisions takes 0.026 s rewritten, against 2,158 s in Gurobi. Rewriting beat Gurobi in every benchmark but one, a budget problem at 100,000 rows, where it took about 10% longer. The answer is exact, with no solver tolerance, and a quadratic class needs no Gurobi license.

A query DeciDB cannot prove to be one of these shapes goes to the solver unchanged, so rewriting never changes what a query means.

How to tell

Nothing in the query marks it. EXPLAIN shows whether it was rewritten and by which rule (the engine's name for the feature is "direct solve"):

SELECT program, alloc FROM Programs DECIDE alloc(REAL) SUCH THAT alloc <= max_alloc AND SUM(alloc) <= 100 MAXIMIZE MIN(alloc / need);

Which queries are rewritten

Nine shapes today. The rule is the name EXPLAIN prints.

Three of them in full:

SELECT good, value_per_kg, available_kg, ROUND(kg, 1) AS kg FROM Cargo DECIDE kg(REAL) SUCH THAT kg <= available_kg AND SUM(kg) <= 1000 MAXIMIZE SUM(value_per_kg * kg);

The truck takes the most valuable goods per kilogram first, until it is full.

SELECT sku, margin, min_qty, max_qty, qty FROM Orders DECIDE qty(INT) SUCH THAT qty BETWEEN min_qty AND max_qty MAXIMIZE SUM(margin * qty);

Each quantity goes to whichever end of its range its margin favors.

SELECT name, score, ROUND(x, 3) AS x FROM Signals DECIDE x(REAL) SUCH THAT SUM(POWER(x, 2)) <= 25 MAXIMIZE SUM(score * x);

x points along the scores, scaled to the limit: with scores 3, 4 and 0 and a limit of 25, it answers 3, 4 and 0.

Turning it off

SettingEffect
SET decide_direct_solve = 'auto'the default: rewrite when DeciDB can prove the shape
SET decide_direct_solve = 'off'always use the solver
SET decide_direct_solve = 'require'stop with an error when no rule applies

When several answers are equally good, the rewritten query may return a different one than the solver would; the objective is the same.

How DeciDB proves a query's shape and builds the plan that replaces the solver is in How it works: query rewriting and the rewrite rules.

DIAGNOSE

A query with no answer usually has one rule that is too tight. Put DIAGNOSE in front of it and DeciDB tells you which clause to change and by how much.

This bag must weigh 40 kg or less and hold at least four items, and no four items are that light:

SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND SUM(x) >= 4 MAXIMIZE SUM(x * value);

The same query with DIAGNOSE in front returns what to change instead of the rows:

DIAGNOSE SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND SUM(x) >= 4 MAXIMIZE SUM(x * value);

Reading the answer

Each row is one finding. Raise the weight limit from 40 to 57 and the query has an answer; the row marked achievable_objective gives the value you would then get.

A query that already has an answer returns one row with state = 'feasible'. To get one suggestion per row or group instead of per clause, SET diagnose_decide_infeasible_slack_scope = 'expanded'; group and row then say which. The result is a table like any other, so a query can filter it:

SELECT clause, suggested_change, amount FROM (DIAGNOSE SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND SUM(x) >= 4 MAXIMIZE SUM(x * value)) WHERE edit_source = 'source_literal';

DIAGNOSE takes a query with exactly one DECIDE. A query that fails before it is solved, from a syntax error to a model the installed solver cannot take, stops with the same error as without DIAGNOSE. It costs nothing until you write it, and it always uses a solver.

No limit on the objective

When nothing stops the objective from growing forever, the query stops and DIAGNOSE names the decision that needs a limit, with how many of its values escape. The DIAGNOSE example shows the full answer for the bag above.

How DeciDB finds the smallest change is in How it works: inside DIAGNOSE.
