New per, when and by: the new DECIDE language

Constrained optimization, native in SQL

DeciDB extends DuckDB with a DECIDE clause. Declare the decisions to make over your rows, state the rules they must follow and what to optimize, and get the optimal rows back from one query. No export, no solver code.

Why in the database

The decision is a query, not a pipeline

Choosing which products to stock, how much to ship or whom to schedule usually means exporting rows, writing a model in Python and copying the answer back. With DeciDB the model is the query: the rows are already there, and the answer comes back as rows.

import duckdb, pulp rows = duckdb.connect("shop.db").execute( "SELECT item, value, weight FROM Items").fetchall() prob = pulp.LpProblem("bag", pulp.LpMaximize) x = {r[0]: pulp.LpVariable(f"x_{r[0]}", cat="Binary") for r in rows} prob += pulp.lpSum(x[r[0]] * r[1] for r in rows) prob += pulp.lpSum(x[r[0]] * r[2] for r in rows) <= 50 prob.solve() chosen = [r[0] for r in rows if x[r[0]].value() == 1] # ... and now write `chosen` back to the database SELECT item, value, weight, x AS take FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 50 MAXIMIZE SUM(x * value);

The language

Three words say which rows a rule covers

Most real constraints are about groups: each depot's capacity, each customer's demand, each sector's limit. DeciDB writes them with three keywords that each do one job.

per
How many?

One decision or one constraint per distinct value of a key. per () means exactly one.

DECIDE per D: open(BOOL)
per D: SUM(ship) by (D) <= D.capacity
when
Which rows?

Only the rows where a condition holds, in front of a constraint, the objective or inside one sum.

when S.priority: ship >= 1
SUM(when S.priority: ship) <= 40
by
Which rows does this sum read?

After a reducer: read only the rows that share the current row's value of a key.

SUM(ship) by (D.region)
ship <= 0.25 * SUM(ship) by (D.depotID)

One constraint per depot, each comparing the depot's capacity with the shipments of its whole region. per and by name different keys, so the rule generates per depot but reads per region:

per D.depotID: SUM(ship) by (D.region) <= D.capacity

The three constraints it writes:

D1x1 + x2 + x3 ≤ 100
D2x1 + x2 + x3 ≤ 80

D1 and D2 are both in the North, so both read all North shipments. A per key must determine every value the rule reads once per class, here D.capacity and D.region. DeciDB checks this on the data before solving.

What you can express

From a knapsack to a fair split

You never name the problem class. DeciDB reads it from the decision types and the shape of the terms, and picks a formulation the solver can take.

{{icon:layers}}

Keyed decisions

One decision per depot, per customer or per anything, shared by every joined row of that key.

DECIDE per D: open(BOOL), ship(INT)
{{icon:target}}

Query-wide decisions

A single value for the whole query: a threshold, a shared ceiling, the worst-case shortfall.

DECIDE ship(INT), per (): worst(INT)
{{icon:layers}}

Min-max objectives

An inner sum per group and an outer max over the groups: balance load, minimize the busiest machine.

MINIMIZE max(per m: sum(h * x) by (m))
{{icon:target}}

Max-min fairness

Make the worst-off row as well off as possible with MIN or MAX in the objective.

MAXIMIZE MIN(alloc / need)
{{icon:search}}

Norms and sparsity

L1, squared L2, L∞ and the L0 count of nonzeros, as a constraint or in the objective.

norm(new - old, 0) <= 2
{{icon:cpu}}

Quadratic and bilinear

Least squares, convex QP, quadratic constraints and products of two decisions.

MINIMIZE SUM(POWER(w - target, 2))

Direct solve

Some problems never reach a solver

Many everyday problems have an exact answer that ordinary relational operators can compute: take the top k per group, fill a budget by value per unit, match two sorted lists. DeciDB proves when a query has one of these shapes and answers it with DuckDB's sort, window and aggregate operators. Nothing in the query changes.

  • Nine problem classes today, each faster than Gurobi at every size measured.
  • Exact answers, without the solver's tolerance.
  • EXPLAIN names the rule; SET decide_direct_solve = 'off' turns it off.

SELECT title, genre, rating, pick FROM Films DECIDE pick(BOOL) SUCH THAT per genre: SUM(pick) by (genre) <= 2 MAXIMIZE SUM(rating * pick) ORDER BY genre, rating DESC;
DIAGNOSE SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND SUM(x) >= 4 MAXIMIZE SUM(x * value);
DIAGNOSE

When the rules can't all hold, DeciDB says which one to move

Prefix an infeasible or unbounded query with DIAGNOSE. It returns the smallest edit to the clauses you wrote, quoted as you wrote them, and the objective you would get after the edit. The answer is a relation, so you can filter and join it like any other.
