Overview

DeciDB answers questions like "which rows, and how much of each, so that these rules hold and this goal is as good as it can be?" You ask them in SQL.

Take a table of items, each with a value and a weight. Which items should go in a bag that holds 50 kg, to carry the most value?

SELECT item, value, weight, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 50 MAXIMIZE SUM(x * value);

DeciDB takes the laptop, camera and lens: 42 kg, worth 235. The query has the three clauses this guide covers, in this order:

ClauseWhat it saysIn this query
DECIDEwhat DeciDB chooses: the decisionsa yes-or-no value x for each item
SUCH THATthe rules a choice must follow: the constraintsthe chosen items weigh 50 kg or less
MAXIMIZEwhat makes one choice better than another: the objectivethe most total value

In the code on this site, the words DECIDE adds to SQL are in purple, and each query's decisions, such as x, are in pink.

How a query runs

  1. The rows. FROM, joins and WHERE run first, as in any query. Their rows are the rows DeciDB makes decisions about.
  2. The model. DeciDB adds each decision as a column and turns SUCH THAT and the objective into an optimization model over those rows.
  3. The answer. It solves the model and fills in every decision with its best value.
  4. The output. SELECT and ORDER BY run last and see the decisions as ordinary columns.

The full shape

SELECT columns FROM tables [JOIN ...] [WHERE ...] DECIDE [per key:] name(type) [, ...] SUCH THAT [[when condition] [per key]:] constraint [AND ...] [MAXIMIZE | MINIMIZE [when condition:] expression]

Square brackets mark optional parts. SUCH THAT is required; the objective is not. A when or per in front of a constraint ends with a colon. DECIDE may also come between SELECT and FROM, the order the DeciDB paper uses; both orders mean the same. Inside these clauses when, per and by are keywords, so a column with one of those names is quoted there: x <= "per".

1. DECIDE: the decisions

A decision is a value DeciDB chooses for you. Declare each one with a name and a type.

TypeValuesUse it forReturned as
x(BOOL)0 or 1pick or skip, open or closedINTEGER
x(INT)0, 1, 2, …units, people, trucksBIGINT
x(REAL)any number from 0 upamounts, shares, pricesDOUBLE

Decisions start at zero. A constraint such as x >= -10 or x BETWEEN -5 AND 5 lets an INT or REAL decision go below it.

One per row, one per key, or one in all

A decision is made once per result row unless you say otherwise. per in front of the declaration shares one decision across rows:

WriteDecisionsFor example
ship(INT)one per result rowhow much each shipment carries
per D: open(BOOL)one per row of D, shared by the rows that join to itwhether each depot opens
per (): biggest(INT)exactly one for the whole querya threshold or a worst case

Separate several decisions with commas; each has its own per. Over shipments joined to the depots they leave from:

SELECT S.shipmentID, D.depotID, ship, open, biggest FROM Shipment S JOIN Depot D USING (depotID) DECIDE ship(INT), per D: open(BOOL), per (): biggest(INT) SUCH THAT ship <= S.demand * open AND ship <= biggest AND SUM(ship) >= 150 MINIMIZE SUM(S.unit_cost * ship) + SUM(per D: D.opening_cost * open) + 10 * biggest;

ship differs on every row. open repeats on every shipment of the same depot, because it is one decision. biggest is the same on every row: the largest single shipment, which the objective keeps small.

A key can be a table (per D), a column (per D.depotID) or several columns (per D.region, S.customerID). A row whose key is NULL gets no decision and shows NULL.

Using a decision

Refer to a decision by its bare name: in SUCH THAT, in the objective, and in SELECT and ORDER BY, where it is an ordinary column (x AS take, price * units AS cost).

2. SUCH THAT: the constraints

Constraints are the rules every answer must follow. Write them after SUCH THAT, joined by AND.

Rules on each row

A constraint without a sum holds on every row, each with its own values: ship <= S.demand keeps every shipment within its own demand.

Rules on totals

A constraint with a sum holds over the rows the sum reads, all of them unless you say otherwise. Besides SUM, a total can be an AVG, MIN or MAX (see reducers).

SUM(x * weight) <= 50 AND SUM(x) >= 2
Compare withNotes
<= >= =Any decision.
BETWEEN a AND bBoth bounds at once.
IN (0, 2, 3)On a decision, only those values are allowed.
< > <>Only between whole numbers: INT or BOOL decisions and integer data.

Bounds can come from the data: a column, an expression, or a subquery.

SUM(x * weight) <= (SELECT MAX(weight) * 2 FROM Items)

A bound that differs from row to row, such as SUM(x) <= cap, holds at its tightest: the smallest cap for <=, the largest for >=. With = a bound that differs is refused, since a total cannot equal two numbers.

No OR between constraints

Every constraint must hold. When an answer may follow one rule or another, that choice is itself a decision: add a BOOL that switches between them.

Only some rows: when

when in front of a constraint limits it to the rows where a condition holds. At most one tech item in the bag:

SELECT item, category, value, weight, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 50 AND when category = 'tech': SUM(x) <= 1 MAXIMIZE SUM(x * value);

A when inside a sum filters only that sum: SUM(when morning: x * hours) <= 20. A row where the condition is NULL counts as false.

One rule for each group: per and by

To write a rule once per group, per sector, per depot or per day, put per in front of it, and tell each sum which rows to read with by. At most two stocks from any sector:

SELECT ticker, sector, expected_return, risk, pick FROM Stocks DECIDE pick(BOOL) SUCH THAT SUM(pick) = 5 AND SUM(pick * risk) <= 30 AND per sector: SUM(pick) by (sector) <= 2 MAXIMIZE SUM(pick * expected_return);

The query never lists the sectors: per sector writes one rule for each sector in the data. The two words do different jobs, and most group rules need both:

  • per sector sets how many rules there are: one for each sector.
  • by (sector) sets which rows each sum reads: the rows of that sector. Without it, every rule would sum over all rows.
WrittenRulesEach sum reads
SUM(ship) <= 300oneall rows
per D.depotID: SUM(ship) by (D.depotID) <= D.capacityone per depotthat depot's rows
ship <= 0.6 * SUM(ship) by (D.depotID)one per rowthe rows of that row's depot
per D.depotID: SUM(ship) by (D.region) <= D.capacityone per depotall rows of the depot's region
SUM(ship) <= 300 AND per D.depotID: SUM(ship) by (D.depotID) <= D.capacity AND ship <= 0.6 * SUM(ship) by (D.depotID) AND per D.depotID: SUM(ship) by (D.region) <= D.capacity

Without per, a rule holds on each row, and rows that would give the same rule share one, so a rule on a total is written once. Without by, a sum reads every row. Both defaults can be written out, as the release notes do: per (): for one rule over the whole query, by () for a sum over every row. This is the first rule above, written in full:

per (): SUM(ship) by () <= 300

When a value differs inside a group

A rule written once per group may read a value that is not the same on every row of the group. DeciDB then writes the rule once for each different value. A depot has several shipments, each with its own ship, so this rule is one rule per shipment, the same as ship <= 10 on every row:

per D.depotID: ship <= 10

The North region has two depots, with capacities 100 and 80. Over that region, this rule is written once for each capacity, so the smaller one, 80, is the limit that holds:

per D.region: SUM(ship) by (D.region) <= D.capacity

To limit each depot's own total instead, sum inside the group: per D.depotID: SUM(ship) by (D.depotID) <= 10.

A reducer inside a reducer

A reducer is a function such as SUM or MAX that turns many rows into one value. One may read the results of another, to any depth. This rule takes each depot's largest shipment, then adds those up:

SUM(per D.depotID: MAX(ship) by (D.depotID)) <= 50

The inner reducer is computed once per group of its by, and the outer one adds one value per depot. SUM, AVG, MIN and MAX nest this way in rules and in the objective.

Ordered data: at and over

Some rules read another row in order, such as last week's stock. at(previous: e) over (week) reads e on the row before, with the rows ordered by week. else 0 gives the value to use where there is no row before. Here a plant can make 60 units a week, and stock carries over from one week to the next:

SELECT week, demand, make, stock FROM Weeks DECIDE make(INT), stock(INT) SUCH THAT make <= capacity AND stock = at(previous else 0: stock) over (week) + make - demand MINIMIZE SUM(make * make_cost + 0.25 * stock) ORDER BY week;

Weeks 2 and 4 need more than 60, so the plant makes extra ahead of them and keeps it in stock. It makes the stock for week 4 in week 3, not in the cheaper weeks 1 and 2, because those already run at capacity.

WriteReads
at(2 previous: e), at(next: e)e two rows before, or one row after
at(first: e), at(last: e)e on the first or the last row
SUM(from first to previous: e)every row from the first to the one before; AVG, MIN and MAX work too, and COUNT over data
SUM(from first to last every 2: e)every second row
SUM(from previous to next all: e)nothing at all when one of those rows is missing
over (week desc)the rows in reverse order
over (week cyclic)the rows in a circle: the row before the first is the last
over (week within product)each product's rows in their own order

Where the row a frame reads does not exist and there is no else, the frame has no value, and the rule is skipped on that row, as for a NULL. A range reads the rows that exist. Any three weeks in a row, with the last week followed by the first, make at least 150:

SUM(from previous to next: make) over (week cyclic) >= 150

One frame reads at most 10,000,000 values; SET decide_frame_limit changes that.

3. MAXIMIZE and MINIMIZE: the objective

The objective says which answer is best. DeciDB returns the answer that makes it as large (MAXIMIZE) or as small (MINIMIZE) as the constraints allow.

MAXIMIZE SUM(x * value) -- the most value MINIMIZE SUM(S.unit_cost * ship) -- the lowest cost MAXIMIZE when S.priority: SUM(ship) -- the most shipped, counting priority rows only

A query has one objective, computed once over all its rows. when in front of it limits the rows it reads. A value it reads outside a sum must therefore be the same on every row: MAXIMIZE SUM(x) + cap is refused when cap differs between rows.

Costs counted once

Over a join, a depot's opening cost appears on every shipment row of that depot, so SUM(D.opening_cost * open) would count it once per shipment. SUM(per D: e) counts it once per depot:

SELECT S.shipmentID, D.depotID, open, ship FROM Shipment S JOIN Depot D USING (depotID) DECIDE per D: open(BOOL), ship(INT) SUCH THAT ship <= S.demand * open AND SUM(ship) >= 120 MINIMIZE SUM(S.unit_cost * ship) + SUM(per D: D.opening_cost * open);

Keep e to the depot's own values. If it also reads something that differs between a depot's shipments, such as S.unit_cost or ship, the sum counts one term for each different value, as a group rule does.

The worst case

To balance work, make the largest load as small as possible. max(per M.machine: ...) takes each machine's total, then the largest of them:

SELECT M.machine, J.job, run FROM Jobs J CROSS JOIN Machines M DECIDE run(BOOL) SUCH THAT per J: SUM(run) by (J) = 1 MINIMIZE max(per M.machine: SUM(run * J.hours) by (M.machine)); -- the busiest machine

The reverse, MAXIMIZE MIN(...), raises the worst-off row: see fair allocation.

Distances and changes

norm(e, p) measures how far a set of values is from where it was: p = 1 the total change, 2 the sum of squares, 'inf' the largest change, 0 the number of values that changed. Raise revenue while changing at most two prices, by as little as possible:

SELECT item, price, new_price FROM Menu DECIDE new_price(REAL) SUCH THAT new_price BETWEEN floor AND ceiling AND SUM(new_price * weekly_qty) >= 16500 AND norm(new_price - price, 0) <= 2 -- at most two prices change MINIMIZE norm(new_price - price, 1); -- smallest total change

No objective

Leave the objective out to ask for any answer that follows every rule, such as a shift rota where every shift has one nurse and no nurse works twice:

SELECT nurse, shift, on_duty FROM Availability DECIDE on_duty(BOOL) SUCH THAT per shift: SUM(on_duty) by (shift) = 1 AND per nurse: SUM(on_duty) by (nurse) <= 1 ORDER BY shift, nurse;

The result

A DECIDE query returns rows like any query, with every decision filled in. You can join it, filter it, or use it in a larger query.

When there is no answer

If no choice can satisfy every constraint, the query stops with an error that says so:

SELECT item, x FROM Items DECIDE x(BOOL) SUCH THAT SUM(x * weight) <= 40 AND SUM(x) >= 4 MAXIMIZE SUM(x * value);

Put DIAGNOSE in front of the query to see which clause to change and by how much. A query whose objective could grow forever stops the same way, and DIAGNOSE names the decision that needs a limit.

Warnings

Some queries run as written but may not do what you meant. DeciDB answers them and prints a warning on the error stream:

  • a rule left with nothing to constrain, because the value it reads is missing on every row: DECIDE warning: 'make <= at(5 previous: make) over (week)' constrains nothing: each of its 4 instances has no value, so each is skipped.
  • an objective that is 0 whatever the decisions, such as a sum whose weights are all zero or NULL, so any answer that follows the rules is the best;
  • a very large or very small number, such as 1e10, which can make the answer inaccurate.

A query answered by query rewriting prints none of them.

A long solve

Each solve stops after 300 seconds; the environment variable DECIDB_TIME_LIMIT sets another limit, in seconds. When the limit is reached, DeciDB reports how far the solver got. At a terminal it then offers to keep solving (Enter) or to stop with the best answer so far (s); anywhere else, such as Python or a script, the query stops with an error. Ctrl-C returns the best answer found so far, marked as not proven best, or an error if there is none yet. SET decide_mip_gap = 1e-4 accepts an answer within 0.01% of the best one, which is often much faster.

Solvers

You never name a solver or a problem type. DeciDB works out the type from your decisions and clauses and picks a solver that can take it.

The bundled HiGHS solver needs no setup. When the Gurobi library and a license are present, DeciDB uses Gurobi instead: it is faster on these models and takes a few that HiGHS cannot (setting up Gurobi).

Your query hasTypeHiGHSGurobi
REAL decisions, sums and boundsLPyesyes
some INT or BOOL decisionsILP, MILPyesyes
no objectivefeasibilityyesyes
MINIMIZE a sum of squares, REAL decisionsconvex QPwhen each square reads one decision and has a fixed weightyes
a sum of squares with INT or BOOL decisionsMIQPnoyes
MAXIMIZE a sum of squares, or a product x * y of two decisionsnon-convex QPnoyes
a square or a product inside SUCH THATQCQPnoyes

A product with one BOOL factor (b * x) is exact on both solvers when x has a finite upper bound. On HiGHS, three more forms need a finite bound on the decisions they read, written in SUCH THAT or implied by other constraints: an ABS held from below (abs(x - 5) >= 2), a <> whose value lies inside the range, and a MIN or MAX pushed the hard way (MAX(x) >= 3, MINIMIZE MIN(x)). The message names the decision that needs the bound.

A query the installed solver cannot take is refused before any row is read, with a message that ends "is not supported on this installation". Some queries need no solver at all: see query rewriting. How DeciDB builds the model and hands it to each solver is in How it works.

EXPLAIN

EXPLAIN shows the model a query builds, without solving it: the decisions, the objective, and each constraint as you wrote it.

SELECT S.shipmentID, ship FROM Shipment S JOIN Depot D USING (depotID) DECIDE ship(INT) SUCH THAT ship <= S.demand AND per D.depotID: SUM(ship) by (D.region) <= D.capacity AND abs(SUM(ship) by (D.region) - 40) <= 30 MAXIMIZE SUM(ship);

A line marked ≡ shows a clause in the form DeciDB solves, when that differs from what you wrote: 5 >= x becomes x <= 5. A line marked ↳ shows what DeciDB added to model a clause, such as a helper value for abs. A query answered by query rewriting names the rule instead. EXPLAIN ANALYZE also solves the query, and adds under a clause how many constraints its per wrote (↳ per g: 3 constraints) and how many rows it skipped for a missing value. EXPLAIN (FORMAT JSON) works too. Life of a query, in How it works, follows one query through every step DeciDB takes.

Sums and other reducers

WriteMeans
SUM(e)the total over the rows it reads
AVG(e)the total divided by the number of rows it reads
MIN(e), MAX(e)the smallest or largest value
norm(e, p)a distance: 1, 2, 'inf' or 0 (see distances)
count(*)the number of rows; count chosen rows with SUM(x)
SUM(per D: e)one term per row of table D, not per joined row (see costs counted once)
SUM(per g: MAX(e) by (g))a reducer over another reducer's results (see a reducer inside a reducer)
at(previous else 0: e) over (t)e on the row before, in the order of t (see ordered data)

SUM, AVG, MIN and MAX take by (...) after them and when or per inside; norm and count(*) take only by. A number may scale a reducer (2 * SUM(x)), and so may a BOOL decision (b * SUM(x)); an INT or REAL one may not, so write SUM(s * x). Inside a reducer, a decision may be multiplied by data or by one other decision, squared (POWER(e, 2)) or wrapped in ABS. Anything else over a decision is refused: another function such as sqrt, CASE or COALESCE, a term of degree 3 or more, a division by a decision, and a cast of one.

AVG(x * value) >= 20 AND SUM(x * weight) <= 2 * count(*) * 5

NULL values

A NULL in the data is skipped where it is read, as SQL's own aggregates skip it, never read as zero.

Where the NULL isWhat happens
in a key column of per or bythe row belongs to no group
in a when conditionthe row is left out
inside a sumthe row is skipped; AVG divides by the rows kept
in a row's own bound (x <= cap)that row has no such limit
in an objective termthe term is left out

To treat NULL as a value instead, say so: SUM(x * COALESCE(w, 0)). A NaN, or an infinite value that multiplies a decision, is an error rather than a skipped row.

Migrating from 0.2

DeciDB 0.2 wrote scopes after a constraint (SUM(x) <= 2 PER sector) and tied declarations to a table (T.x(INT), scalar x(INT)). Scopes now go in front, and a sum says which rows it reads with by. Each old spelling now stops the query with an error before it runs, most of them a syntax error:

SELECT ticker, pick FROM Stocks DECIDE pick(BOOL) SUCH THAT SUM(pick) <= 2 PER sector MAXIMIZE SUM(pick * expected_return);
Old spellingWrite instead
DECIDE T.x(INT)DECIDE per T: x(INT)
DECIDE scalar x(INT)DECIDE per (): x(INT)
SUM(x) <= 2 PER gper g: SUM(x) by (g) <= 2
SUM(x) >= 2 WHEN cwhen c: SUM(x) >= 2
SUM(x * h) WHEN c inside an expressionSUM(when c: x * h)
MAXIMIZE SUM(e) WHEN cMAXIMIZE when c: SUM(e)
MINIMIZE MAX(SUM(e)) PER gMINIMIZE max(per g: SUM(e) by (g))
D.x to name a decisionx

Two meanings changed too. per g: SUM(x) <= 10 without by bounds the total over all rows, once per g; write by (g) for each group's own total. And a NULL in the data no longer stops the query: it is skipped.

Not built yet

DeciDB does not build these yet; most come from the DECIDE language proposal. A query that uses one is refused with a message, never answered differently:

  • a rule that holds only when a condition on decisions holds (the proposal's if). With a yes-or-no decision, multiplying by it often says the same: ship <= S.demand * open;
  • bounds and allowed values written in the declaration, such as x(INT) between 0 and 5: write them in SUCH THAT. The proposal's other decision types, SEMIREAL, SEMIINT and TEXT, are not built either;
  • several objectives in order of priority (MINIMIZE e1 THEN MAXIMIZE e2), and SATISFY (leave the objective out instead);
  • a table name on a decision, such as D.open: write the decision's own name;
  • norm inside a reducer, or a reducer inside norm;
  • a distance that is the square root of a sum of squares. norm(e, 2) is the sum of squares itself, so bound it by the square of the distance: norm(x - w, 2) <= 25 keeps x within 5 of w.
