Overview #

A DECIDE query is a SELECT that also declares decisions, the constraints they must satisfy and, optionally, what to optimize. DeciDB builds a model from the query's rows, solves it, and returns the rows with the decisions filled in.

Two clause orders parse to the same plan. Write the declaration in one place, never both:

SQL
-- The paper's order: the declaration between SELECT and FROM
SELECT ...
DECIDE [per key:] name(type) [, ...]
FROM ... [JOIN ...] [WHERE ...]
SUCH THAT [scope:] constraint [AND [scope:] constraint ...]
[MAXIMIZE | MINIMIZE [when condition:] objective]

-- Single-block order: everything after WHERE
SELECT ... FROM ... [WHERE ...]
DECIDE [per key:] name(type) [, ...]
SUCH THAT ...
[MAXIMIZE | MINIMIZE ...]
  • FROM, joins and WHERE run first. Their result rows are the rows decisions are made over.
  • SUCH THAT is required. Constraints are joined by AND; a comma between them is an error.
  • No objective means a feasibility problem: any assignment that satisfies every constraint.
  • SELECT, ORDER BY and any outer query run after the solve and see decisions as ordinary columns.

Grammar

Grammar
decide_list ::= declarator (',' declarator)*
declarator  ::= ['per' key ':'] name '(' INT | BOOL | REAL ')'
constraint  ::= [scope ':'] comparison
objective   ::= (MAXIMIZE | MINIMIZE) [scope ':'] expression     -- the objective takes no per but ()
scope       ::= ['when' condition] ['per' key]                    -- at least one of the two
reducer     ::= agg '(' [scope ':'] expression ')' ['by' '(' [expression, ...] ')']
              | agg '(' relation, ... ':' expression ')' ['by' ...]
agg         ::= SUM | AVG | MIN | MAX                             -- norm(e, p) and count(*) take a by
key         ::= '(' ')'  |  'row'  |  element (',' element)*
element     ::= column | relation                                 -- a relation stands for all its columns

Inside a DECIDE clause, when, per, a by right after ) and a row right after per are keywords. Quote a column with one of those names there: x <= "per". Outside the clause nothing changes; GROUP BY and ORDER BY in a subquery are untouched.

Decisions #

Each declarator has a name and a mandatory type. Reference a decision by its bare name in SUCH THAT, the objective, SELECT and ORDER BY.

TypeDomainResult type
x(BOOL){0, 1}INTEGER
x(INT)0, 1, 2, … by defaultBIGINT
x(REAL)[0, ∞) by defaultDOUBLE

Signed decisions

Zero is a default lower bound for INT and REAL, not a floor. A decision becomes signed when the query bounds it alone below zero: x >= -K in any affine spelling, x BETWEEN -K AND K, an easy MIN(x) >= -K, or a negative value in an IN list. Under a when, only the rows it keeps take the negative floor.

SQLRuns as shown
x BETWEEN -2 AND 2 AND SUM(x * weight) <= 40

There is no fully free domain: a signed decision always has a finite lower bound, unless the query writes -1e30 or below.

How many decisions

The declaration's key sets how many decisions a declarator makes. Each declarator has its own key.

SpellingScopeDecisions
x(INT), per row: x(INT)per row (default)one per result row
per K: x(INT)keyedone per distinct value of K among the result rows
per (): x(INT)query-wideexactly one

Keyed decisions: per K: x(TYPE) #

SQL
DECIDE per D.depotID: reserve(REAL)              -- one per distinct depotID
DECIDE per D: open(BOOL)                         -- one per distinct row of D
DECIDE per D.region, S.shipmentID: alloc(INT)    -- one per distinct pair, across relations
DECIDE ship(INT), per D: open(BOOL), per (): cap(INT)   -- each declarator has its own key
  • Key elements are columns and relations of the FROM clause, spelled as anywhere in the query. A relation stands for all its stored columns. Expressions belong in by, not in a key.
  • A key is a set: per a, b and per b, a are the same key.
  • Every row shows its class's value. A row whose key column is NULL is in no class and has no decision; it shows NULL.
Sums count result rows

Over a join, a keyed decision appears on every row of its key, and an unscoped SUM reads it once per row, as SQL would. To count each class once, give the reducer its own per (SUM(per n: keep * skill)) or use the colon form. See the nurse example.

SQLRuns as shown
SELECT n.name, s.shift_date, keep
FROM nurses n JOIN shifts s ON n.id = s.nurse_id
DECIDE per n: keep(BOOL)
SUCH THAT SUM(keep * s.hours) <= 60            -- one term per shift row
MAXIMIZE SUM(per n: keep * n.skill_score);     -- each nurse's skill once

Query-wide decisions: per (): x(TYPE) #

One decision for the whole query, whatever the input size: a threshold, a shared ceiling, a worst case. Its value repeats on every row. It may stand beside a reducer or be its bound under any per, and it counts once.

SQLRuns as shown
-- The DeciDB paper's Example 1: no region falls short by more than max_shortfall
SELECT r.routeID, r.regionID, ship, max_shortfall
FROM routes r JOIN regions g USING (regionID)
DECIDE ship(INT), per (): max_shortfall(INT)
SUCH THAT ship <= r.capacity AND SUM(ship) <= 40
      AND per g: g.demand - SUM(ship) by (g) <= max_shortfall
MINIMIZE max_shortfall;

A sum over query-wide decisions alone (SUM(cap)) is refused as a constraint's whole decision side: there is one value and nothing to add up, so write cap. Mixed with row data it is ordinary scaling: SUM(cost * cap) is (Σ cost) · cap.

Constraints #

Every constraint must hold. Join them with AND; OR between constraints is refused, because a choice between alternatives is a BOOL decision. OR inside a when or a subquery is data and unaffected.

A constraint with no reducer holds on every row (units <= capacity). One with a reducer holds over the rows the reducer reads (SUM(units) >= 500). Either side may carry decisions: 5 >= x and x <= 5 are the same constraint, and a reducer may sit on both sides.

OperatorNotes
= <= >=Any decisions.
< > <>Exact only on whole numbers, so each side must have an integer type: INT/BOOL decisions and integer or DECIMAL(p, 0) data. Checked on declared types, so one fractional row can never break a working query. SUM(x) <> 0 over non-negative decisions becomes SUM(x) >= 1.
BETWEENTwo constraints under one scope.
INOn a decision, restricts its domain: x IN (0, 2, 3). On a column, a filter.
SQLRuns as shown
x IN (0, 2, 3) AND SUM(x * weight) <= 80 AND SUM(x) <> 4
SQL
SUM(x * weight) > 40
Errorrefused before solving
Binder Error: Strict inequality '>' is not supported over the REAL decision 'x': 'SUM(x * weight) > 40'. A REAL decision takes any value up to the bound, so there is no next value to stop at. Use '>=' instead, and move the bound by one step if the compared quantity is a count or other whole number.

What a term may hold

  • Data. Any operand that reads no decision is data, evaluated per row exactly as SQL would: arithmetic, functions, CASE, comparisons as 0/1, lambdas, prepared-statement parameters.
  • Decisions. Linear terms, products of two decisions and squares (POWER(e, 2), e ** 2, e * e). ABS and POWER with a whole exponent are the only functions that take a decision. A term of degree 3 or more, a division by a decision, a cast of a decision or a CASE over a decision is refused, with a message that quotes the clause.
  • Subqueries. Scalar subqueries, correlated or not, may be bounds or factors. A subquery cannot read the enclosing query's decisions.
SQLRuns as shown
SUM(x * weight) <= (SELECT MAX(weight) * 2 FROM Items)
      AND x <= CASE WHEN category = 'tech' THEN 1 ELSE 0 END + 1

A DECIDE inside a bound

A scalar subquery that bounds a constraint may hold its own DECIDE. It solves first and its one-row result becomes the bound. Here: the lightest bag worth at least as much as the best 30 kg bag.

SQLRuns as shown
SELECT item, value, weight, x
FROM Items
DECIDE x(BOOL)
SUCH THAT SUM(x * value) >= (
    SELECT SUM(y * value) FROM (
        SELECT value, y FROM Items
        DECIDE y(BOOL)
        SUCH THAT SUM(y * weight) <= 30
        MAXIMIZE SUM(y * value)))
MINIMIZE SUM(x * weight);

Scopes: per, when, by #

Three keywords, three separate jobs.

KeywordWhereJob
per Kin front of a declarator, a constraint, the objective, or a reducer's argumenthow many: one decision, constraint or reducer input per class of K
when cin front of a constraint, the objective, or a reducer's argumentwhich rows are looked at: those where c is true
by (Γ)right after a reducerwhich rows that one reducer reads: the kept rows sharing the current value of Γ

when comes before per, and a colon follows the scope. A scope covers one constraint: in per g: A AND B, only A is scoped.

OmittedMeans
per on a declarator, a constraint or inside a reducerper row
per on the objectiveper (): the objective is produced once
byby (): all kept rows
whenevery row

per never selects the rows a reducer reads, and by never changes how many constraints exist. One constraint often needs both:

WrittenConstraintsEach reducer reads
ship <= 0.20 * SUM(ship)one per rowall rows
per (): SUM(ship) <= networkCapacityoneall rows
per D.depotID: SUM(ship) by (D.depotID) <= D.capacityone per depotthat depot's rows
ship <= D.maxShipmentShare * SUM(ship) by (D.depotID)one per rowthat row's depot
per D.depotID: SUM(ship) by (D.region) <= D.capacityone per depotthe depot's region

These come from the language proposal's worked examples, over shipments joined to depots (FROM Shipment S JOIN Depot D USING (depotID), with DECIDE ship(INT), per D.depotID: reserve(REAL)). All of them run:

Examples 1–4Runs as shown
ship <= 0.20 * SUM(ship)
AND per (): SUM(ship) <= networkCapacity
AND per D.depotID: reserve >= D.networkReserveShare * SUM(S.demand)
AND per D.depotID: SUM(ship) by (D.depotID) <= D.capacity
Examples 5–8Runs as shown
ship <= D.maxShipmentShare * SUM(ship) by (D.depotID)
AND per D.depotID: reserve >= 0.10 * SUM(S.demand) by (D.region) + 0.02 * SUM(S.demand) by (D.country)
AND per D.depotID: SUM(when S.priority: ship) by (D.depotID) <= D.priorityCapacity
AND per S.shipmentID: ship <= 0.25 * SUM(ship) by (D.depotID, S.dispatchDay + S.transitDays)
  • per K lists columns and relations without parentheses (per a, b:); per (): is exactly one; per row: is the default.
  • when c is any boolean over data, ended by per or the colon, so when a and b: needs no parentheses. NULL counts as false. It may not mention a decision, a reducer or a window function. Nothing is computed on a row it drops, so when s <> '' and CAST(s AS INT) > 3: never casts an empty string.
  • by (Γ) applies to SUM, AVG, MIN, MAX, norm and count(*), on either side, with or without a decision inside. Γ lists columns, relations and data expressions, never a decision.

How a scope is evaluated #

  1. Filter. Keep the rows where the when condition is true.
  2. Generate. Split the kept rows into classes by the per key; write the constraint once per class.
  3. Aggregate. A reducer agg(...) by (Γ) reads every kept row whose Γ equals the class's, including rows outside the class.
  4. Check. The key must determine every value the constraint reads once per class (below).
per D.depotID: SUM(ship) by (D.region) <= D.capacity
  shipment  depot  region  ship  capacity
  S1        D1     North   x1    100
  S2        D1     North   x2    100
  S3        D2     North   x3     80
  S4        D3     South   x4     50

  D1: x1 + x2 + x3 <= 100    D2: x1 + x2 + x3 <= 80    D3: x4 <= 50

A reducer inside a scope can have its own when and per, written agg(when c per K: e). The order is: the rows by selects, then the inner when, then one value per class of the inner per, then the aggregate.

SQL
SUM(when S.priority: ship)                          -- only priority rows
SUM(per D: D.opening_cost * open)                   -- each depot once
SUM(when S.priority per D: D.opening_cost * open)   -- filter, then each remaining depot once

The determination rule #

A constraint written once per class must read one value per class. So a per key must determine everything its body reads outside reducers (bounds, factors, decisions) and every by key: every row of a class must carry the same value.

  • A keyed decision is determined when each class lies inside one class of its own key; a per-row decision only when each class is one row; a query-wide decision always.
  • Literals and uncorrelated subqueries are always determined. per () and the objective need one value over all kept rows.
  • It is checked on the data, every run, before solving, on kept rows only. A query can pass on one dataset and fail on another; a static check would have to refuse queries that are fine on their data.
SQLRuns as shown
per D.depotID: SUM(ship) by (D.region) <= 500   -- holds: each depot has one region
SQL
per D.depotID: ship <= 10    -- fails: ship is per row, a depot has several rows
Errorrefused before solving
Invalid Input Error: DECIDE: per D.depotID does not determine the decision ship (declared per row). D.depotID = 'D1' covers more than one ship.

Without a per, a value that varies by row is reduced to its tightest value within each by group instead: SUM(ship) by (depotID) <= stock uses the smallest stock for <=, the largest for >=. = refuses a bound that varies.

Reducers #

ReducerMeaning
SUM(e)The primary reducer. Data-only terms inside it move to the bound.
AVG(e)SUM(e) / n, where n is the number of values it reads.
MIN(e), MAX(e)See MIN and MAX.
norm(e, p)L1, squared L2, L∞ or L0. See norm().
count(*)Data only: the number of kept rows; takes a by.

COUNT(x) over a decision is refused; count chosen rows with SUM(x). A factor may scale any reducer, on either side: 2 * SUM(x * p), SUM(x) / 2, -MAX(e). In a constraint the factor may be any data; in the objective it must be one value over the kept rows. A BOOL decision may scale a bare reducer (b * SUM(x) <= 4).

SQLRuns as shown
AVG(x * value) >= 20 AND SUM(x * weight) <= 2 * count(*) * 5

The colon form: SUM(D: e) #

agg(Rel: e) means agg(per Rel: e): one term per tuple of the named relation instead of one per result row. Use it for a fixed cost that a join repeats.

SQLRuns as shown
SELECT S.shipmentID, D.depotID, open, ship
FROM Shipment S JOIN Depot D USING (depotID)
DECIDE per D: open(BOOL), ship(INT)
SUCH THAT ship <= S.demand * open AND SUM(ship) >= 120
MINIMIZE SUM(S.unit_cost * ship) + SUM(D: D.opening_cost * open);  -- each depot's cost once
  • Identity is the tuple, not the value: two depots with equal cost are two terms. This is not SUM(DISTINCT ...).
  • The named relations must determine the body; this is checked on the data.
  • AVG(D: e) divides by the number of depots. Naming several relations (SUM(D, T: e)) removes the fan-out of each.

MIN and MAX #

The easy direction, MAX(e) <= K or MIN(e) >= K, bounds every member and adds nothing to the model. The hard direction (the opposite, or =) adds an extremum variable per group, tied to the members by indicator constraints, so every member needs a finite bound. In the objective, MINIMIZE MAX and MAXIMIZE MIN are cheap; the other two directions add indicators.

SQLRuns as shown
MAX(x * weight) <= 40 AND MAX(x * weight) >= 30 AND SUM(x) <= 4

norm(e, p) #

pMeansClass
1SUM(ABS(e))LP
2SUM(POWER(e, 2)), the squared L2 normconvex QP
'inf'MAX(ABS(e))LP
0 or 0, Mthe number of rows where |e| ≥ a tolerance (1e-4)MILP

The L0 count is exact in every direction (cap, floor, =, MAXIMIZE); e needs finite bounds. A norm takes a when or per in front of its clause and a by after it, but no scope inside.

SQLRuns as shown
SELECT item, price, new_price
FROM Menu
DECIDE new_price(REAL)
SUCH THAT new_price BETWEEN floor AND ceiling
      AND SUM(new_price * weekly_qty) >= 16500
      AND norm(new_price - price, 0) <= 2       -- at most two prices change
MINIMIZE norm(new_price - price, 1);            -- smallest total change

Objective #

SQL
MAXIMIZE SUM(ship)                                     -- produced once: per () implied
MAXIMIZE when S.priority: SUM(ship)                    -- over the priority rows only
MINIMIZE SUM(S.unit_cost * ship) + SUM(D: D.opening_cost * open)
MINIMIZE max(per D.depotID: SUM(ship) by (D.depotID))  -- two-level form
  • The objective is produced once: no per means per (), and any other per is an error.
  • Its body is reducers, decisions outside them, and sums of those, with at least one decision.
  • A decision outside a reducer must have one instance over the kept rows: any per () decision, or a per-row or keyed one when the when keeps one row or class (MAXIMIZE when id = 3: x).
  • when c filters the rows for the whole objective. A term that reads no row is dropped.
SQLRuns as shown
MINIMIZE when S.priority: SUM(S.unit_cost * ship) + SUM(D: D.opening_cost * open) + cap

Two-level objective #

outer(per k: inner(e) by (k)) computes inner once per class of k, then outer over those values. All nine SUM/MIN/MAX pairs work; k may list several columns. It takes a minus sign or a constant factor and a when in front. The by key must be the per key.

SQLRuns as shown
SELECT M.machine, J.job, run
FROM Jobs J CROSS JOIN Machines M
DECIDE run(BOOL)
SUCH THAT per J: SUM(run) by (J) = 1
MINIMIZE max(per M.machine: SUM(run * J.hours) by (M.machine));   -- the busiest machine

Quadratic and bilinear terms #

  • Squares. MINIMIZE SUM(POWER(linear, 2)) is a convex QP on both solvers (on HiGHS when continuous and the matrix is non-singular). -POWER(...) under MAXIMIZE is concave and also fine. MAXIMIZE SUM(POWER(...)) is non-convex: Gurobi only. Any number of squares may be added together.
  • Quadratic constraints, such as SUM(POWER(x - target, 2)) <= 9, need Gurobi.
  • Products of two decisions. With one BOOL factor, b * x is linearized exactly and runs on both solvers (the other factor needs a finite upper bound). Otherwise it is non-convex and Gurobi only. Three decision factors are refused.
  • Integer decisions with a quadratic objective (MIQP) need Gurobi.
SQLRuns as shown
SELECT asset, w
FROM Holdings
DECIDE w(REAL)
SUCH THAT w <= max_weight AND SUM(w) = 1
      AND SUM(POWER(w - target, 2)) <= 0.02             -- a quadratic constraint (Gurobi)
MINIMIZE SUM(POWER(w - target, 2)) + 0.1 * norm(w - target, 1);

A query whose class the available solver cannot take is refused at plan time, before any row is read, with a message naming the clause and the solver it needs. See problem classes.

NULL and empty groups #

A NULL data value is skipped where it is read, never read as zero.

SituationOutcome
NULL in a declaration, per or by key columnno class or group for that row (a relation key compares NULL as a value)
a keyed decision on a NULL-key rowno decision: the row shows NULL
NULL when conditionthe row is dropped
NULL in a reducer's summandthe row is skipped, as in SQL; AVG divides by the rows kept
NULL bound or coefficient outside a reducerthat instance of the constraint is skipped
NULL in an objective termthe term is dropped
a when that keeps no row, or a group a reducer reads nothing fromno constraint there
count(*) over no rows0, as in SQL
NULL written beside a decision (SUM(x + NULL)), NaN in data, an infinite coefficientan error that names the value

To impute instead of skip, write it: SUM(x * COALESCE(w, 0)).

Numbers and casts #

  • A model carries one numeric type, DOUBLE, as both solvers do.
  • A cast over a decision is refused in SUCH THAT and the objective; cast the data instead. Data casts keep DuckDB's meaning: x <= CAST(1.6 AS INTEGER) has bound 2.
  • A whole-number answer beyond 253 is refused rather than rounded.
  • When the model holds a coefficient of 1e6 or more, a bound of about 4.5e9 or more, or an objective coefficient of 1e-6 or less, DeciDB prints one warning to scale the data toward 1, then solves.

EXPLAIN #

EXPLAIN, EXPLAIN ANALYZE and EXPLAIN (FORMAT JSON) work on a DECIDE query. The DECIDE node lists the decisions, the objective and the constraints, each as you wrote it. Indented lines follow only where the model differs: ↳ for what a rewrite made of a clause, such as an auxiliary variable or a helper decision. EXPLAIN plans without solving.

SQLRuns as shown
SELECT S.shipmentID, ship
FROM Shipment S JOIN Depot D USING (depotID)
DECIDE ship(INT)
SUCH THAT ship <= S.demand
      AND per D.depotID: SUM(ship) by (D.region) <= D.capacity
      AND abs(SUM(ship) by (D.region) - 40) <= 30
MAXIMIZE SUM(ship);
EXPLAIN: the DECIDE node
DECIDE
  Variables: ship
  Objective: MAXIMIZE SUM(ship)
  Constraints:
    ship <= S.demand
    per D.depotID: SUM(ship) by (D.region) <= D.capacity
    abs(SUM(ship) by (D.region) - 40) <= 30

      ↳ sum(ship) by (D.region) becomes a helper decision per group
      ↳ abs(sum(ship) by (D.region) - 40) - sum(ship) by (D.region) >= -40
      ↳ abs(sum(ship) by (D.region) - 40) + sum(ship) by (D.region) >= 0 + 40

DIAGNOSE #

When no assignment satisfies every constraint, a query stops with an error that says what to do next:

SQL
SELECT item, x FROM Items
DECIDE x(BOOL)
SUCH THAT SUM(x * weight) <= 40 AND SUM(x) >= 4
MAXIMIZE SUM(x * value);
Errorrefused before solving
Invalid Input Error: DECIDE optimization is infeasible. Prefix the query with DIAGNOSE to see which clause to change.

Prefix it with DIAGNOSE. The query runs, and instead of its rows you get one row per finding: the clause as you wrote it, the smallest change that fixes it, and the objective you would get after the change. DIAGNOSE is the only thing that starts the diagnosis engine, so a query without it never pays for one.

A slow solve

If a solve hits its time limit or you press Ctrl-C, the query prints a checkpoint report. At a terminal it offers to keep solving (Enter) or stop with the best answer so far (s); in a script it errors; after Ctrl-C it returns the best answer found, marked as not proven best. SET decide_mip_gap = 1e-4 accepts an answer within 0.01% of the optimum.

Direct solve #

Some queries have a closed-form answer that DuckDB's own operators compute: sort and take the top k, fill a budget greedily, match two sorted lists. When DeciDB can prove a query has one of these shapes, it answers that way instead of calling a solver. A query it cannot prove takes the solver path unchanged. There is no syntax for it: the same SQL simply gets faster and exact.

SettingEffect
SET decide_direct_solve = 'auto'default: answer directly when proved
SET decide_direct_solve = 'off'always use the solver
SET decide_direct_solve = 'require'raise an error when no rule applies

When several assignments are optimal, direct solve may return a different one than the solver; the objective is the same. The classes it covers are listed on Problems.

Migrating from 0.2 #

DeciDB 0.2 wrote scopes after a constraint (SUM(x) <= 2 PER sector) and qualified declarations with a table (T.x(INT), scalar x(INT)). The language now follows the DECIDE language proposal: scopes go in front, and a reducer says which rows it reads with by.

Each old spelling is refused with a message that names the new one, built from your own query so you can paste it back:

SQL
SELECT ticker, pick FROM Stocks
DECIDE pick(BOOL)
SUCH THAT SUM(pick) <= 2 PER sector
MAXIMIZE SUM(pick * expected_return);
Errorrefused before solving
Parser Error: DECIDE: the postfix PER is removed; write per sector: in front of the constraint and by (sector) after each of its reducers
Old spellingWrite instead
DECIDE T.x(INT)DECIDE per T: x(INT), or per T.k: x(INT) to key on one column
DECIDE scalar x(INT)DECIDE per (): x(INT)
SUM(x) <= 2 PER gper g: SUM(x) by (g) <= 2
x <= cap PER g (no reducer)x <= cap: a constraint without a reducer already holds on every row
SUM(x) >= 2 WHEN cwhen c: SUM(x) >= 2
SUM(x) >= d WHEN c PER gwhen c per g: SUM(x) by (g) >= d
SUM(x * h) WHEN c inside an expressionSUM(when c: x * h)

Two meanings changed as well. A per without a by does not group the sum: per g: SUM(x) <= 10 bounds the total over all kept rows, once per g; write by (g) for each group's own total. And a NULL in the data no longer stops the query: it is skipped where it is read, as SQL's aggregates skip it (details).

Not supported yet #

The DECIDE language proposal goes further than DeciDB does today. These parts of it are planned, and a query that uses one is refused with a message rather than answered differently:

  • Nested reducers to any depth, such as SUM(MAX(ship) by (customer)) by (depot). Today the two-level objective is the one nested shape.
  • Variant signatures: one constraint per distinct combination where a key does not determine a value. Today that is the determination error.
  • Frame selectors for ordered data: at(previous: e), SUM(from first to last: e) over (day), cyclic orders.
  • Conditional constraints on decisions with if: enforce a capacity only if a depot is decided open.
  • Declaration bounds and domains: between at the declaration, semi-continuous SEMIREAL/SEMIINT, finite text domains.
  • Lexicographic objectives (minimize e1 then maximize e2) and an explicit satisfy.
  • A qualified decision name (D.open) as a plain name lookup.
  • Second-order cone constraints. The squared form norm(e, 2) <= R * R already covers the common case.
