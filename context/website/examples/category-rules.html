Category rules and a budget from a table

Rules that apply to one category at a time, and limits read from a settings table instead of written into the query.

WHERE before DECIDEwhen c: constraintbound from a subquery

The problem

A store picks products for a display. The budget and the item limit live in a Settings table so they can change without editing the query. At least two products must come from category A, at most one from category B, and out-of-stock products are not candidates at all.

The data

Setup
CREATE TABLE Settings (budget INT, max_items INT);
INSERT INTO Settings VALUES (120, 5);

CREATE TABLE Products (name VARCHAR, category VARCHAR, value INT, cost INT, in_stock BOOLEAN);
INSERT INTO Products VALUES
    ('Desk lamp', 'A', 40, 25, true), ('Monitor arm', 'A', 55, 35, true),
    ('Webcam', 'A', 35, 30, true), ('Headset', 'B', 60, 45, true),
    ('Keyboard', 'B', 50, 30, true), ('Mouse', 'B', 30, 15, true),
    ('Cable kit', 'C', 20, 10, true), ('Dock', 'C', 70, 60, false),
    ('Chair mat', 'C', 25, 20, true);

The query

DECIDE query
SELECT name, category, value, cost, pick
FROM Products
WHERE in_stock
DECIDE pick(BOOL)
SUCH THAT SUM(pick * cost) <= (SELECT budget FROM Settings)
      AND SUM(pick) <= (SELECT max_items FROM Settings)
      AND when category = 'A': SUM(pick) >= 2
      AND when category = 'B': SUM(pick) <= 1
MAXIMIZE SUM(pick * value);

Problem class: ILP.

How it reads

  • WHERE in_stock
    Ordinary SQL runs first. The dock is out of stock, so it never gets a decision.
  • <= (SELECT budget FROM Settings)
    A bound can be any scalar subquery. Change the table, rerun the query.
  • when category = 'A': SUM(pick) >= 2
    when in front of a constraint keeps only the rows where the condition holds. The sum reads category A alone.
  • when category = 'B': SUM(pick) <= 1
    One rule per category, each with its own condition.

The answer

Five products for exactly 120: the lamp and monitor arm from A, the keyboard from B, and both C items. The headset is the most valuable product, but B allows only one pick and the keyboard leaves more of the budget for the rest.

A condition inside one sum

A when can also sit inside a reducer, where it filters that reducer only. This caps the spend on category C while the other sums still read every row:

SQL
SUM(when category = 'C': pick * cost) <= 25
