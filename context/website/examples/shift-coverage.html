Cover every shift

Exactly one nurse per shift, at most one shift per nurse. There is nothing to optimize, only rules to satisfy.

Feasibility
decidb · shift-coverage.sql
SELECT nurse, shift, on_duty
FROM Availability
DECIDE on_duty(BOOL)
SUCH THAT per shift: SUM(on_duty) by (shift) = 1
      AND per nurse: SUM(on_duty) by (nurse) <= 1
ORDER BY shift, nurse;

The problem

Each row says a nurse is available for a shift. Every shift needs exactly one nurse, and nobody works twice. Leaving out MAXIMIZE and MINIMIZE asks for any assignment that satisfies the rules.

Problem class: Feasibility, solved by Gurobi or HiGHS.

How it reads

per shift:
Write this constraint once per distinct shift: four shifts, four constraints.
SUM(on_duty) by (shift) = 1
by (shift) makes the sum read only the rows of the current shift.
per nurse: SUM(on_duty) by (nurse) <= 1
The same pattern per nurse.
no objective
A feasibility query: DeciDB returns one assignment that satisfies every constraint, or says none exists.

The answer

Each of the four shifts has exactly one nurse and nobody works twice; Bob is left free. Other valid rosters exist. To prefer one, add an objective, such as MAXIMIZE SUM(on_duty * seniority).

Why both per and by?

per sets how many constraints there are; by sets which rows a sum reads. They are separate words because they are separate choices: per shift: SUM(on_duty) <= 3 would write one constraint per shift, each bounding the total over all rows. Here, a weekend rule combines a when with a per:

SQLRuns as shown
when weekend per nurse: SUM(on_duty) by (nurse) <= 1

This example shows

  • per K: one constraint per group
  • by (K): sum within the group
  • feasibility (no objective)
