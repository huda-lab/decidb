Three stages

The front end turns SQL text into a LogicalDecide operator in DuckDB's logical plan. It runs in three stages, and each refuses only what it alone can see.

StageReadsProducesRefuses
01 Parserthe query texta parsed SelectNode with the four DECIDE parts, and the text of every expression in the clausesyntax: a missing type, a comma between constraints, a removed spelling
02 Binderthe parsed tree and the catalogbound expressions: decisions, keys, types, reducersnames, keys, scopes, casts over decisions, strict comparisons on fractional values
03 Logical planthe bound treeone LogicalDecide above the scans and filtersnothing of its own; it calls the canonicalizer, which refuses shapes

None of the three moves a term across a comparison or picks a formulation. Which side a term belongs on is decided once, by the canonicalizer, on the bound tree. How each construct reaches the solver is decided by the optimizer. Keeping the front end free of both is what lets EXPLAIN, DIAGNOSE and every message quote a clause exactly as the user typed it.

The parser

The parser turns SQL text into a parsed SelectNode carrying the decisions, the constraints, the objective's sense and the objective. It refuses syntax and decides no shape.

DuckDB parses with libpg_query, its fork of the PostgreSQL grammar. Bison compiles that grammar into an LALR(1) parser: a parser that chooses each step from the next token alone. DeciDB adds its productions to the same grammar, so a DECIDE query is one SELECT statement to DuckDB, with one more optional clause. DECIDE, SUCH, MAXIMIZE, MINIMIZE and DIAGNOSE are reserved keywords.

One clause, two orders

A query may declare its decisions after WHERE, in one block, or between SELECT and FROM, the order the DeciDB paper uses (the full shape). The grammar has a slot for each order, decide_clause for the first and decide_declaration with decide_body for the second, and both build the same PGDecideClause through makeDecideClause(). Nothing after the parser knows which order the user chose.

A declaration is a name and a type in parentheses, alone or behind a per. The type is a plain identifier that makeDecideVariableType reads as INT, REAL or BOOL in any case. DECIDE adds no keyword for a type on purpose: DuckDB quotes every keyword when it prints a name, so a keyword BOOL would quote a column named bool in every message and rendered query.

Some productions exist only to produce a message. A name with no type, a comma between constraints and each removed spelling (below) have a production of their own, so the parser names the fix instead of reporting a syntax error at the next token:

SQL
SELECT item, x
FROM Items
DECIDE x
SUCH THAT SUM(x * weight) <= 50
MAXIMIZE SUM(value * x)
Errorrefused before solving
Parser Error: DECIDE variable "x" needs a type; write x(INT), x(BOOL) or x(REAL)

The scopes of the language (when and per in front of what they govern, by after a reducer) are four small productions:

The scope productions (select.y, simplified)
decide_scope ::= decide_when | decide_when decide_per | decide_per
decide_when  ::= WHEN_DECIDE a_expr | WHEN_DECIDE_OBJECTIVE a_expr
decide_per   ::= PER_DECIDE expr_list | PER_DECIDE_PAREN '(' ')' | PER_DECIDE_ROW ROW
decide_by    ::= BY_DECIDE '(' ')' | BY_DECIDE '(' expr_list ')'

A constraint or an objective is decide_scope ':' body or a bare body. Three choices keep the grammar small:

  • The colon ends the scope. So the condition of a when is a full SQL expression and needs no parentheses.
  • One precedence level, DECIDE_ITEM, closes a body. It sits above AND and below the comparison operators. A top-level AND therefore separates two constraints, per g: A AND B scopes only A, and each body keeps its SQL shape. The parser never repairs an association after the fact.
  • The colon form reads its qualifier as an argument list. SUM(D, T: e) and sum(a, b) share a prefix that LALR(1) cannot split at the comma. Read as func_arg_list ':' func_arg_list, the choice moves to : or ) after a complete list, which has no conflict. makeQualifiedReducer then checks that each element is a relation name.

The grammar declares %expect 4: Bison accepts exactly four shift-reduce conflicts. All four come from the optional declaration slot, one per simple_select alternative. They arise only when FROM and WHERE are both empty, and both derivations build the same node, so Bison's default choice changes nothing.

Gated keywords

Three of DECIDE's words already mean something in SQL. WHEN belongs to CASE, and a DECIDE WHEN after a function call collides with WITHIN GROUP and breaks ordinary function-call parsing. BY belongs to GROUP BY and ORDER BY. And per must stay usable as a column name in every other query.

So the words become DECIDE tokens only inside a DECIDE clause. DuckDB's lexer passes every token through a filter, base_yylex, which already looks one token ahead for NOT, NULLS and WITH. DeciDB adds its rules to that filter:

WordBecomesWhen
WHENWHEN_DECIDEoutside any CASE of the clause
WHENWHEN_DECIDE_OBJECTIVEthe same, after MAXIMIZE or MINIMIZE
BYBY_DECIDEdirectly after )
PERPER_DECIDE_PARENbefore (, as in per ()
PERPER_DECIDE_ROWbefore ROW
PERPER_DECIDEotherwise

The three PER tokens need the lookahead: per (), per row and per key cannot be told apart by an LALR(1) grammar alone, since ( also opens an expression and row is also a column name. GROUP BY, ORDER BY and PARTITION BY always follow a keyword, never ), so they stay plain inside a subquery written in the clause.

The filter tracks four pieces of state:

  • Armed. DECIDE or SUCH sets in_decide_clause. SUCH sets it again for the split order, whose declaration slot clears it so that FROM, JOIN ... ON and WHERE lex as plain SQL.
  • Objective. MAXIMIZE or MINIMIZE sets in_decide_objective.
  • CASE depth. CASE adds one to decide_case_depth and END takes one away, so a WHEN inside a CASE stays SQL's.
  • A stack of enclosing clauses. A DECIDE query may be a subquery inside another DECIDE clause. PGDecidePushLexState saves the enclosing clause's state when a new clause opens, and the grammar action that closes the clause restores it, so a scope written after the subquery still lexes as DECIDE's. The stack keeps 16 levels.
third_party/libpg_query/src_backend_parser_parser.cpp (base_yylex)
if (cur_token == MAXIMIZE || cur_token == MINIMIZE)
	yyextra->in_decide_objective = true;
else if (cur_token == CASE)
	yyextra->decide_case_depth++;
else if (cur_token == END_P) {
	if (yyextra->decide_case_depth > 0)
		yyextra->decide_case_depth--;
} else if (cur_token == WHEN && yyextra->decide_case_depth == 0)
	return yyextra->in_decide_objective ? WHEN_DECIDE_OBJECTIVE : WHEN_DECIDE;
else if (cur_token == BY && after_rparen)
	return BY_DECIDE;

One clause can hold both kinds of WHEN. The scope's when is at depth 0; the CASE WHEN inside the sum is at depth 1 and stays SQL's:

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3
      AND when category = 'tech': SUM(x * CASE WHEN weight > 15 THEN 2 ELSE 1 END) <= 4
MAXIMIZE SUM(value * x)

The cost of gating: inside a DECIDE clause, subqueries included, these words are keywords in those positions. A column named per is written quoted there ("per"), as DeciDB's own printer does. Outside the clause nothing changes.

The transformer and source spans

DuckDB's transformer turns the PostgreSQL parse tree into DuckDB's parsed expressions. TransformSelectNode moves the DECIDE clause onto the SelectNode as four fields: decide_variables, decide_constraints, decide_sense (MAXIMIZE, MINIMIZE, or FEASIBILITY when no objective is written) and decide_objective. A declaration with no SUCH THAT is refused here.

DECIDE adds no parsed expression class. Each DECIDE parse node becomes a FunctionExpression whose name is a reserved tag, with the body as its first child and the condition or key after it:

WrittenParsed as
when c: CSCOPE_WHEN_TAG(C, c)
per K: CSCOPE_PER_TAG(C, K...)
per row: CSCOPE_PER_ROW_TAG(C), so the clause keeps its spelling
SUM(e) by (G)REDUCER_BY_TAG(SUM(e), G...)
SUM(D, T: e)QUALIFIED_REDUCER_TAG(SUM(e), D, T)

The transformer also keeps where each expression came from. Every SQL expression reduces through one decorator rule (a_expr: a_expr_body), whose action, noteDecideExpr, records the start and end of each expression of the DECIDE clause. The transformer keys each span by the query location of the parsed node it builds, and TransformSelectNode collects the spans and the clause's text into SelectNode::decide_text, a DecideSourceText. This is Clang's SourceManager idea: one store of source text, and a location on every node. A later stage that quotes a clause cuts the user's text at a node's location instead of printing its tree. So a message shows x <> 5 where the tree would print x != 5, and keeps the user's spacing and function names.

SelectNode::ToString() reverses the encoding: it prints x(INT), PER key: x(INT), the scope in front of a clause and reducer BY (key). The contract is a structural round trip, not a copy of the text: parsing the printed SQL gives an equal parsed statement. DuckDB's statement verifier checks it whenever verification is on.

The DIAGNOSE prefix is one more alternative of VariableShowStmt, as SUMMARIZE is, and the transformer turns it into a table reference with ShowType::DIAGNOSE. Whether the inner query holds a DECIDE is a binding question, since the clause may sit in a subquery (how DIAGNOSE is routed).

Removed spellings

Some spellings are not part of the language: a WHEN or PER written after a constraint, a reducer or the objective, a declaration T.x(INT), and scalar x(INT). The grammar keeps a production for each, so that RefuseRemovedDecideSpellings can refuse it with a message that names the spelling to write, built from the user's own expressions:

SQL
SELECT item, x
FROM Items
DECIDE x(BOOL)
SUCH THAT SUM(x * weight) <= 40 WHEN category = 'tech'
MAXIMIZE SUM(value * x)
Errorrefused before solving
Parser Error: DECIDE: the postfix WHEN is removed; write when category = 'tech': in front of the constraint

The walk visits the declarations, the constraints and the objective, and throws at the first removed form, outermost first. Every message starts with DECIDE: and holds the phrase "is removed". The binder calls the same function again for a parse tree stored before the query arrived, in a view or a macro. The test runner fails any query whose error says "is removed" unless the test is about a removed spelling, and a scanner keeps those spellings out of every other test.

The binder

The binder resolves every name in the clause, gives each decision its key and type, recognizes reducers, and refuses what only binding can see. It moves no term and judges no algebra.

DuckDB binds FROM and WHERE as for any query. The DECIDE section of BindSelectNode then calls DecideDeclarationsBinder::BindDeclarations, which works in this order:

  1. Declarations. Every name is checked and collected, then every key is resolved.
  2. The parsed clauses. Function aliases are renamed, and the checks that need what the user typed run before binding erases it: D.x, where scopes stand, casts over decisions, an aggregate over data that scales a decision, and strict comparisons on a REAL decision.
  3. The constraints. DecideConstraintsBinder binds them; then volatile functions and fractional operands of strict comparisons are refused on the bound tree.
  4. The objective. DecideObjectiveBinder binds it.

The two clause binders derive from DecideBinder, which derives from DuckDB's ExpressionBinder. That is DuckDB's own pattern: one expression binder per clause, with a shared base class for the rules every clause follows. Here the shared rules are reducers, the colon form, key scopes and where when, per and by may stand.

Declarations and keys

The binder reads every declaration's name before it resolves any key, so a key can be told apart from a decision declared before or after it. A name that matches a column of the FROM clause, or a name declared twice, is refused. A decision is then registered under its bare name, and only that name reaches it: D.x is refused with a message that says to write x.

Each decision gets a scope (DecideVarScope) from the way it is declared (one per row, one per key, or one in all):

ROW
x(INT) or per row: x(INT): one decision per result row.
KEYED
per K: x(INT): one decision per class of the key K. The scope also keeps the key as written, so a message can name the decision the way the user declared it.
GLOBAL
per (): x(INT): one decision for the whole query, a query-wide decision.

A key element resolves against the query's own FROM clause, in this order: a declared decision (refused, since a key holds only data), a column as SQL resolves it, a relation (standing for all its stored columns), a column of an outer query (refused), and otherwise an error that names it:

SQL
SELECT S.shipmentID, ship
FROM Shipment S JOIN Depot D USING (depotID)
DECIDE ship(INT), per depot: open(BOOL)
SUCH THAT ship <= S.demand * open
MINIMIZE SUM(D: opening_cost * open) + SUM(unit_cost * ship)
Errorrefused before solving
Binder Error: DECIDE: depot is neither a column nor a relation of the FROM clause

Every key the clauses write goes into one key table of DecideKey entries: a declaration's per K, a reducer's own per, a by (G), a constraint's per K: and the colon form SUM(D: e). FindOrCreateDecideKey compares elements as a set and puts them in one order, so per D.depotID, D.region and by (D.region, D.depotID) are one entry, with one grouping at execution. A keyed decision points at a KeyedScopeInfo: its key and the decisions it keys. One scope exists per key, whichever spelling names it.

A decision has no value until the solve, so WHERE, which runs below DECIDE, may not read one. The select list, ORDER BY, HAVING and QUALIFY run above DECIDE and read a decision as an ordinary column.

The width must hold any value the solve can reach, and no bound tells the binder what that is: a limit may arrive as a column read at execution (x <= cap) or as a total that bounds no single variable (SUM(x) <= 5000000000). A 32-bit column would move the failure to the readback, which would truncate the excess. Execution still range-checks every value it returns.
  • BOOL is INTEGER with a flag. It must take part in arithmetic (x * weight), which BOOLEAN cannot. The domain travels separately, in is_boolean_var, to the model builder, which gives the column its [0, 1] box. The binder writes no x >= 0 or x <= 1 constraint.
  • REAL is DOUBLE.

Where when, per and by may stand

A clause with no scope written is per row:, and a reducer with no by is by (). ValidateDecideScopeSpellings checks each scope on the parsed tree, one constraint at a time, before the clauses bind. A condition, a key and a by key may read only data. A decision there has no value until the solve, and a window function or a reducer would read rows the scope has not chosen yet.

SQL
SELECT item, x
FROM Items
DECIDE x(BOOL)
SUCH THAT when x > 0: SUM(x * weight) <= 40
MAXIMIZE SUM(value * x)
Errorrefused before solving
Binder Error: DECIDE: x is a decision; when, per and by may only use data

Bound, a scope becomes data on the clause, not a rewrite of it:

WrittenBound as
when c: Ca wrapper tagged WHEN_FILTER_TAG, children [C, c]
per K: Ca wrapper tagged PER_CLASS_TAG over C, naming K's entry in the key table
per row: Cnothing: the default written out
SUM(e) by (G)the aggregate, tagged with G's entry in the key table
SUM(when c: e)the aggregate's own filter
SUM(per K: e), SUM(D: e)the aggregate, tagged with the key scope whose classes it counts once

No layer turns a scoped clause into a different unscoped one. The canonicalizer reads the wrappers to choose the clause's shape, and execution partitions rows by each key. That is why EXPLAIN can print a scoped clause in the user's own words.

Reducers

A reducer is an aggregate over decisions: SUM, AVG, MIN or MAX. DECIDE uses its own word so it is never confused with a SQL aggregate over data, which stays DuckDB's. DecideBinder::ClassifyReducerCall is the one place both clause binders ask whether a call is a reducer. A reducer takes exactly one argument: max(x, 2) is DuckDB's top-n aggregate and is refused.

  • BindScopedReducer peels a reducer's own when and per. The condition binds as data onto the aggregate's filter; the key becomes a tag naming its key scope.
  • BindQualifiedReducer binds the colon form SUM(D: e) as sum(per D: e), on the same key scope. Whether D determines what the body reads is a property of the data, checked before the solve (the scope checks).
  • norm(e, p) binds as an inert SUM marker tagged with its order. The canonicalizer and the optimizer lower it.
  • COUNT binds as data only.

The binder chooses no formulation for any of them: an ABS, a hard MAX or an IN is still the node the user wrote when the plan is built.

One name per function

DuckDB registers one function under several names: pow, power and ^ for **; abs for @; add, subtract and multiply for +, - and *; mean for avg. Before any check reads a name, RespellDecideAliases renames each such call in the DECIDE clauses to the primary name DuckDB records for it. DeciDB keeps no alias list of its own.

So every later check matches one name per function, and multiply(x, weight) answers as x * weight does. The name the user typed survives in a display tag, which only rendering reads. The renaming runs in the binder, not the canonicalizer, because binder checks read names: renamed later, multiply(avg(v), x) would slip past the refusal of avg(v) * x.

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT SUM(multiply(x, weight)) <= 50 AND pow(x, 1) <= 3
MAXIMIZE SUM(value * x)
EXPLAIN: the DECIDE node
DECIDE
  Variables: x
  Objective: MAXIMIZE SUM(value * x)
  Constraints:
    SUM(multiply(x, weight)) <= 50
      ≡ sum(multiply(weight, x)) <= 50
    pow(x, 1) <= 3
      ≡ x <= 3

The ≡ lines are the canonical form. multiply is respelled like any *, with the data coefficient moved to the left, and keeps its written name; pow(x, 1) is x.

What only binding can refuse

Four layers refuse a DECIDE query, each for what only it can see:

LayerRefuses
Parsersyntax, the removed spellings
Bindernames, keys, scopes, function resolution; who wrote a cast; the declared types a strict comparison needs; a truth value read as a number
Shape checkthe algebra: functions over a decision, exponents, division by a decision, CASE over a decision, degree
Solver gatewhat the chosen solver cannot take, such as quadratic constraints on HiGHS

The binder judges no algebra, on purpose. It sees the tree as typed, and one polynomial has many trees: 2*x*x, x*2*x and (x-t)*(x-t) differ. A judgement there needs a recognizer per spelling, a list of cases that keeps growing, and every gap in it refuses a legal query. After canonicalization each product has one spelling, so the shape check reads each shape one way.

What the binder does refuse needs the parsed tree, the declared types or the bind context:

  • A cast over a decision. A cast the user wrote and a cast the binder inserted are the same bound node, so authorship is visible only on the parsed tree (casts).
  • <, > and <> over fractional values. Each is modeled by stepping the bound one whole unit (< K becomes <= K - 1), which is exact only on whole numbers. The rule reads declared types, never rows, so a query's validity follows from the query and the schema, not from the data it happens to hold.
  • A volatile function. Later stages read a clause more than once, so one random() would select different rows each time.
  • An OR between constraints, and a comparison read as a number (x <= (x > 1)): both need an indicator no layer builds.
  • A column of an outer query. A DECIDE solves one problem; solving it again for each outer row is not built.
SQL
SELECT item, x
FROM Items
DECIDE x(REAL)
SUCH THAT SUM(x) < 5
MAXIMIZE SUM(value * x)
Errorrefused before solving
Binder Error: Strict inequality '<' is not supported over the REAL decision 'x': 'SUM(x) < 5'. A REAL decision takes any value up to the bound, so there is no next value to stop at. Use '<=' instead, and move the bound by one step if the compared quantity is a count or other whole number.

A refusal quotes the clause as typed. Each bound node keeps the query location of the parsed node it comes from (DecideBinder::PreserveQueryLocation), and DecideWrittenSql cuts the user's text at that location. A function is named as typed: count(*), not DuckDB's internal count_star.

The logical plan

The plan holds the decision query as one operator, LogicalDecide, above the scans and filters of its rows. The node carries everything the binder and the canonicalizer decided, and the name of a solver, never a solver.

Where the node sits

LogicalDecide sits above the scans, joins and filters of the query, so the solver only ever sees rows that survive WHERE. A projection above it computes the select list and drops the columns of the auxiliary variables the optimizer adds.

SQLRuns as shown
SELECT S.shipmentID, ship
FROM Shipment S JOIN Depot D USING (depotID)
WHERE D.country = 'US'
DECIDE ship(INT)
SUCH THAT ship <= S.demand AND ship <= 0.20 * SUM(ship)
MAXIMIZE SUM(ship)
EXPLAIN: the operators
PROJECTION
└─ DECIDE   decisions: ship
   └─ HASH_JOIN
      ├─ SEQ_SCAN   Shipment
      └─ SEQ_SCAN   Depot

The WHERE filter has no operator of its own: DuckDB pushes it into the scan of Depot. The node's output is its child's columns plus one column per decision, auxiliaries included (GetColumnBindings), because the constraints refer to them by binding. A filter written above a DECIDE stays above it: join ordering treats the node as one relation, so a parent's filter never moves into the rows the problem is defined over.

Subquery provenance

DuckDB's PlanSubqueries flattens each scalar subquery into a join. After that, a column that varies by row, an uncorrelated subquery and a correlated one all look alike: each is a plain column reference. Yet DECIDE treats them differently. An uncorrelated subquery is one value for the whole query, and may scale a reducer in the objective; a column that varies by row may not. So plan_select_node.cpp records the difference while it is still visible:

  1. Collect. Every scalar subquery in the constraints and the objective, split by IsCorrelated(). It holds the slot, not the node, since flattening replaces the node in place.
  2. Flatten. PlanSubqueries.
  3. Read back. What each slot became, recorded as a table index in query_wide_table_indexes or correlated_subquery_table_indexes.
  4. Tag. Each flattened value with QUERY_WIDE_VALUE_TAG or ROW_VARYING_SUBQUERY_TAG, so the fact survives copies.
  5. Canonicalize. The constraints and the objective, then the shape check (the canonicalizer).

The canonicalizer reads the allow-list: a factor on a reducer in the objective must be one value for the whole query. An uncorrelated subquery passes:

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3 AND SUM(weight * x) <= 50
MAXIMIZE (SELECT max(value) FROM Items) * SUM(x)

A column fails, and so does a correlated subquery. The correlated set changes no decision; it exists so the message can say "this subquery" rather than the internal name of the flattened join:

SQL
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3 AND SUM(weight * x) <= 50
MAXIMIZE (SELECT max(I.value) FROM Items I WHERE I.category = Items.category) * SUM(x)
Errorrefused before solving
Binder Error: DECIDE objective: this subquery returns a different value for each row, so it cannot multiply SUM(x). Move it inside the aggregate, e.g. SUM(x * (SELECT ...)).

The canonicalizer copies the constraint tree, and a bound subquery cannot be copied. So the DECIDE block makes PlanSubqueries flatten every subquery at once, even inside another flattening, where DuckDB would otherwise defer it. Without that, a subquery inside a nested DECIDE would fail.

AddConstraint and SetObjective

After planning, the constraints and the objective change only through two methods. Assigning either field directly would skip canonicalization and its checks.

  • AddConstraint canonicalizes the new constraint, verifies it, and joins it to the tree with AND. It verifies only the new subtree, so many appends cost linear time.
  • SetObjective canonicalizes and verifies the replacement. The constant it peels off is added to objective_constant_offset, not assigned, so the constant the user wrote survives every rewrite.

The optimizer emits every constraint it writes through AddConstraint and every objective through SetObjective. With the call in plan_select_node.cpp, these are the only three places the canonicalizer runs (one shape boundary).

What the node carries

Grouped by who writes it:

Binder
The decisions and their is_boolean_var flags, the constraints, the sense, the objective, each decision's scope, the key table (keys), the key scopes, and the text of the clause (source_text, a DecideSourceText).
Canonicalizer
objective_constant_offset, and scope_checks: the checks of each clause that run on the data before the solve.
Optimizer
The solver's name, the constructs it states natively, the number of auxiliary variables, the labels and records of each rewrite, and the prepared linear form.

The solver is named, not held. The optimizer settles which backend runs the query, and the plan carries the answers: solver_backend_name, use_native_constructs and force_native_constructs. A live solver handle would let a logical plan open a solver session, which is the solver stage's job. A name cannot: execution turns it back into a backend with a registry lookup, where the solve runs.

One list of expressions. LogicalDecide::EnumerateExpressions visits every field that holds an expression execution evaluates: the decisions, the constraints, the objective, the key table, the scope checks and the side vectors the optimizer fills. DuckDB's column pruning and binding resolution walk that list, so a key column only a declaration names (per region: x) stays in the scan, and every field gets chunk positions. A field missing from the list would read a logical index as a chunk position, an error a single-table query hides and a join reveals.

Serialization

LogicalDecide serializes through DuckDB's generator. Its fields are listed in logical_operator.json, the structs they hold (DecideKey, KeyedScopeInfo, DecideScopeCheck, DecideSourceText and others) in nodes.json, and scripts/generate_serialization.py writes both directions. There is no hand-written copy that could drift. Property ids are a running checkpoint, not keys: the reader expects the next field in the stream to be the one it reads, so write order and read order come from one list. A retired field stays in the list marked "deleted": true.

The wire carries bound plans only. LogicalDecide::optimized is set before the optimizer's first rewrite, and from that point SupportSerialization() returns false. The optimizer chooses a formulation for this host's solver, so an optimized plan is an answer for one machine. It declines to be copied rather than arrive elsewhere as a formulation that machine cannot run; the optimizer rebuilds it from the canonical tree wherever the plan lands.

PRAGMA verify_serializer round-trips the bound plan and replaces the live plan with the copy, so a field that never reaches the wire becomes a wrong answer, not a silent omission. Run over the whole suite, it guards every field with no per-field test:

Shell
DECIDB_VERIFY_SERIALIZER=1 make decide-test
