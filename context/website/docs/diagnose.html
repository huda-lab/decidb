The router

A solve can end four ways: solved, infeasible, unbounded or stopped by a limit. The router is the one place that decides what each ending turns into: the query's rows, a diagnosis engine, or the plain error.

This page explains how DIAGNOSE works inside. What it returns and how to read it are on the Novel features page; the Guide shows when to reach for it.

Three terms recur. Infeasible means no assignment of the decisions meets every constraint. Unbounded means the objective can improve forever, because nothing stops some decision from growing. A terminal is one leaf of the router's decision tree: where a run ends up.

From prefix to operator

DIAGNOSE is a statement prefix, built the way DuckDB builds SUMMARIZE: one grammar alternative and a flag. The flag travels with the plan and is never read from a session setting, so a query without the prefix never pays for a diagnosis.

  1. Parser. DIAGNOSE SelectStmt is an alternative of VariableShowStmt and sets is_diagnose. The transformer makes a ShowRef of type DIAGNOSE, so FROM (DIAGNOSE ...) works through the grammar's existing parenthesized form.
  2. Binder. Binder::BindDiagnose binds the inner query unchanged and counts its DECIDE operators. A query with none, or with more than one, is refused here: one relation cannot say which solve it describes. It sets LogicalDecide::diagnose on the one operator and puts a LogicalDecideDiagnose above it, whose output columns are fixed at this point.
  3. Optimizer. A query under the prefix keeps the solver path: query rewriting does not run, because a rewritten query has no model to diagnose. The solver backend is chosen here, once, and every diagnostic solve later runs on that same backend.
  4. Execution. PhysicalDecide::diagnose arms what the engines need: ray extraction, rows for one-decision clauses that would otherwise become column bounds, and a copy of the model input to formulate the repair model from.

Why an operator and not a different result? The decision columns are bound into the query's output before the solve runs, so a failed solve cannot switch the result's columns at run time. A prefix declares the findings' columns at bind time instead, which makes DIAGNOSE a different statement, as EXPLAIN is.

From status to terminal

The solve facade, SolveModel, returns a status rather than throwing (see A status, not an exception). Before the router sees that status, the facade settles what it can:

  1. Proven before solving. A model whose own bounds contradict, such as x >= 5 AND x <= 1 folded into one column, is answered INFEASIBLE without reaching a backend (SolverModel::ProvesInfeasible). The model is kept, so the clause can still be named.
  2. Solve on the backend the optimizer chose.
  3. Settle an ambiguous status with a second, zero-objective solve (next section).
  4. Catch a false optimum. No MIP solver represents an unbounded integer: both backends cap an integer column near 2e9 and report the answer as optimal. An optimum on that ceiling, for a column the query left open, is reported as UNBOUNDED.
  5. Find a ray, under the prefix only, for an unbounded result (see The ray).

RouteSolveResult then maps the status and the prefix flag to a terminal. It is a pure function: it runs no engine and touches no DuckDB operator, so its whole decision tree is tested without a solver.

SUBOPTIMAL is a feasible answer Gurobi could not prove best; it is delivered with a warning. A time limit or Ctrl-C is not a diagnosis at all: the operator handles it before the router runs, with or without the prefix. UNDIAGNOSED raises the plain error, which states the outcome and, for an infeasible or unbounded query, names the prefix.

PhysicalDecide::Finalize calls the router once and switches on the terminal. That switch is the only dispatch site. SOLVED stores the solution; UNBOUNDED and INFEASIBLE run their engine and hand its findings up; UNDIAGNOSED throws. Each engine is a free function whose dependencies arrive as callbacks (dependency injection): the infeasible engine's solver call, the unbounded engine's categorical candidates. So an engine can change behind its terminal without touching the router, and is tested without DuckDB's operators. Under the prefix, a query that solves returns one row:

Infeasible or unbounded

Some solvers stop at an ambiguous answer, INF_OR_UNBD: "infeasible or unbounded". HiGHS gives it for an unbounded integer model. An improving direction alone does not settle it, because a model with no solution can have one: x - y <= -10 AND y - x <= -10 has no solution, yet raising x and y together leaves both rows unchanged and improves MAXIMIZE x forever.

So DisambiguateInfOrUnbd solves a copy of the model with its objective replaced by zero. That copy cannot be unbounded. If it solves, the region is not empty and the original is UNBOUNDED; if it is infeasible, so is the original. Every solve goes through this step: the primary solve and every diagnostic one.

When the zero-objective solve cannot decide either (it hits a limit or fails), the status stays INF_OR_UNBD and the router lets the ray choose. A ray sends the run to the unbounded engine; if that engine cannot name a decision, its finding keeps state = 'infeasible or unbounded' rather than hide the doubt. No ray means no improving direction, so the run goes to the infeasible engine.

src/decidb/diagnostics/decide_router.cpp
case SolverStatus::INF_OR_UNBD:
	if (!armed) {
		return DiagnosisTerminal::UNDIAGNOSED;
	}
	return result.ray.empty() ? DiagnosisTerminal::INFEASIBLE : DiagnosisTerminal::UNBOUNDED;

The infeasible engine

An infeasible query has no answer as written. The infeasible engine builds a second optimization, the elastic model, whose optimum is the smallest edit to the user's own clauses that gives the query an answer.

The elastic model

The elastic model is the standard tool of infeasibility analysis. Each constraint gets a slack: a new variable, zero or more, that lets its bound stretch. The model's objective minimizes the stretch. When the conflict lies in rows that can stretch, the elastic model has a solution although the query has none, and the slacks above zero name the clauses to loosen and by how much.

Slack on each relaxable row
a·x <= b   becomes   a·x - s <= b            s >= 0
a·x >= b   becomes   a·x + s >= b            s >= 0
a·x  = b   becomes   a·x - s⁺ + s⁻ = b       s⁺, s⁻ >= 0

A slack is continuous and uncapped, even on an integer bound. Only rows the user can edit get one. Each model row carries a role (ConstraintKind):

USER_PARAMETER
a row of a clause the user wrote, carrying a bound they can change. It gets a slack.
USER_MECHANISM
a helper row of a user clause, such as the rows a <> or a hard MAX lowers into. It stays rigid.
STRUCTURAL
a definition the formulation adds, such as a McCormick envelope for a product of decisions. It stays rigid.

A slack on a mechanism row would be measured in the mechanism's units, and it would name a clause the user never typed. So the repair goes to rows that carry the user's own bound.

One clause often becomes many rows. per category: SUM(x) by (category) >= 3 becomes one row per category. The engine puts the slack on the knob the user edits, not on each row: the rows of one clause share one slack, which settles at the largest shortfall. That one number is the edit to the literal that fixes every row. This is why DeciDB builds the elastic model itself instead of calling Gurobi's feasRelax, which puts one slack on each row; it also means the engine runs the same way on HiGHS.

The bag has three tech items and two gear items. The gear row can reach 2, so the shared slack is 1 and the literal moves from 3 to 2. One slack gives one edit: the literal the user wrote, not a separate number per category.

The repair model is formulated, not patched. The constants a lowering derives, such as a Big-M (a large constant that switches a row off when a binary is 0), are sized from each decision's range as the query states it. A repair often widens that range, so slacks added to the solved model would be capped by constants sized for the old range. Instead, FormulateElasticModel runs the formulation pass again on the model input as it stands before any constant is derived, with each column's range widened by OpenElasticColumnBox. A column widens by ten times its own magnitude, or by what one row demands of it (the row's bound divided by the column's coefficient), whichever is larger. The widening is per column, so a large number in one clause does not inflate the constants of an unrelated column. A type's own range, such as a BOOL's 0 and 1, never widens.

Finding the smallest edit

"Smallest" is lexicographic: a priority order where each step keeps the optimum of the steps before it. DiagnoseInfeasible runs these steps:

  1. Unreachable bounds. A clause that demands that a sum reach +inf or -inf cannot be repaired by any finite amount. Each one is reported as unreachable_bound, with no amount, and no elastic model is built.
  2. Fewest removed clauses. Some clauses have no bound to loosen: <>, IN (...) and a constraint with an L0 norm. Each is one removal group, dropped whole with every row it lowers into, or kept. The engine tries no removal, then each single removal, then each pair, and stops at the first count with a repair: an exact search by increasing cardinality.
  3. Least data offset. A bound read from a column, such as ship <= available, has no literal to edit; loosening it says the data conflicts. This total is minimized and frozen, as a row of the model, before the next step, so an editable literal wins whenever one alone can restore an answer.
  4. Least editable loosening, weighted. Slacks of different clauses are in different units: a count of items, kilograms, dollars. Each editable slack is weighted by ref / rms(a), where rms(a) is the root-mean-square of the row's coefficients (its typical magnitude) and ref is the smallest such value. The objective then measures how far a boundary moves per unit of decision, so a count floor is not gutted to zero when a dollar budget is the clause that is actually tight. The root-mean-square, unlike the plain vector length, does not grow with the number of terms, so a many-term floor is not made cheaper to loosen for its length alone.
  5. Best objective. Among the repairs of that size, pick the one best for the query's own objective (The achievable objective).
  6. Ties by written order. When two repairs tie on every step above, one more solve weights each slack by its clause's position and prefers the earlier clause (BuildTieBreakModel), so Gurobi and HiGHS name the same clause in common ties.
  7. Certified amounts. A solver returns slacks with rounding noise: an exact 7 can arrive as 7.00000028. The engine prints the tidiest reading of the amounts (rounded to nearest, noise dropped) only if the elastic model, with every slack fixed at those amounts, still solves. Otherwise it rounds outward. The last reading keeps every amount and repairs by construction, so a printed edit always works.

Slack scope

The setting diagnose_decide_infeasible_slack_scope answers two different questions with the same engine. query, the default, answers "which literal in my SQL do I change?" expanded answers "which generated rows or classes are tight?"

The whole difference is how BuildElasticModel groups slacks. Two small functions decide it: folds() says whether a row shares a slack, and block_key() says with which rows. In the query scope the key is the clause's repair group alone, so every class of a per clause shares one slack, and a bound read from data folds into one offset. In the expanded scope the key adds the row's class, so each per class gets its own slack, and a data bound keeps one slack per row. The bag above, under expanded, reports one finding for gear, with gear in the group column.

The achievable objective

The steps above find how much repair is needed, but several repairs often cost the same. In the order lines above, lowering the floor ship >= ordered by 7 is the same size of edit as raising the cap, and it also restores an answer, but it leaves the total at 100. Raising the cap gives 128.

So a second stage (BuildStage2Model) freezes the repair budgets found so far as rows of the model (data offset at most its minimum, editable loosening at most its minimum), restores the query's own objective, and solves again. It reports the edit of that solution together with its objective, so the edit and the number agree: the cap, and 128.

  • The value is shown as the query states it. The model always minimizes, so a MAXIMIZE value is negated back, and the objective's constant term, which no solver receives, is added back.
  • If the repaired model is unbounded, the engine keeps the edit and adds an unbounded_after_fix finding: the fix works, but the objective can then grow without limit. It does not hand over to the unbounded engine, since the edit is the part the user can act on.
  • A query with no objective has no second stage and no achievable_objective row. Its ties go to the earlier clause.

The unbounded engine

An unbounded query can improve its objective without limit. The fix is always a bound, so the engine's job is to name the decision that needs one and the rows where it escapes. The value of the bound is the user's to choose.

The ray

A ray (a recession direction) is a direction d along which any feasible point can move forever, staying feasible and improving the objective. Its nonzero entries are the escaping columns. Solver ray APIs exist but differ: Gurobi's returns a ray for continuous models only, and HiGHS's costs an extra solve. DeciDB builds a small linear program of its own from the model instead (BuildUnboundedRayFallbackModel), which runs on either backend:

The ray model
minimize    c·d                    the model's own objective
subject to  aⱼ·d  (<=, =, >=) 0    each linear row, its bound replaced by 0
            0 <= dᵢ <= 1           column i open above
           -1 <= dᵢ <= 0           column i open below
           -1 <= dᵢ <= 1           column i open both ways
                 dᵢ  = 0           column i bounded on both sides, or in a non-linear part
            d continuous

Replacing every bound by 0 keeps only the directions the feasible region extends in forever. The unit box keeps this program bounded, so it always finishes. A ray exists when the program improves the objective by more than DIAGNOSTIC_RAY_EPSILON (1e-8). A column with both bounds finite is fixed at 0, so every nonzero entry is already a suspect, with no further filter.

A column inside a square, a product, a native general constraint or an indicator is held at 0. Along such a ray every non-linear part keeps its value, so the ray is a true escape and never an artifact of relaxing a square. The cost: a runaway inside a square finds no ray, and the engine reports one undiagnosed finding saying a non-linear term prevents naming the decision.

The integer ceiling the facade catches (From status to terminal) needs no ray model: the pinned column is the escaping direction, and the facade hands it over as the ray.

Naming the runaway

Each solver column maps back to a decision and an instance: the row, for a decision per row, or the class, for a keyed decision (Provenance). DiagnoseUnbounded groups the escaping columns by decision. When only some instances escape, it looks for a categorical column that explains which.

  • A candidate column has from 2 to max(diagnose_decide_min_categories, diagnose_decide_categorical_ratio × rows) distinct values (defaults 20 and 0.1), which keeps out continuous and id-like columns on large tables.
  • For each value, the share of its instances that escape is its escape rate. A value whose rate reaches diagnose_decide_escape_rate (default 0.8) becomes a slice finding.
  • Slices that pick out exactly the same escaping instances state one fact, so they collapse to one: a column the DECIDE clause reads wins over one that only rides along in the SELECT.
  • If whole slices (rate 1) cover every escaping instance, the suggested cap is scoped with a when, so pasting it back does not cap rows that already have a bound. Otherwise the cap stays global: capping extra rows is only over-restrictive, while missing one runaway would leave the query unbounded.

The cap exempts the West, and both West routes escape: 2 of 2, so the slice region = 'West' covers every runaway and the cap is scoped to it. The objective reads margin, but each margin value holds one escaping route out of three, below the threshold, so it explains nothing and is not reported.

Column names come from the clause's own column references and, for the rest, from the names the binder resolved (LogicalDecide::source_columns), so a column reads the same through a table, a VALUES alias list or a CTE. A computed column with no AS name gets none and is never used as a slice.

A decision, not a clause

The ray names a missing bound. It cannot blame a clause: a constraint with its sign flipped has the same escaping direction as one never written. So an unbounded finding prescribes a bound to add and never points at an existing clause.

Shared foundations

Both engines stand on the same base: a solve that returns its status, a map from every model row and column back to the user's query, and a handoff that turns findings into the statement's answer.

A status, not an exception

Every solve returns a SolverResult: a SolverStatus (OPTIMAL, INFEASIBLE, UNBOUNDED, INF_OR_UNBD, TIME_LIMIT, SUBOPTIMAL, ITERATION_LIMIT or OTHER), the solution, the objective, the ray when one is extracted, and whether a diagnostic solve ran out of time. Each backend maps its own codes to these and returns; only a genuine API error throws. The plain message of a query without the prefix is written in one place, ThrowDecideSolveError.

Diagnosis adds solves: the zero-objective probe, the ray program, the elastic passes. Each runs through SolvePreparedModel with a budget of the smaller of 60 seconds and the query's own time limit, and with the same Ctrl-C check as the primary solve. When diagnosis runs out of time, its finding says so instead of guessing. Each runs on the backend the primary solve used, chosen once at planning: a failure is diagnosed on the solver that produced it.

Provenance

A diagnosis reports in terms of clauses, but the solver sees rows and columns. Provenance is the record, on every row and column, of where it came from. Each model row carries a ConstraintProvenance, stamped where the model builder emits the row, with separate identities for separate questions:

source_clause_id
which written clause to quote.
repair_group_id
which rows share one slack.
removal_group_id
which rows are dropped together.
group_key, class_set, data_row
which by group, per classes or data row the row stands for.
kind, shape
the row's role, and whether its bound is one literal shared by every row (SHARED_SCALAR) or read from data (PER_ROW_DATA).

Columns carry a ColumnProvenance: a user decision, an auxiliary or a global helper, with the decision's name and its instance. The unbounded engine reads it to name a runaway.

A clause is quoted as written. The canonicalizer rewrites clauses into one shape, decisions on the left (Canonical form). When both sides of a comparison hold decisions, the canonical row is a clause the user never typed:

SQLRuns as shown
SELECT depot, ship, open FROM Depots
DECIDE ship(REAL), open(BOOL)
SUCH THAT ship BETWEEN 0 AND capacity * open
      AND ship >= demand
MINIMIZE SUM(open)
EXPLAIN: the DECIDE node
DECIDE
  Variables: ship, open
  Objective: MINIMIZE SUM(open)
  Constraints:
    ship BETWEEN 0 AND capacity * open
      ≡ ship >= 0
      ≡ ship - capacity * open <= 0.0
    ship >= demand

So the binder records each clause's written text in a source registry (ConstraintSourceInfo) before canonicalization runs, and a finding quotes that text, as a compiler underlines the source in an error rather than reprinting its syntax tree. An offset added to a bound means the same in either form, so the repair reads against the written clause:

SQLRuns as shown

The findings relation

An engine returns a DecideDiagnostic: one state and a list of findings, each with real types (amount a DOUBLE, row a BIGINT). Getting it to the user takes two operators in the same plan:

  1. Write. PhysicalDecide writes the diagnosis to a state that lives for one statement (DecideDiagnosticState, a DuckDB ClientContextState) and emits no rows. A solve that succeeds clears that state instead.
  2. Take. PhysicalDecideDiagnose, directly above, is a sink that swallows the query's rows. In its Finalize it takes the diagnosis (TakeDecideDiagnostic), which clears it, or finds none and reports feasible.
  3. Emit. As a source, it emits one row per finding (RenderDecideDiagnostic) in the columns GetDecideDiagnoseSchema defines.

Because the state lives for one statement, there is no stale diagnosis and no id to manage, and the result composes like any relation: the DIAGNOSE example filters it in a subquery. Four session settings tune the engines; they change how a diagnosis is computed, never whether one runs.
