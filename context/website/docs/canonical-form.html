The canonicalizer

One planning boundary decides the shape of every constraint and of the objective. Every later stage reads that shape and never decides it again.

A user can write one constraint many ways: 5 >= x or x <= 5, SUM(x * w) or SUM(w * x), 2 * (x - 1) or 2 * x - 2. If each later stage had to accept every spelling, each would carry its own list of cases, and the lists would drift apart. So the canonicalizer writes one form per meaning, as a compiler's canonicalization pass does (LLVM's InstCombine is the standard example), and every later stage matches that one form.

One shape boundary

The canonicalizer runs at exactly three places, and there must not be a fourth:

Entry pointCovers
Binder::CreatePlan, after PlanSubqueriesthe constraints and the objective the user wrote
LogicalDecide::AddConstraintevery constraint the optimizer writes
LogicalDecide::SetObjectiveevery objective the optimizer rewrites

It runs after binding for two reasons. A decision is exactly a bound column reference on the DECIDE operator's table index, an identity the parsed tree does not have. And it must see the flattened subqueries that PlanSubqueries produces. At the first entry point, the order is:

src/planner/binder/query_node/plan_select_node.cpp
if (statement.decide_constraints) {
	canonicalizer.BuildConstraintScopeChecks(*statement.decide_constraints, scope_checks);
	statement.decide_constraints = canonicalizer.CanonicalizeTree(*statement.decide_constraints);
	canonicalizer.VerifyCanonical(*statement.decide_constraints);
	FinalizeConstraintSourceInfo(*statement.decide_constraints, statement.decide_constraint_sources,
	                             statement.decide_text, statement.keyed_scopes, statement.decide_index,
	                             &statement.decide_keys);
	shape_check.CheckConstraints(*statement.decide_constraints, statement.decide_constraint_sources);
	canonicalizer.SkipNullData(*statement.decide_constraints, statement.keyed_scopes,
	                           statement.decide_keys);
}

The scope checks read each clause as bound; the shape check reads it as canonicalized; and SkipNullData adds a tagged IS NOT NULL test to a reducer's filter for each data factor of its body, so a reducer skips a NULL the way SQL's aggregates do.

Every rule of the pass is an identity: for every input it gives the same value, type, NULL and error under DuckDB's evaluation. The pass is also:

  • Total. It never declines an input. A pass that may decline cannot be the single home of anything: every stage after it must handle both "it ran" and "it declined", and the declined branch is where duplicate implementations come from.
  • Pure. It takes a tree by const reference and returns a new one, so the written form and the canonical form are both alive at the call site. That is what lets EXPLAIN print both.
  • A fixed point. Canonicalizing a canonical tree changes nothing.

A rewrite belongs here only if it also reads nothing but what binding knows, serves every later stage rather than one back end, and removes a variant some later stage checks. That keeps the pass from becoming a second optimizer: a rewrite that needs a key or a NOT NULL holds only for some tables, and a form one solver prefers is a formulation choice.

Decisions left, the bound right

The pass splits each side of a comparison into additive terms (a + b into +a and +b, a - b into +a and -b) and asks one question of each term: does it reference a decision? A term that does goes left; a term that does not goes right, with its sign flipped. If every decision is on the right, the sides swap and the operator flips. It then merges like terms, and distributes a factor known before the query runs over a sum, as a negation already distributes:

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT 3 >= x
      AND SUM(x * weight) + 5 <= 60
      AND 2 * (x - 1) <= 3
      AND x + 1 >= 2 * x - 1
MAXIMIZE SUM(value * x)
EXPLAIN: the DECIDE node
DECIDE
  Variables: x
  Objective: MAXIMIZE SUM(value * x)
  Constraints:
    3 >= x
      ≡ x <= 3
    SUM(x * weight) + 5 <= 60
      ≡ sum(weight * x) <= -5 + 60
    2 * (x - 1) <= 3
      ≡ 2 * x <= 2 * 1 + 3
    x + 1 >= 2 * x - 1
      ≡ -1 * x >= -1 - 1

Each ≡ line is the canonical form EXPLAIN prints under the clause as written. Read them one at a time:

  • 3 >= x has its decision on the right, so the sides swap: x <= 3.
  • The constant 5 crosses with its sign flipped, and the product takes its one spelling, data first: sum(weight * x) <= -5 + 60.
  • The 2 is known before the query runs, so it distributes: 2 * x <= 2 * 1 + 3.
  • x and 2 * x are like terms; the left side bears a decision, so the operator stays and the terms merge: -1 * x >= -1 - 1.

The pass never folds constants (it leaves -5 + 60 for execution to add), never multiplies out a power or a product of sums, and never opens an ABS, a MIN, a MAX or a subquery. A quadratic POWER(x - t, 2), a composed MAX(x * v) and a filtered SUM(when c: x) are each one decision-bearing term, as plain as x. A data-only reducer carries no decision, so it goes right like any other data. One look inside a term is allowed, because it holds for every body: a MIN or MAX hands its constant addends to the bound (max(x + 0.75) > 7 is max(x) + 0.75 > 7), since adding one number to every row does not change which row is extreme.

A factor stays outside its reducer

A factor on a reducer (2 * SUM(x), SUM(x) * 2, SUM(x) / 2) has one canonical place: outside the reducer, written factor * AGG or AGG / factor. PeelScale is the one function that judges it, and it peels to exhaustion, so 2 * (3 * SUM(x)) yields one factor.

Outside, because MIN and MAX are order statistics, not linear functions: they commute with a positive factor only. MAX(-2 * x) is -2 * MIN(x), not -2 * MAX(x). Pushing a factor inside therefore needs its sign, and a scalar subquery's sign is unknown until the query runs. Kept outside, the sign never affects correctness; it only selects the cheaper formulation, so an unknown sign costs time instead of failing.

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3
      AND SUM(x) * 3 <= 12
      AND (SUM(weight * x) + 10) / 2 <= 30
      AND 2 * (MIN(value * x) - 10) >= -20
MAXIMIZE SUM(value * x)
EXPLAIN: the DECIDE node
DECIDE
  Variables: x
  Objective: MAXIMIZE SUM(value * x)
  Constraints:
    x <= 3
    SUM(x) * 3 <= 12
      ≡ 3 * sum(x) <= 12
    (SUM(weight * x) + 10) / 2 <= 30
      ≡ sum(weight * x) / 2 <= -(10 / 2) + 30
    2 * (MIN(value * x) - 10) >= -20
      ≡ 2 * min(value * x) >= 2 * 10 + -20
      ↳ min(value * x) becomes a bound on each member

The last clause shows why a known factor distributes. Left as one product, 2 * (MIN(...) - 10) would be a reducer inside an expression, the value shape below. Distributed, it is a plain MIN term, which the optimizer turns into one bound per member (the ↳ line).

What may be a factor:

  • A constant, an uncorrelated subquery, or arithmetic over query-wide values: anywhere.
  • A column, or a correlated subquery: in a constraint, where each row has its own value and the comparison takes the value shape; never in the objective, which is produced once (subquery provenance).
  • A BOOL decision on a bare reducer (b * SUM(x)): the optimizer holds the reducer in a helper decision and linearizes the product.
  • Any other decision: never. An INT or REAL decision times a reducer is not convex.

One spelling per product

Every product of decisions takes one spelling: a coefficient on the left (a constant, data, or a product of data) times decision factors, each raised to a whole power. NormalizeProducts is a bottom-up rewrite rule over every * and whole-exponent POWER that holds a decision, in the manner of DuckDB's ArithmeticSimplificationRule over constants. It merges equal factors into powers, comparing a sum as a multiset of signed terms, so (x + y) * (y + x) is a square.

WrittenCanonical
2*x*x, x*2*x2 * POWER(x, 2)
w*x*x, x*w*x, POWER(x, 2)*ww * POWER(x, 2)
(x-t)*(x-t)POWER(x - t, 2)
(x+y)*(y+x)POWER(x + y, 2)

POWER(x, 1)x
POWER(x, CAST(2 AS INTEGER))POWER(x, 2)

The rule never expands a square and never folds data: it composes data factors into the coefficient with *, so SQL's own arithmetic over the data runs as written, overflow included. With a BOOL decision every square is linear (b * b is b), so this example runs on any solver, and the ↳ lines show the optimizer's next step:

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(BOOL)
SUCH THAT SUM(x * weight * x) <= 45
      AND SUM(x*2*x) <= 6
      AND SUM(POWER(x, 1) * weight) >= 10
MAXIMIZE SUM(value * x)
EXPLAIN: the DECIDE node
DECIDE
  Variables: x
  Objective: MAXIMIZE SUM(value * x)
  Constraints:
    SUM(x * weight * x) <= 45
      ≡ sum(weight * power(x, 2)) <= 45
      ↳ sum(weight * x) <= 45
    SUM(x*2*x) <= 6
      ≡ sum(2 * power(x, 2)) <= 6
      ↳ sum(2 * x) <= 6
    SUM(POWER(x, 1) * weight) >= 10
      ≡ sum(weight * x) >= 10

Across a clause's additive spine, like terms merge over products as over atoms: x*x + x*x is 2 * POWER(x, 2). Inside one reducer body they stay apart, and the term reader adds them into one coefficient later, so the model is the same. A respelled node takes the query location of the node it replaces, so a message about it underlines the term as the user typed it, as Clang underlines a source range rather than reprinting its syntax tree.

The objective

An objective is one side of a comparison, with no relation to orient and no bound to separate. CanonicalizeObjective uses the same decomposition, factor peeling and like-term merging as the constraints, which is the reason the objective goes through this boundary instead of a normalizer of its own. Two rules are its own:

  • Constant terms move to an offset. A term with no decision moves into objective_constant_offset. It shifts the objective's value without moving the best answer.
  • Every objective is a minimization. MAXIMIZE f is stored as MINIMIZE -f, the sign carried by each term (CVXPY's FlipObjective reduction does the same). The flip is the last step, so like terms merge in the written direction. Every later stage reads one sense; only messages, EXPLAIN and two reported values read the sense the user wrote.
SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3 AND SUM(weight * x) <= 50
MAXIMIZE SUM(x * value) + SUM(value * x) + 7
EXPLAIN: the DECIDE node
DECIDE
  Variables: x
  Objective: MAXIMIZE SUM(x * value) + SUM(value * x) + 7
    ≡ 2 * sum(value * x)
  Constraints:
    x <= 3
    SUM(weight * x) <= 50

EXPLAIN prints the canonical objective in the written sense, so the flip alone adds no ≡ line. The two sums merge into 2 * sum(value * x), and the 7 moves to the offset.

Casts

A solver model has one numeric domain, DOUBLE. That does not license erasing SQL casts: a data cast is a value operation (CAST(1.6 AS INTEGER) is 2), and dropping it would change a bound or a coefficient. Three rules follow:

  1. A cast the user writes over a decision is refused, whatever its target type. Only the parsed tree shows who wrote a cast, so the binder checks it (ValidateDecideNoExplicitDecisionCasts).
  2. A cast over data keeps DuckDB's meaning. The whole typed expression is evaluated first, and only its result becomes a DOUBLE at the solver's door.
  3. A cast the binder inserts over decision algebra is transparent. Once rule 1 has run, such a cast is type reconciliation, and UnwrapDecideCasts looks through it.
SQL
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT SUM(CAST(x AS DOUBLE) * weight) <= 50
MAXIMIZE SUM(value * x)
Errorrefused before solving
Binder Error: DECIDE does not allow casts over decision expressions: 'CAST(x AS DOUBLE)'. Decision values are modeled directly as DOUBLE. Remove the cast; casts over data-only expressions are allowed.

This is an authorship boundary, and that is why it cannot be reconstructed later. A cast the user wrote and a cast the binder added are both a BoundCastExpression, and whether a cast widens does not say who wrote it.

Per-row, aggregate and value shapes

ClassifyScoped reads each canonical comparison's decision side and names its shape, which fixes how many model rows the clause becomes:

Decision side holdsShapeModel rows
no reducerper-row (ROWS)one per kept row, or one per class of an enclosing per K:
reducers sharing one by key, beside terms that are one value per groupaggregate (AGGREGATE)one per by group
anything else: a per-row decision beside a reducer, a factor that varies by row, two by keys, a reducer inside an expressionvalue (VALUE)each reducer becomes a helper decision per group, then one row per class
SQLRuns as shown
SELECT S.shipmentID, ship
FROM Shipment S JOIN Depot D USING (depotID)
DECIDE ship(INT)
SUCH THAT ship <= S.demand
      AND per D.depotID: SUM(ship) by (D.depotID) <= D.capacity
      AND ship <= 0.40 * SUM(ship) by (D.region)
MAXIMIZE SUM(ship)
EXPLAIN: the DECIDE node
DECIDE
  Variables: ship
  Objective: MAXIMIZE SUM(ship)
  Constraints:
    ship <= S.demand
    per D.depotID: SUM(ship) by (D.depotID) <= D.capacity
    ship <= 0.40 * SUM(ship) by (D.region)
      ≡ ship - 0.40 * sum(ship) by (D.region) <= 0.0
      ↳ sum(ship) by (D.region) becomes a helper decision per group

The first clause is per-row: one row per shipment. The second is aggregate: one row per depot. The third compares each shipment with its region's total, which one row per group cannot hold, so it takes the value shape and the optimizer replaces the regional sum with a helper decision (the value rewrite).

A term beside the reducers is one value per group when its scope, the join of its factors' scopes on the lattice query-wide < key < per row (JoinDecideKeys), is the by key or query-wide. So the facility link per D: SUM(ship) by (D) <= cap * open, with open declared per D:, is aggregate: one row per depot, reading that depot's open.

Only the canonicalizer sees the enclosing scope, so it decides the shape once and stamps it on the comparison: the by key for the aggregate shape, VALUE_REWRITE_TAG for the value shape. The linear form, the value rewrite and query rewriting read the stamp instead of classifying again.

The scope checks

A clause written per K: is one constraint per class of K, so everything it reads outside its reducers must be one value per class. BuildConstraintScopeChecks and BuildObjectiveScopeChecks read each clause as bound and record DETERMINES checks on LogicalDecide::scope_checks: the clause's key must determine each data value, each decision outside a reducer and each by key, and a reducer's own per must determine its body. Execution runs every check before it reads a clause:

SQL
SELECT S.shipmentID, ship
FROM Shipment S JOIN Depot D USING (depotID)
DECIDE ship(INT)
SUCH THAT ship <= S.demand
      AND per D.region: SUM(ship) by (D.region) <= D.capacity
MAXIMIZE SUM(ship)
Errorrefused before solving
Invalid Input Error: DECIDE: per D.region does not determine D.capacity. D.region = 'North' has more than one value: 80, 100.

The checks run on the data, not as a static proof, because whether a key determines a column is a property of the rows. A static rule would refuse queries that are fine on their data. Two cases need no check: a literal or a query-wide value, and one of the key's own elements, which the key determines by construction (per a: SUM(x) by (a) builds no check for a). Key elements compare as rows group on them, collation included, as GROUP BY compares them.

The shape check

DecideShapeCheck is the one place the algebra of a clause is judged. It is the semantic-analysis pass of a compiler front end: the parser has refused syntax, the binder what only it sees, and what remains is whether the model has a reading for each term. It reads the one spelling the canonicalizer writes, so a shape has one reading however the user typed it, and it runs only on what the user wrote. It refuses:

  • a function or operator over a decision outside the vocabulary (+, -, *, division by data, a whole-exponent POWER, ABS and the reducers, under any name DuckDB registers for them), such as sqrt(x), x % 2 or COALESCE(x, 0);
  • a POWER whose exponent is not a whole number known before the query runs;
  • a division by a decision;
  • a CASE over a decision (a CASE over data is a per-row coefficient);
  • a term of degree above 2.
SQL
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3 AND SUM(x * x * x) <= 10
MAXIMIZE SUM(value * x)
Errorrefused before solving
Invalid Input Error: DECIDE: the SUCH THAT clause `SUM(x * x * x) <= 10` has a term of degree 3, which no solver DeciDB supports can optimize. Instead, write each term with at most two decision factors, as in x, POWER(x, 2) or x * y.

Degree is read by DecideDegreeOf, the one definition in the code base: a decision is 1, data is 0, a reducer has the degree of its body, +, - and ABS take their largest child, * adds, a whole-exponent POWER multiplies, and a division by data keeps its numerator's. Degree is not a count of occurrences: (x + y) * z has three and degree 2. Every refusal quotes the clause as written and carries the term's location, so the caret underlines it. The check runs before any optimizer rewrite, so whether a query is legal never depends on what a rewrite did.

Verification

VerifyCanonical and VerifyCanonicalObjective check the invariant without changing the tree: wrappers, decision side, placement, and a fixed-point test that canonicalizes a copy and compares the two. The comparison reads the expression's alias, where DECIDE keeps its tags, because DuckDB's Expression::Equals ignores it. They run at three points: after the user's clauses are canonicalized, on each subtree entering AddConstraint or SetObjective, and on the whole tree when the physical plan is built, after every optimizer rewrite.

A failure there is an engine bug, not user input, so it throws an internal error. The full check is debug-only, in the idiom of DuckDB's LogicalOperator::Verify: canonicalizing every tree a second time is too costly for release. The user-facing refusals of ValidateCanonicalTree are a separate function and run in every build.

The optimizer

The DECIDE optimizer picks a formulation for every construct a solver cannot take as written: ABS, MIN and MAX, AVG, <>, IN, norm and products of decisions. It reads canonical input and writes canonical output.

It runs as one of DuckDB's optimizer passes, OptimizerType::DECIDE_OPTIMIZER, and it is required, not an optional speedup: a plan the DECIDE optimizer never saw is refused at physical planning. Every constraint it writes re-enters through AddConstraint and every objective through SetObjective, so its output is canonical by construction. It never decides shape, parses SQL, reads data or calls a solver.

The solver comes first

The right formulation depends on what the backend states natively: a solver with a native absolute value needs no Big-M envelope, and lowering one anyway would only lose accuracy. So before any formulation rewrite, ChooseDecideSolver picks the backend and records three answers on the plan: solver_backend_name, use_native_constructs (the constructs it can state) and force_native_constructs (the policy over them). Nothing downstream picks again: the choice rides the plan to execution and to every diagnostic re-solve.

Capability is not policy, and MIN/MAX is where the two part. Gurobi can state a maximum as a general constraint, but measured on the Q9 benchmark shape at 30K rows the native form is 1.8 times slower than the lowering, and 41 times slower on a MAX(e) >= K constraint of the same size. So the native form is the fallback, used only where the lowering has no valid Big-M. Whether a clause has one depends on evaluated coefficients, so execution applies the recorded policy to data only it can see.

RequireDecideSolverSupport, the model-class gate, compares what the query demands with what the backend declares, once the prepared form exists. A construct the backend lacks is lowered; a model class it lacks is refused, since nothing lowers a quadratic constraint or a non-convex objective into linear rows. The gate runs at plan time, not bind time, because the same SQL is legal on every machine: the message blames the host and names the solver to install. And it runs before any row is read, because each class follows from the tree's shape and declared types alone.

Pass order

OptimizeDecide first runs RewriteRhsAggregates, which replaces each data-only reducer on a bound (sum(x) <= sum(cap)) with a column computed by DuckDB, grouped by its by key. Then ChooseDecideAnswer lets the query rewriting rules try the node (below); if none applies, it chooses the solver, and RewriteForSolver runs fifteen passes. The order is load-bearing:

#PassWhy here

2TagAtomicRemovalGroupsgives each clause an identity before any rewrite splits it into several rows, so DIAGNOSE removes a clause's rows together
3RewriteNormlowers norm(e, 0) before later passes meet the marker
4RewriteInDomainlowers x IN (...) to indicators

Each rewrite records what it made of a construct (rewrite_accounts). EXPLAIN prints each record under its clause as a ↳ line, followed by the rows the rewrite added. The examples below show them.

ABS

RewriteAbs replaces each ABS(e) over decisions with an auxiliary variable a and the lower envelope a >= e, a >= -e. That alone is exact when the clause pushes a down: SUM(ABS(e)) <= K, or MINIMIZE SUM(ABS(e)). Anywhere else (ABS(e) >= K, =, a subtracted ABS, MAXIMIZE), the solver could inflate a, so a also needs an upper envelope: a sign indicator with two Big-M rows, or the solver's native absolute value where it has one.

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3
      AND SUM(ABS(x - 2)) <= 4
      AND ABS(SUM(x) - 6) >= 2
MAXIMIZE SUM(value * x)
EXPLAIN: the DECIDE node
DECIDE
  Variables: x
  Objective: MAXIMIZE SUM(value * x)
  Constraints:
    x <= 3
    SUM(ABS(x - 2)) <= 4
      ↳ abs(x - 2) becomes an auxiliary variable
      ↳ abs(x - 2) - x >= -2
      ↳ abs(x - 2) + x >= 0 + 2
    ABS(SUM(x) - 6) >= 2
      ↳ abs(sum(x) - 6) becomes an auxiliary variable stated to the solver as an absolute value
      ↳ sum(x) becomes a helper decision
      ↳ abs(sum(x) - 6) - sum(x) >= -6
      ↳ abs(sum(x) - 6) + sum(x) >= 0 + 6

The first ABS is pinned by the clause, so its two envelope rows are all it needs. The second is pushed up, so its account names the upper envelope this host's solver uses: a native absolute value on Gurobi, a sign indicator on HiGHS. Its sum sits inside an expression, the value shape, so the sum also becomes a helper decision. TagAbsForBigM decides which ABS needs it by reading the sign each term carries, through +, -, casts, reducer bodies and constant factors (WalkPolarity). A factor whose sign is known only at run time, such as a data column in SUM(w * ABS(x - t)), gets the exact form: assuming it positive would be unsound, since a negative w lets the auxiliary grow and the constraint stop binding.

MIN and MAX

Each direction of an extremum has its own cost. MAX(e) <= K holds exactly when every member does, so the easy direction becomes one bound per member, with no new variable. MAX(e) >= K needs some member to reach K, which takes an extremum column pinned by indicator rows: binary variables with Big-M links. MIN is the mirror. ExtremumPushOf reads once which way a clause pushes a term, for every pass that needs it.

SQLRuns as shown
SELECT S.shipmentID, ship
FROM Shipment S JOIN Depot D USING (depotID)
DECIDE ship(INT)
SUCH THAT ship <= S.demand
      AND MAX(ship) <= 35
      AND MAX(ship) >= 30
      AND SUM(ship) + MAX(ship) <= 150
      AND AVG(ship) >= 20
MINIMIZE SUM(unit_cost * ship)
EXPLAIN: the DECIDE node
DECIDE
  Variables: ship
  Objective: MINIMIZE SUM(unit_cost * ship)
  Constraints:
    ship <= S.demand
    MAX(ship) <= 35
      ↳ max(ship) becomes a bound on each member
    MAX(ship) >= 30
      ↳ max(ship) becomes an extremum column pinned by indicator rows
    SUM(ship) + MAX(ship) <= 150
      ↳ max(ship) becomes an extremum column
    AVG(ship) >= 20
      ↳ avg(ship) becomes a sum divided by its row count
      ↳ sum(ship) >= 20

The optimizer marks a hard clause; it allocates no binary itself. It cannot see the data, so it cannot know whether a clause will take the native form or the lowering, and a binary per row for a native clause would reference nothing. The model stage allocates them once bounds are known (building the model).

A MIN or MAX beside other terms (SUM(ship) + MAX(ship) <= 150) is a composed term. RewriteComposedMinMax lifts each term into a ComposedMinMaxTerm, from which the model stage builds an extremum column for the clause's one row, and leaves a TRUE placeholder in the tree. A body that squares or multiplies decisions under a MIN or MAX is first named by a helper decision per row (DefineNonlinearReducerBodies), stated only in the direction the clause pushes it, as the Plaisted-Greenbaum encoding states a definition only in the polarity where it occurs.

NORM and IN

The canonicalizer replaces norm(e, 1), norm(e, 2) and norm(e, 'inf') with their definitions: SUM(ABS(e)), SUM(POWER(e, 2)) and MAX(ABS(e)). That swaps one term for another and opens nothing, so the pass stays total. norm(e, 0) counts the nonzero values, which needs indicator variables, a formulation, so RewriteNorm lowers it: one Boolean z per row, a forward link |e| <= M·z and a reverse link |e| >= tol·z. The reverse link makes the count exact; without it, SUM(z) would only bound the count from above. The tolerance must exceed the solver's feasibility tolerance; it is 1e-4 by default and set with decide_l0_tolerance.

RewriteInDomain lowers x IN (v1, ..., vk) to k indicators with z1 + ... + zk = 1 and x = v1·z1 + ... + vk·zk. x IN (v) is x = v, and x IN (0, 1) on a BOOL is dropped.

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3
      AND x IN (0, 2, 3)
      AND norm(x, 0) <= 3
MAXIMIZE SUM(value * x)
EXPLAIN: the DECIDE node
DECIDE
  Variables: x
  Objective: MAXIMIZE SUM(value * x)
  Constraints:
    x <= 3
    x IN (0, 2, 3)
      ↳ x IN (0, 2, 3) becomes one indicator per value
      ↳ (x = 0) + (x = 2) + (x = 3) = 1
      ↳ x + (0 - 0) * (x = 0) + (0 - 2) * (x = 2) + (0 - 3) * (x = 3) = 0
    norm(x, 0) <= 3
      ↳ norm(x, 0) becomes one indicator per row
      ↳ abs(x) becomes an auxiliary variable stated to the solver as an absolute value
      ↳ sum(x <> 0) <= 3
      ↳ M * (x <> 0) - x >= 0.0
      ↳ M * (x <> 0) + x >= 0.0
      ↳ abs(x) - 0.0001 * (x <> 0) >= 0.0
      ↳ abs(x) - x >= 0.0
      ↳ abs(x) + x >= 0

EXPLAIN names each indicator by what it stands for: (x = 2) for a value of the domain, (x <> 0) for a nonzero row. The second IN row is x = 0·z0 + 2·z2 + 3·z3 with every term moved left. M is the Big-M the model stage derives from the decisions' bounds, and 0.0001 is the tolerance. The norm's absolute value is stated natively or by a sign indicator, as for any ABS pushed up.

An unlowered marker is the worst failure here: it is a real SUM with the order in its alias, so a missed one would read as SUM(e) and give a confident wrong answer. VerifyNormMarkersLowered fails the query instead, at the end of the optimizer.

AVG and <>

RewriteAvgToSum replaces an AVG over decisions with a SUM tagged AVG_REWRITE_TAG, and execution divides its terms by the number of rows the reducer reads in each group (the AVG line in the MIN and MAX example above). An AVG over data alone is left as it is: there is nothing to linearize, and rebinding it as SUM would give it SUM's integral type while its value stays fractional.

A <> becomes a disjunction: <= K - 1 or >= K + 1, chosen by one binary with two Big-M rows. RewriteNotEqual only marks the clause and its label; the model stage allocates the binary once the bounds are known, for the same reason as a hard MIN or MAX. A fractional K on a whole-numbered side can never be equaled, so that clause always holds and is dropped.

Products of decisions

RewriteBilinear reads each product in its canonical spelling and picks by the factors' types:

FactorsFormulation
BOOL times BOOLan AND: w <= b1, w <= b2, w >= b1 + b2 - 1; no Big-M
BOOL times x in [L, U]a McCormick envelope, exact for a binary factor: w <= U·b, w >= x - U·(1 - b) and the L corners
BOOL squaredthe factor itself
neither factor BOOLleft in place for the quadratic (Q) matrix

The McCormick corners need the bounds L and U, which may come from the data, so the pass records the link and the model stage emits the rows. Each auxiliary takes its scope as DuckDB promotes a binary operator's type: the least upper bound of its factors' scopes, on the order query-wide < keyed < per row (JoinScopes). Two query-wide factors give one query-wide column, not one per row.

The value rewrite

A comparison in the value shape cannot be one row per group. RewriteScopedReducers turns it into a per-row clause: each reducer on its decision side becomes a helper decision, one per by group, defined by its own rows in the model. So ship <= 0.20 * SUM(ship) costs one row per shipment and one helper, not one row per shipment holding a term for every shipment.

SQLRuns as shown
SELECT S.shipmentID, ship
FROM Shipment S JOIN Depot D USING (depotID)
DECIDE ship(INT)
SUCH THAT ship <= S.demand
      AND per D.region: SUM(ship) by (D.region) <= 0.6 * SUM(ship)
MAXIMIZE SUM(ship)
EXPLAIN: the DECIDE node
DECIDE
  Variables: ship
  Objective: MAXIMIZE SUM(ship)
  Constraints:
    ship <= S.demand
    per D.region: SUM(ship) by (D.region) <= 0.6 * SUM(ship)
      ≡ per D.region: sum(ship) by (D.region) - 0.6 * sum(ship) <= 0.0
      ↳ sum(ship) by (D.region) becomes a helper decision per group
      ↳ sum(ship) becomes a helper decision
  • Type. A helper is INTEGER when the reducer's value is whole by declared types, so a strict bound on the new row still steps exactly; otherwise it is DOUBLE.
  • Sharing. One helper per reducer over one set of rows: a second occurrence with the same body, by key, own per and enclosing when reuses the first. Two helpers for one value could drift apart.
  • Sides. A helper's definition states only the side its clauses need, as an epigraph does: a SUM pushed down needs helper >= members. An unknown sign, = or <> needs both.

Bounds into boxes

x <= 10 is one fact about a column, so it belongs in the column's bounds, its box, rather than in one model row per data row. FoldSingletonRows folds every bound on one decision known before the query runs into one box per decision, as MIP presolve turns a single-variable row into a column bound. One classifier, DecideReadSingletonRow, reads every bound on one decision for this pass, the linear form and query rewriting, so they cannot disagree about which values a bound admits. It admits exactly what DuckDB admits: on an INT, 0.1 * x <= 0.3 admits 3, because DuckDB evaluates 0.1 * 3 as the exact decimal 0.3.

  • Tagged, not replaced. The comparison keeps its place in the tree with SINGLETON_ROW_BOUND_TAG, so EXPLAIN and DIAGNOSE still show the bound the user wrote.
  • Never under a when. when c: x <= 0 holds on some rows, so it is not a domain.
  • Intersect, never assign. x = 5 AND x = 10 inverts the box and is caught, instead of keeping whichever bound came last.
  • Last of all. An IN with a negative value emits a lower bound below 0, itself a bound to fold; folded earlier, the default floor of 0 would make that value unreachable and change the answer.

This is a formulation choice, bound or row, so it belongs here and not in the canonicalizer, whose pass is pure and never writes into bound arrays.

The prepared linear form

BuildDecidePreparedModel flattens each canonical comparison and the objective into terms, sign * coefficient * variable, and product groups for the terms of degree 2. This is where the algebra happens: K * (1 - pick) becomes K - K * pick, a divisor moves into every coefficient, and a reducer's factor multiplies everything the reducer produced. The result is LogicalDecide::prepared, a DecidePreparedModel.

A coefficient stays an unevaluated expression: SUM(x * price) yields the coefficient price, which is a number only once a row exists. Everything else about a term (its variable, sign, reducer, filter and key scope) is settled here, and no data is read. Like terms in a linear row merge, but only when they also read the same rows: sum(when a: x) and sum(when b: x) name one column over two row sets, and TermsAreLike keeps them apart.

The code is the optimizer's, but it runs from plan_decide.cpp, at physical planning. DuckDB's column pruning and late materialization run after the DECIDE optimizer and rebind the operator's expressions; a coefficient copied earlier would keep a stale binding and silently read the wrong column. Physical planning is the first point where bindings are final, and the same point where the final VerifyCanonical runs.

Where query rewriting enters

Query rewriting answers some queries with DuckDB's own operators instead of a solver. It enters at one point: ChooseDecideAnswer, after the bound-side rewrite and before the solver is chosen. A rule that applies replaces the DECIDE node with an ordinary plan, and none of the fifteen passes runs. A DIAGNOSE query, or one with a forced solver, keeps the solver path. The same table answers both ways. A capacity across rows needs the solver:

SQLRuns as shown
SELECT item, x
FROM Items
DECIDE x(INT)
SUCH THAT x <= 3 AND SUM(weight * x) <= 50
MAXIMIZE SUM(value * x)
EXPLAIN: the operators
PROJECTION
└─ DECIDE   decisions: x
   └─ SEQ_SCAN   Items

With only a box on each row, every row is independent, and rule A1 computes each value with DuckDB's own operators, with no solver:

SUCH THAT x <= 3

The rules read the canonical tree through their own intermediate representation, so they see the same one spelling as the passes on this page. How a rule recognizes its class and builds its plan is in query rewriting, and each rule is in the rewrite rules.
