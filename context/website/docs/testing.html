How a test judges an answer

A correctness test never compares DeciDB's answer with a number its author worked out. It states the same problem a second time, to a solver DeciDB does not touch, and requires the two answers to agree.

The second statement is the oracle: a test oracle, the standard name for the source of truth a test checks a result against. In DeciDB's suite it is a model written by hand in Python with gurobipy, Gurobi's Python interface. This is differential testing (McKeeman, 1998): two independent implementations of one problem, run on the same input, must agree. Each correctness test takes five steps:

  1. Run DeciDB. The query goes to the DeciDB command-line binary, and the test reads the rows it prints.
  2. Read the same data elsewhere. The test reads the input rows with stock DuckDB, never through DeciDB. For the tests over TPC-H tables that is a database of its own at scale factor 0.01, made by the same deterministic generator as DeciDB's, so the rows are identical.
  3. State the model. The test builds the model in Python from those rows: one variable per decision, one constraint per clause, the objective.
  4. Solve it with Gurobi.
  5. Compare. compare_solutions checks the objective and the decision vector.

A knapsack over TPC-H's lineitem table shows the shape. The query is ordinary DECIDE SQL:

test_var_boolean.py: the query
SELECT l_orderkey, l_linenumber, l_extendedprice, l_quantity, x
FROM lineitem
WHERE l_orderkey < 100
DECIDE x(BOOL)
SUCH THAT SUM(x * l_quantity) <= 100
MAXIMIZE SUM(x * l_extendedprice)

The oracle states the same problem as numbers, with no DECIDE clause, no DeciDB code, and none of DeciDB's choices about how to write a clause:

test_var_boolean.py: the oracle
    oracle_solver.create_model("q01_knapsack")
    vnames = [f"x_{i}" for i in range(len(data))]
    for vn in vnames:
        oracle_solver.add_variable(vn, VarType.BINARY)

    oracle_solver.add_constraint(
        {vnames[i]: data[i][3] for i in range(len(data))},
        "<=",
        100.0,
        name="capacity",
    )
    oracle_solver.set_objective(
        {vnames[i]: data[i][2] for i in range(len(data))},
        ObjSense.MAXIMIZE,
    )
    build_time = time.perf_counter() - t_build
    result = oracle_solver.solve()

What agreement means

compare_solutions makes two checks:

  • The objective. It recomputes DeciDB's objective from DeciDB's own rows, never from a value DeciDB reports, and requires it to match the oracle's within 1e-4. A linear objective is recomputed from a coefficient per row; a quadratic one from a function the test supplies.
  • The decision vector. It sorts both answers by their data columns and compares them row by row. The result is identical when the vectors match, and optimal when they differ but reach the same objective: an alternate optimum, which is a right answer too.

A query with no answer is judged the same way. assert_infeasible checks that DeciDB reports the query infeasible or unbounded, and the test states the model to the oracle as well and checks that Gurobi agrees. That catches DeciDB calling a feasible problem infeasible, not only the reverse.

Why the oracle is independent

The oracle shares nothing with DeciDB's model builder, on purpose. A test that reused DeciDB's own code to state the expected model would agree with DeciDB whenever both are wrong in the same way, a lockstep bug. The bugs that matter most in an optimizer are exactly of that kind: a wrong coefficient, a constraint pointing the wrong way, a Big-M too small to switch a row off. Each one returns a plausible answer that is not the optimum.

  • No shared data path. The oracle reads its rows with stock DuckDB from a separate file. No DeciDB parser, binder or coefficient evaluation stands between the data and the model.
  • No shared formulation. Where DeciDB writes a construct with Big-M rows, the oracle states the construct's meaning with a different tool. For <>, add_ne_indicator uses Gurobi's native indicator constraints, which need no M at all. Mirroring DeciDB's rows would only test that the mirror matches.
  • No worked answers. A hand-computed expected answer checks only the instance its author thought through. An encoding bug that happens to give the same number passes. The suite forbids them.
  • Each clause as the query writes it. The oracle states x + 3 <= 10 as a constraint row, x <= 10 - 3, never as the bound x <= 7 on the variable itself. Moving a row into a bound is a simplification DeciDB makes, and the oracle must not repeat it.

The oracle's solver is Gurobi only. HiGHS is never an oracle fallback, since HiGHS is one of the two backends under test. The oracle sets Gurobi's NonConvex parameter to 2 whenever a model has a quadratic term, so convex and non-convex quadratic models are stated the same way.

The oracle cache

An oracle solve is deterministic for a given test and database, so its result is cached on disk. Each entry is keyed by the test's id and a hash of the test function's source and the database file. Changing a test's body invalidates only that test's entry. On a hit, the model-building calls do nothing and the solve returns the cached result, so a rerun spends no Gurobi time on the tests that did not change.

A run of the whole suite that passes removes the entries it did not use. A run filtered with -k or -m keeps them, which is why a focused run always passes one of the two.

The scope suite

The scope language (when, per, by) has its own oracle, which reads no SQL at all. It builds the model the language defines from a plain description of the clauses.

A scope test describes its query to ScopedModel as Python data: the result rows, the decisions with their keys, and each clause with its scope. The oracle then follows the language's definition step by step. It keeps the rows a when keeps, splits them into the classes of the per key, generates the clause once per class, and evaluates each reducer over its by group. It solves the result with Gurobi through the same interface as the main oracle.

The SQL string and the oracle's statement sit side by side. In the combination grid, each body is a pair of functions: one writes the SQL, the other states the same clause to the oracle.

test_scope_combinations.py: one clause, two statements
    "one-reducer": (
        lambda agg, inner: f"{agg}({inner}x) by (t.g) <= t.cap",
        lambda agg, inner: ((_reduce(agg, inner, ("g",)),), "<=", (CAP,)),
    ),

judge_scoped then checks DeciDB's answer against the same clauses: every row of a decision's class shows one value, a whole-numbered decision is whole and within its bounds, every generated clause holds, and the objective reaches the oracle's optimum. The solver and the judge build their clauses with the same code, so they cannot drift apart. And because the oracle never sees the SQL, a test that keeps passing after its SQL is respelled shows that the two spellings mean the same thing.

Some shapes the scope oracle cannot state: a product of decisions, a square, an ABS, an AVG under <>. For those, _brute_force.py gives each solver column a small whole-number domain, enumerates every assignment, and keeps the best one that satisfies the constraints, written as plain Python.

The combination grid

test_scope_combinations.py crosses every part of the scope language with every other. A decision is per row or keyed. The scope in front of the clause is one of eight spellings: no per, per row, per () or a key, each with or without a when. The clause body is a per-row bound alone, one reducer, a decision beside a reducer, or two reducers with different by keys. The reducer is SUM, AVG, MIN or MAX, with one of four scopes of its own. That makes 2 × 8 × (1 + 3 × 4 × 4) = 784 cells.

Each cell has two allowed outcomes: the oracle's optimum, or the error the language defines for that data, with the same phrase in its message. Never a message that the shape is not supported, never a wrong answer, never an internal error. The grid exists to find bugs that only a combination shows. It is kept whole under one rule: no two cells reach the same set of branches in the DECIDE code.

The other scope suites each cover one part of the language: declarations (test_scope_declare.py), clause generation, reducers with a by and with their own scope, the objective, the rule that a key must determine what its clause reads (test_scope_determination.py), the value rewrite, bare clauses, the language specification's eight worked examples as written and in fully explicit form, the EXPLAIN and DIAGNOSE text, and every removed spelling's message (test_scope_removed_syntax.py).

The suites

Each suite answers one question about the system. The Python suite judges answers; the C++ and SQL logic tests check internal pieces; the golden dumps check the model itself.

The DIAGNOSE suites need their own judge, because a diagnosis can go wrong while its numbers stay right: the solve still fails and a diagnosis still appears, but it blames text the user never wrote. Two invariants are checked mechanically. Every identifier and number in a reported edit comes from the user's query, not from an internal constant such as a Big-M. And an infeasible query under DIAGNOSE comes back with a repair that, applied to the query, makes it solve, or with a statement that it could not be analyzed; a sweep across scales and clause shapes checks this.

Golden model dumps

Every test above asks what the answer is. Two different models routinely share an optimum, so a change can alter which rows are emitted, how large a Big-M is or how an auxiliary is bounded, and every answer stays the same. The golden dumps make such a change visible. They are characterization tests: they record what the system does and fail on any difference, right or wrong, so a person reads it.

corpus.sql holds 112 queries, each there for the shape of its constraints, not for its answer. With DECIDB_DUMP_MODEL set, DeciDB writes the exact model it hands the backend: columns with their bounds and integrality, rows with their senses and coefficients, and the native constraints. There is one baseline per backend, because the backend is part of the model: Gurobi states some constructs natively where HiGHS receives them lowered to linear rows. The Gurobi baseline holds 112 models and the HiGHS baseline 109; the other three queries are refused on HiGHS, and that refusal is recorded too.

make decide-test runs check.sh before any Python test and fails on any difference. When a difference is intended, capture.sh --solver gurobi and --solver highs regenerate the baselines, and they are committed with the change that caused them. A missing baseline fails; it does not skip.

Testing a rewrite

A rewrite rule replaces the solver with an algorithm, so its tests check that the algorithm and the solver agree. Every rule ships three kinds:

  1. A differential oracle test (test_direct_<id>_<slug>.py). Each case runs three times: on the independent oracle, on DeciDB with rewriting off (the solver's path), and on DeciDB with rewriting required (so the test fails if the rule does not apply). Both DeciDB runs must satisfy every constraint and reach the oracle's objective, or all three must call the case infeasible. Bad data goes to an error table where both paths must fail.
  2. The conformance suite (test_direct_rule_conformance.py). It checks what every rule owes the user whatever its algorithm: the result's columns and rows, prepared statements, serialization, EXPLAIN, the error under require, the solver path under off, a forced backend and DIAGNOSE. A rule joins it by adding one fixture. Each fixture also lists near misses, queries one step outside the rule's shape, which must decline and still answer as the solver does.
  3. C++ cases for each branch where the rule's condition declines (test_decidb_direct_decline.cpp), and a test that runs every rule against every other rule's shapes, since two rules must never apply to one query.

Guards on every run

  • The skip audit. Every allowed reason to skip a test is declared in advance: no Gurobi, no database, no binary, no solver and no cached answer, and one known case of Gurobi nondeterminism on a non-convex quadratic model. A skip with any other reason fails the run. A skip because DeciDB refused a query is never declarable: it would hide a shape that stopped working behind a green run. The audit prints passed plus skipped, a total that stays the same between runs.
  • The leak guard. Every query run through the test wrapper fails its test if the output holds an internal error or an internal tag name.
  • The removed-spelling guard. Every query fails its test if DeciDB answers that a spelling is removed, except in the one suite written to check those messages. A scanner also keeps removed spellings out of every test file, the golden corpus and the benchmark queries.

Running the suite

The same suite runs under several settings, because one DeciDB build answers a query in several ways: on Gurobi or HiGHS, rewritten or solved, with or without a serialization round trip.

CommandWhat it checks
./test/decide/run_tests.sh -k <pattern>The tests a change touches, while developing
make decide-testThe golden models, then the whole Python suite, as each host picks its solver
DECIDB_FORCE_SOLVER=highs make decide-testEvery query on HiGHS, the solver every build has
DECIDB_TEST_DIRECT_SOLVE=off make decide-testEvery query on the solver's path, with query rewriting off
DECIDB_VERIFY_SERIALIZER=1 make decide-testEvery plan survives DuckDB's serialization round trip
build/release/test/unittest "[decidb]"The C++ tests
test/decide/run_direct_matrix.shThe five checks from make decide-test down, with one summary line each

A forced backend name that DeciDB does not know is refused, never ignored, so a typo cannot run the default solver under a name that promises another. The Python suite runs on several workers at once with pytest-xdist, since much of its time is solver time limits, not work.

Coverage

Coverage is read two ways: what each feature's tests check, kept as a written map, and which branches of the code the tests run, measured by an instrumented build.

What each area's tests check

For each feature area, the internal docs list the scenarios its tests cover and the pairs of features tested together. Each test checks at one of five levels:

LevelWhat it shows
OracleThe answer is optimal: objective and vector agree with an independent model
Scope oracleThe answer is optimal under the scope language's own definition, or brute force
Constraint onlyThe constraints hold; allowed only for a query with no objective
Expected failureA known defect or an unbuilt feature, kept so that the fix is noticed
Error testAn invalid query is refused with the right message

Open gaps are ranked by risk. The highest is an optimizer rewrite meeting another feature, such as a Big-M under a per scope or a quadratic matrix with per, since two features that each pass alone can still fail together.

Branch coverage

make decide-coverage builds an instrumented copy of DeciDB in build/coverage with Clang's source-based coverage, limited to the files it names. By default those are the query rewriting code and the data-bound pass. It then runs the Python suite with one profile per test, and the C++ tests as one more profile.

The unit it counts is the arm: one outcome of one branch condition, the true side or the false side of an if, a && or a loop test. coverage_report.py reports, for each test, the arms it reaches and the arms only it reaches. With --unreached it also lists every arm no test reaches. coverage_report.py compare OLD NEW lists the arms an older run reached and a newer run does not, matching arms by their condition text so that code that moved still matches.

The measurements back four rules for tests:

  • Every decision point a change adds gets a test that reaches it and fails if that branch is removed.
  • A grid case must reach an arm no other case reaches, or it is redundant.
  • When code is deleted, the tests that only reached it are deleted too.
  • An arm no test reaches is either deleted or listed with its reason. Each listed one checks a promise another component makes, which no query can break.

Branch coverage shows which branches a test runs, not whether its assertion would catch a wrong value there. That second question is the oracle's.
